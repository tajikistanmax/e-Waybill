
### 3.3. Детализация сценариев оформления ЭПЛ

#### Сценарий № 1. Стандартный сценарий (коммерческая перевозка, городской рейс)

| Шаг | Действие | Роль | Валидация |
| :--- | :--- | :--- | :--- |
| 1 | Авторизация в системе через ЕСИА | Диспетчер | Проверка прав |
| 2 | Создание ЭПЛ, заполнение Т1 | Диспетчер | Проверка обязательных полей |
| 3 | Выбор вида перевозки «коммерческая» | Диспетчер | Автопоявление ИНН |
| 4 | Ввод данных о ТС | Диспетчер | Валидация госномера |
| 5 | Выбор водителя из справочника | Диспетчер | Проверка прав |
| 6 | Ввод маршрута (до 10 точек) | Диспетчер | — |
| 7 | Сохранение Т1 | Диспетчер | Проверка всех полей |
| 8 | Уведомление медика | Система | — |
| 9 | Медик заполняет Т2 (результат осмотра) | Медик | Дата осмотра ≤ дата начала рейса |
| 10 | Медик подписывает Т2 УКЭП | Медик | Проверка сертификата |
| 11 | Уведомление механика | Система | — |
| 12 | Механик заполняет Т3 (чек-лист техосмотра) | Механик | Все 10 пунктов заполнены |
| 13 | Механик подписывает Т3 УНЭП/УКЭП | Механик | Проверка подписи |
| 14 | Механик заполняет Т4 (одометр выезд) | Механик | Одометр ≥ 0 |
| 15 | Механик подписывает Т4 | Механик | Проверка подписи |
| 16 | Генерация QR-кода | Система | ≤ 0,5 сек |
| 17 | Водитель выполняет рейс | Водитель | — |
| 18 | Механик заполняет Т5 (одометр въезд) | Механик | Показания ≥ Т4 |
| 19 | Механик подписывает Т5 | Механик | — |
| 20 | Проверка наличия всех титулов | Система | Все подписаны |
| 21 | Автозакрытие ЭПЛ | Система | Статус «Закрыт» |
| 22 | Формирование XML-пакета | Система | Валидация по XSD |
| 23 | Отправка в ГИС ЭПД | Система | Статус «Отправлен» |
| 24 | Получение подтверждения | Система | Статус «Принят» |
| 25 | Архивация (5 лет) | Система | — |

**Бизнес-правила:**
- Т2 → Т3 → Т4 (строгая последовательность).
- При результате «не годен» или «неисправно» — блокировка.
- QR-код обновляется каждые 60 секунд.

#### Сценарий № 2. Длительный рейс (> 1 суток)
- Срок действия ЭПЛ до 5 дней.
- Послерейсовый осмотр обязателен.

#### Сценарий № 3. Смена водителей в пути
- В Т1 указываются несколько водителей.
- При смене фиксируются показания одометра.

#### Сценарий № 4. С прицепом
- В Т1 добавляется блок «Сведения о прицепе».
- Чек-лист техосмотра дополняется пунктами по прицепу.

#### Сценарий № 5. Для собственных нужд
- Вид перевозки «собственные нужды».
- ИНН необязателен.

#### Сценарий № 6. С внешним медработником (АДМК)
- Данные передаются автоматически из АДМК через API.
- Медик только подписывает.

#### Сценарий № 7. Аннулирование ЭПЛ
- Только до момента закрытия.
- Статус «Аннулирован», в ГИС ЭПД не передаётся.

#### Сценарий № 8. Корректировка данных
- Только для пользователей с правом корректировки.
- Все изменения логируются.

#### Сценарий № 9. Проверка инспектором ГИБДД
- Сканирование QR-кода.
- Отображение всех титулов в режиме чтения.

#### Сценарий № 10. Восстановление после сбоя
- Данные сохраняются в резервной копии.
- Автоматическое восстановление незакрытых ЭПЛ.

*(Остальные 15 сценариев — по требованию Заказчика: перевозка опасных грузов, скоропортящихся грузов, международные перевозки, такси, перевозка детей, аренда ТС, несколько прицепов, комбинированные перевозки, сезонные перевозки и др.)*

## Раздел 4. ТРЕБОВАНИЯ К СИСТЕМЕ В ЦЕЛОМ

### 4.1. Требования к архитектуре
- Микросервисная архитектура.
- Компоненты: сервис ЭПЛ, сервис интеграции с ГИС ЭПД, сервис ЕСИА, сервис ЭП, сервис QR, сервис уведомлений, сервис хранения.
- Взаимодействие через REST API + асинхронные очереди (RabbitMQ/Kafka).

### 4.2. Требования к надёжности
- Доступность: 99,95%.
- RPO ≤ 15 минут.
- RTO ≤ 2 часа.
- Резервирование ЦОД (основной/резервный).

### 4.3. Требования к производительности
- Нагрузка: ≥ 100 000 ЭПЛ/сутки.
- Время отклика API ≤ 1 сек (95% запросов).
- Генерация QR-кода ≤ 0,5 сек.
- Пропускная способность ≥ 1000 RPS.
- Одновременных пользователей ≥ 10 000.

### 4.4. Требования к информационной безопасности
- СКЗИ класса КС1/КС2 (КриптоПро CSP, ViPNet).
- Межсетевое экранирование (сертифицированный МЭ).
- TLS 1.3, VPN (ViPNet для промышленного контура).
- SIEM-система с хранением логов ≥ 1 года.
- Защита ПД (152-ФЗ): обезличивание, согласие на обработку.

### 4.5. Требования к хранению данных
- Срок хранения ЭПЛ: 5 лет.
- Резервное копирование: ежедневное полное, еженедельное инкрементное.
- БД: PostgreSQL (структурированные данные) + S3 (XML-пакеты).
- Шифрование данных в покое (AES-256).

### 4.6. Требования к масштабируемости
- Горизонтальное масштабирование (Kubernetes).
- Автоматическое масштабирование при нагрузке (HPA).

### 4.7. Требования к эргономике
- Интерфейс по дизайн-системе Госуслуг.
- Адаптивный дизайн.
- Соответствие 422-ФЗ (доступность).

## Раздел 7. ТРЕБОВАНИЯ К ИНТЕГРАЦИИ

### 7.1. Интеграция с ГИС ЭПД
- Протокол: REST API (HTTPS).
- Запросы:
  - Отправка ЭПЛ (POST /api/v1/epd/send).
  - Получение статуса (GET /api/v1/epd/status/{guid}).

- Протокол: OpenID Connect.

- Использование УНЭП («Госключ»).

### 7.3. Интеграция с СМЭВ
- Межведомственный обмен.
- Запросы к ГИБДД, медрегистрам.

### 7.4. Интеграция с АДМК
