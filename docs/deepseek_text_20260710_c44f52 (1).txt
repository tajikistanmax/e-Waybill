1. Т5 заполняется после возвращения ТС (после рейса).
2. Показания одометра не могут быть меньше показаний Т4 (логический контроль).
3. Разность пробега (Т5 — Т4) не может превышать нормативное значение (контрольное правило, например, для городских рейсов ≤ 500 км, для междугородних — по расчёту).
4. Дата въезда должна быть ≥ даты выезда (Т4) и ≤ срока действия ЭПЛ.

#### 5.1.6. Заполнение Титула 6 (Послерейсовый медицинский осмотр)

**Состав полей Титула 6:** Аналогичен составу Титула 2.

**Обязательность:** Условно-обязательный. Заполняется только если в Т1 установлен признак «Обязательность послерейсового медосмотра» = «Да».

**Требования к подписанию:** Только УКЭП (усиленная квалифицированная электронная подпись) медработника.

**Бизнес-правила для Т6:**
1. Заполнение Т6 возможно только после заполнения Т5.
2. Дата осмотра должна быть ≥ даты въезда (Т5).
3. При результате «НЕ ГОДЕН» система выдаёт предупреждение, но не блокирует закрытие ЭПЛ (в отличие от Т2).

#### 5.1.7. Закрытие ЭПЛ и передача в ГИС ЭПД

**Этапы автоматического закрытия:**
1. Система проверяет наличие всех обязательных титулов:
   - Т1 — подписан (диспетчер).
   - Т2 — подписан (медик, УКЭП).
   - Т3 — подписан (механик, УНЭП/УКЭП).
   - Т4 — подписан (механик, УНЭП/УКЭП).
   - Т5 — подписан (механик, УНЭП/УКЭП).
   - Т6 — подписан (медик, УКЭП) — если признак в Т1 = «Да».
2. Система проверяет логическую целостность данных (последовательность дат, показания одометра).
3. Формируется XML-пакет согласно Приказу ФНС № ЕД-7-26/116@ (4 обязательных XML-файла).
4. XML-пакет подписывается УКЭП собственника ТС (или диспетчера с правом подписи).
5. Отправка XML-пакета в ГИС ЭПД через аккредитованного оператора ЭДО.
6. Получение статуса от ГИС ЭПД:
   - «Принят» — ЭПЛ считается юридически значимым.
   - «Ошибка» — система формирует уведомление диспетчеру, повторная отправка.
7. ЭПЛ получает статус «Закрыт» (при успешной передаче) или «Ошибка отправки» (при ошибке).
8. Архивация ЭПЛ в системе на 5 лет.

**Аннулирование ЭПЛ:**
- ЭПЛ может быть аннулирован только до момента закрытия.
- Диспетчер нажимает кнопку «Аннулировать», указывает причину.
- Аннулированный ЭПЛ не передаётся в ГИС ЭПД.
- Все аннулированные ЭПЛ сохраняются в архиве с пометкой «Аннулирован».

## РАЗДЕЛ 7. ТРЕБОВАНИЯ К ИНТЕГРАЦИИ

### 7.1. Интеграция с ГИС ЭПД

**Протокол обмена:** REST API (HTTPS).

**Перечень запросов:**

| № | Запрос | Метод | URL | Описание |
| :--- | :--- | :--- | :--- | :--- |
| 1 | Отправка ЭПЛ | POST | /api/v1/epd/send | Передача XML-пакета ЭПЛ в ГИС ЭПД |
| 2 | Получение статуса | GET | /api/v1/epd/status/{guid} | Проверка статуса обработки ЭПЛ |
| 3 | Аннулирование | POST | /api/v1/epd/cancel/{guid} | Отмена ранее переданного ЭПЛ |
| 4 | Получение информации об ЭПЛ | GET | /api/v1/epd/info/{guid} | Получение данных ЭПЛ из ГИС ЭПД |

**XML-схема:** Согласно Приказу ФНС России от 17.02.2023 № ЕД-7-26/116@ (4 обязательных XML-файла: Титулы 1-5, плюс Титул 6 при необходимости).

**Взаимодействие через оператора ЭДО:**
- Платформа ЭПЛ взаимодействует с ГИС ЭПД через аккредитованных операторов электронного документооборота.
- Операторы: СберКорус, Тензор, СКБ Контур, Такском, Калуга Астрал, Эдисофт, Э-КОМ.
- Выбор оператора осуществляется в настройках Платформы (возможно несколько операторов).

**Требования к передаче:**
- XML-пакет должен быть сформирован в соответствии с XSD-схемой Приказа ФНС.
- Отправка осуществляется с использованием защищённого канала (TLS 1.3).
- При получении ошибки система автоматически повторяет отправку (не более 3 раз).

### 7.2. Интеграция с ЕСИА (Госуслуги)

**Протокол:** OpenID Connect.

**Функции:**
1. Аутентификация пользователей (диспетчеров, медиков, механиков, администраторов) через портал Госуслуг.
2. Получение данных пользователя (ФИО, СНИЛС, ИНН, контактные данные) для заполнения профиля.
3. Использование УНЭП («Госключ») для подписания титулов Т1, Т3, Т4, Т5.

**Требования:**
- Поддержка OpenID Connect с использованием алгоритмов RS256/ES256.
- Получение токенов доступа с ограниченным сроком действия (access token — 1 час, refresh token — 30 дней).
- Поддержка двухфакторной аутентификации через ЕСИА (по требованию Заказчика).

### 7.3. Интеграция с СМЭВ (Система межведомственного электронного взаимодействия)

**Функции:**
1. Запрос к ГИБДД для проверки данных ТС (госномер, VIN, статус регистрации).
2. Запрос к базе водительских удостоверений (проверка прав водителя).
3. Запрос к медрегистрам (для проверки лицензий медицинских организаций).

**Протокол:** СМЭВ 3.0 (SOAP/XML).

**Требования:**
- Поддержка электронных подписей (УКЭП) для защиты запросов.
- Логирование всех запросов и ответов СМЭВ.
- Обработка ошибок при недоступности внешних систем.

### 7.4. Интеграция с медицинскими АДМК

**Функции:**
1. Автоматическая передача данных медицинского осмотра (алкотестер, ЭКГ, тонометр) в Т2 и Т6.
2. Автоматическое заполнение полей Т2 и Т6 данными из АДМК.
3. Предоставление медику возможности проверки и корректировки данных перед подписанием.

**Протокол:** REST API или MQTT.

**Формат данных:** JSON или XML.

**Требования:**
- Шифрование канала (TLS 1.3).
- Аутентификация АДМК в системе (API-ключ или сертификат).
- Обработка ошибок при недоступности АДМК (возможность ручного ввода данных).

### 7.5. Интеграция с тахографами и ГЛОНАСС (опционально)

**Функции:**
1. Автоматическое снятие показаний одометра для Т4 и Т5.
2. Контроль маршрута в реальном времени через ГЛОНАСС.
3. Отслеживание отклонений от маршрута.

**Протокол:** REST API или специализированный протокол от производителя оборудования.

**Требования:**
- Поддержка основных производителей тахографов (Штрих-М, Атол, VDO).
- Поддержка российских систем ГЛОНАСС (ГЛОНАСС-навигация, ЭРА-ГЛОНАСС).
- Обработка данных в реальном времени (задержка ≤ 10 секунд).

| :--- | :--- |
| API-каналы | TLS 1.3 (сертификаты, проверка отзыва) |
| VPN | ViPNet (для промышленного контура), OpenVPN (для тестового контура) |
| Межсетевое экранирование | Сертифицированный межсетевой экран с функцией глубокого анализа пакетов |
| Антивирусная защита | Сертифицированное антивирусное ПО (Kaspersky, Dr.Web) |

### 8.3. Защита от несанкционированного доступа

| Параметр | Требование |
| :--- | :--- |
| Аутентификация | Двухфакторная аутентификация (пароль + SMS/код Госуслуг через ЕСИА) |
| Разграничение доступа | Ролевая модель доступа (RBAC): Администратор, Диспетчер, Медик, Механик, Водитель |
| Защита от брутфорса | Ограничение количества попыток входа (5 попыток → блокировка на 15 минут) |
| Защита от SQL-инъекций | Использование параметризованных запросов и ORM (Hibernate/Spring Data JPA) |

### 8.4. Регистрация событий безопасности (SIEM)

| Параметр | Требование |
| :--- | :--- |
| SIEM-система | MaxPatrol SIEM 8+ или аналогичная сертифицированная система |
| Логирование | Логирование всех входов, действий, ошибок |
| Содержание логов | IP-адрес, время, пользователь, действие, статус выполнения |
| Хранение логов | Не менее 1 года (для критических событий — 3 года) |
| Сигналы о подозрительной активности | Автоматическое оповещение администратора при подозрительных действиях (брутфорс, множественные неудачные входы) |

### 8.5. Защита персональных данных (152-ФЗ)

| Параметр | Требование |
| :--- | :--- |
| Обезличивание данных | Отчёты содержат обезличенные данные (агрегированная информация) |
| Согласие на обработку ПД | Согласие водителей и медработников на обработку персональных данных (электронная форма) |
| Шифрование ПД | Шифрование персональных данных в БД (AES-256) |
| Доступ к ПД | Только авторизованные пользователи с соответствующими ролями |
