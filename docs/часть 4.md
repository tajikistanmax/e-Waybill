# ЧАСТЬ 4. ФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ (ПРОДОЛЖЕНИЕ)  
## ТИТУЛЫ 4–6, МОБИЛЬНОЕ ПРИЛОЖЕНИЕ, АДМИНИСТРИРОВАНИЕ, ОТЧЁТНОСТЬ

---

### 5.1.4. Полное описание Титула 4 (Показания одометра при выезде)

**Назначение:** Фиксация показаний одометра транспортного средства в момент выезда из гаража/парковки.

**Обязательность:** **Всегда обязательный титул.** Без Т4 ЭПЛ не может быть продолжен, и не генерируется QR-код.

**Кто имеет право заполнять:** Только **механик** (или иное уполномоченное лицо, ответственное за фиксацию одометра).

**Кто имеет право подписывать:** Механик (УНЭП через Госуслуги или УКЭП).

**Полный перечень полей Титула 4:**

| № | Название поля | Тип данных | Обязательность | Валидация | Описание |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 1 | **Дата выезда** | Дата (ДД.ММ.ГГГГ) | **Да** | Формат ДД.ММ.ГГГГ, ≥ даты Т3 | Дата фактического выезда ТС |
| 2 | **Время выезда** | Время (ЧЧ:ММ) | **Да** | Формат ЧЧ:ММ | Время фактического выезда ТС |
| 3 | **Показания одометра (км)** | Целое число | **Да** | ≥ 0 | Показания одометра в километрах |
| 4 | **ФИО лица, зафиксировавшего показания** | Строка (до 100 символов) | **Да** | Из справочника (автоматически) | Кто зафиксировал показания |
| 5 | **Электронная подпись** | Файл (сертификат) | **Да** | УНЭП (Госуслуги) или УКЭП | ЭП механика |

**Бизнес-правила для Т4 (обязательные к реализации):**

1. Заполнение Т4 возможно **только после подписания Т2 и Т3**.
2. После подписания Т4 система **автоматически генерирует QR-код** для водителя.
3. QR-код содержит **уникальный идентификатор ЭПЛ (GUID)** и **временную метку** для защиты от подделки.
4. QR-код **обновляется каждые 60 секунд** (динамический).
5. Показания одометра должны быть **≥ 0**.
6. Дата выезда должна быть **≥ даты Т3**.
7. Т4 не может быть изменён после подписания.
8. При невозможности снять показания (неисправный одометр) — допускается ручной ввод с отметкой «Одометр неисправен» (требуется подтверждение механика).
9. При использовании тахографа (интеграция) показания одометра могут передаваться **автоматически**.
10. После подписания Т4 водитель получает уведомление о готовности QR-кода (Push / Email).

### 5.1.5. Полное описание Титула 5 (Показания одометра при въезде)

**Назначение:** Фиксация показаний одометра транспортного средства в момент въезда в гараж/парковку после завершения рейса.

**Обязательность:** **Всегда обязательный титул.** Без Т5 ЭПЛ не может быть закрыт.

**Кто имеет право заполнять:** Только **механик** (или иное уполномоченное лицо).

**Кто имеет право подписывать:** Механик (УНЭП через Госуслуги или УКЭП).

**Полный перечень полей Титула 5:**

| № | Название поля | Тип данных | Обязательность | Валидация | Описание |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 1 | **Дата въезда** | Дата (ДД.ММ.ГГГГ) | **Да** | Формат ДД.ММ.ГГГГ, ≥ даты Т4 | Дата фактического въезда ТС |
| 2 | **Время въезда** | Время (ЧЧ:ММ) | **Да** | Формат ЧЧ:ММ | Время фактического въезда ТС |
| 3 | **Показания одометра (км)** | Целое число | **Да** | ≥ показаний Т4 | Показания одометра в километрах |
| 4 | **ФИО лица, зафиксировавшего показания** | Строка (до 100 символов) | **Да** | Из справочника (автоматически) | Кто зафиксировал показания |
| 5 | **Электронная подпись** | Файл (сертификат) | **Да** | УНЭП (Госуслуги) или УКЭП | ЭП механика |

**Бизнес-правила для Т5 (обязательные к реализации):**

1. Т5 заполняется **после возвращения ТС** (после рейса).
2. Показания одометра **не могут быть меньше** показаний Т4 (логический контроль).
3. Разность пробега (Т5 — Т4) **не может превышать нормативное значение**:  
   - Для городских рейсов: ≤ 500 км.  
   - Для пригородных: ≤ 1000 км.  
   - Для междугородных: по расчёту, но не более 5000 км.  
   - При превышении — система выдаёт **предупреждение**, но не блокирует закрытие.
4. Дата въезда должна быть **≥ даты выезда (Т4)** и **≤ срока действия ЭПЛ**.
5. Т5 не может быть изменён после подписания.
6. При использовании тахографа (интеграция) показания одометра могут передаваться **автоматически**.
7. Если ТС не вернулось в гараж в установленный срок (превышение срока действия ЭПЛ), система **уведомляет диспетчера** и переводит ЭПЛ в статус «Просрочен».

### 5.1.6. Полное описание Титула 6 (Послерейсовый медицинский осмотр)

**Назначение:** Фиксация результатов послерейсового медицинского осмотра водителя.

**Обязательность:** **Условно-обязательный.** Заполняется **только если** в Т1 установлен признак «Обязательность послерейсового медосмотра» = «Да».

**Кто имеет право заполнять:** Только **медицинский работник**.

**Кто имеет право подписывать:** Только **медицинский работник** с использованием **УКЭП**.

**Полный перечень полей Титула 6:**

| № | Название поля | Тип данных | Обязательность | Валидация | Описание |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 1 | **Дата осмотра** | Дата (ДД.ММ.ГГГГ) | **Да** (при заполнении) | Формат ДД.ММ.ГГГГ, ≥ даты Т5 | Дата проведения осмотра |
| 2 | **Время осмотра** | Время (ЧЧ:ММ) | **Да** (при заполнении) | Формат ЧЧ:ММ | Время проведения осмотра |
| 3 | **Результат осмотра** | Справочник | **Да** (при заполнении) | Выбор: ГОДЕН / НЕ ГОДЕН | Результат осмотра |
| 4 | **ФИО медработника** | Строка | **Да** (при заполнении) | Из справочника | ФИО медработника |
| 5 | **СНИЛС медработника** | Строка | **Да** (при заполнении) | Формат: 123-456-789 01 | СНИЛС медработника |
| 6 | **Должность медработника** | Строка | **Да** (при заполнении) | Из справочника | Должность медработника |
| 7 | **Электронная подпись (УКЭП)** | Файл (сертификат) | **Да** (при заполнении) | Проверка сертификата УКЭП | УКЭП медработника |

**Бизнес-правила для Т6 (обязательные к реализации):**

1. Заполнение Т6 возможно **только после заполнения Т5**.
2. Дата осмотра должна быть **≥ даты въезда (Т5)**.
3. При результате «НЕ ГОДЕН» система выдаёт **предупреждение**, но **не блокирует** закрытие ЭПЛ (в отличие от Т2).
4. Т6 подписывается **только УКЭП**.
5. Если признак в Т1 = «Да», а Т6 не заполнен — ЭПЛ **не может быть закрыт** (обязательное условие).
6. Интеграция с АДМК возможна для **автоматической передачи данных** осмотра.
7. Т6 не может быть изменён после подписания.

### 5.1.7. Полное описание процесса закрытия ЭПЛ и передачи в ГИС ЭПД

**Этапы автоматического закрытия (выполняются системой):**

| Шаг | Действие | Ответственный | Результат |
| :--- | :--- | :--- | :--- |
| 1 | Система проверяет наличие **всех обязательных титулов**: | Система | Проверка пройдена / Ошибка |
| 2 | Т1 — подписан (диспетчер, УНЭП/УКЭП) | Система | Проверка подписи |
| 3 | Т2 — подписан (медик, УКЭП) | Система | Проверка УКЭП |
| 4 | Т3 — подписан (механик, УНЭП/УКЭП) | Система | Проверка подписи |
| 5 | Т4 — подписан (механик, УНЭП/УКЭП) | Система | Проверка подписи |
| 6 | Т5 — подписан (механик, УНЭП/УКЭП) | Система | Проверка подписи |
| 7 | Т6 — подписан (медик, УКЭП) — **если признак в Т1 = «Да»** | Система | Проверка УКЭП |
| 8 | Система проверяет **логическую целостность** данных: | Система | Проверка пройдена |
| 9 | — последовательность дат (Т2 ≤ Т3 ≤ Т4 ≤ Т5) | Система | — |
| 10 | — показания одометра (Т5 ≥ Т4) | Система | — |
| 11 | — срок действия ЭПЛ не превышен | Система | — |
| 12 | Формируется **XML-пакет** согласно Приказу ФНС № ЕД-7-26/116@ | Система | XML-файл создан |
| 13 | XML-пакет подписывается **УКЭП собственника ТС** (или диспетчера с правом подписи) | Система | XML подписан |
| 14 | Отправка XML-пакета в **ГИС ЭПД** через аккредитованного оператора ЭДО | Система | Статус «Отправлен» |
| 15 | Получение статуса от ГИС ЭПД: | Система | — |
| 16 | — «Принят» → ЭПЛ считается **юридически значимым** | Система | Статус «Закрыт» |
| 17 | — «Ошибка» → система формирует уведомление диспетчеру, повторная отправка (до 3 раз) | Система | Повторная попытка |
| 18 | ЭПЛ получает статус **«Закрыт»** (при успешной передаче) или **«Ошибка отправки»** (при ошибке) | Система | Статус обновлён |
| 19 | Архивация ЭПЛ в системе на **5 лет** | Система | Архив |

**Аннулирование ЭПЛ:**

| Шаг | Действие | Ответственный | Результат |
| :--- | :--- | :--- | :--- |
| 1 | Диспетчер открывает ЭПЛ в ЛК | Диспетчер | — |
| 2 | Нажимает кнопку «Аннулировать» | Диспетчер | — |
| 3 | Вводит причину аннулирования (обязательно) | Диспетчер | Причина сохранена |
| 4 | Подтверждает аннулирование | Диспетчер | — |
| 5 | ЭПЛ получает статус **«Аннулирован»** | Система | — |
| 6 | Аннулированный ЭПЛ **не передаётся в ГИС ЭПД** | Система | — |
| 7 | Аннулированный ЭПЛ сохраняется в архиве с пометкой «Аннулирован» и причиной | Система | Архив |

**Бизнес-правила для закрытия:**
- ЭПЛ может быть аннулирован **только до момента закрытия**.
- Аннулированный ЭПЛ **нельзя восстановить**.
- При ошибке отправки в ГИС ЭПД система **автоматически повторяет отправку** до 3 раз с интервалом 5 минут.
- При повторной ошибке ЭПЛ переводится в статус **«Ошибка отправки»**, администратор получает уведомление.
- Статус «Ошибка отправки» может быть сброшен администратором для повторной отправки.

### 5.2. Подсистема «Мобильное приложение водителя»

**Назначение:** Обеспечение доступа водителя к ЭПЛ, отображение QR-кода для проверки контролирующими органами.

**Платформы:**
- **iOS:** 14+.
- **Android:** 10+.

**Подход:** Нативный подход (Swift для iOS, Kotlin для Android) или кросс-платформенный (React Native / Flutter) — по согласованию с Заказчиком.

**Полные функциональные требования:**

| № | Функция | Описание | Требования | Бизнес-правила |
| :--- | :--- | :--- | :--- | :--- |
| 1 | **Авторизация через ЕСИА** | Вход в приложение через портал Госуслуг (OpenID Connect) | Проверка прав пользователя, получение данных (ФИО, СНИЛС) | Доступ только для авторизованных водителей |
| 2 | **Отображение активных ЭПЛ** | Список всех ЭПЛ, назначенных водителю | Статусы: «Ожидает начала», «Активен», «Завершён», «Аннулирован», «Просрочен» | Отображаются только ЭПЛ, где водитель указан в Т1 |
| 3 | **Отображение QR-кода** | Динамический QR-код для предъявления инспекторам | Обновление каждые 60 секунд, отображение в полноэкранном режиме, возможность увеличения | QR-код отображается только для активных ЭПЛ |
| 4 | **Просмотр ЭПЛ** | Отображение всех титулов ЭПЛ в режиме чтения | Только чтение, без редактирования | Водитель не имеет права редактировать ЭПЛ |
| 5 | **Уведомления** | Push-уведомления о статусах ЭПЛ | Новые рейсы, смена статуса, напоминания об осмотрах | Использование FCM (Android) и APNS (iOS) |
| 6 | **Работа офлайн** | Кэширование QR-кода и активных ЭПЛ | Автоматическая синхронизация при восстановлении связи | QR-код доступен офлайн в течение 60 секунд после последнего обновления |
| 7 | **История ЭПЛ** | Просмотр истории завершённых и аннулированных ЭПЛ | Фильтр по дате, статусу | — |
| 8 | **Профиль** | Отображение данных водителя | ФИО, СНИЛС, контактные данные, права | — |
| 9 | **Настройки** | Настройка уведомлений, смена пароля (через ЕСИА) | Push-уведомления (вкл/выкл), язык интерфейса | — |

**Требования к безопасности мобильного приложения:**
- Шифрование данных в покое (AES-256).
- Биометрическая аутентификация (Face ID / Touch ID) — опционально.
- Защита от подмены QR-кода (динамическое обновление).
- HTTPS для всех сетевых запросов (TLS 1.3).
- Защита от jailbreak / root (опционально).

**Требования к производительности:**
- Время открытия приложения: ≤ 2 секунды.
- Время отображения QR-кода: ≤ 1 секунда.
- Обновление QR-кода: ≤ 0,5 секунды.
- Размер приложения: ≤ 50 МБ.

### 5.3. Подсистема «Личный кабинет медработника»

**Назначение:** Обеспечение доступа медицинского работника к ЭПЛ для проведения предрейсовых и послерейсовых осмотров.

**Функциональные требования:**

| № | Функция | Описание | Требования |
| :--- | :--- | :--- | :--- |
| 1 | **Авторизация через ЕСИА** | Вход в систему через портал Госуслуг | Проверка прав медработника |
| 2 | **Список назначенных ЭПЛ** | Список ЭПЛ, ожидающих медосмотра | Фильтры: по дате, по организации, по статусу, поиск по GUID |
| 3 | **Заполнение Т2 и Т6** | Внесение результатов осмотра | Все поля обязательны, дата осмотра ≤ даты рейса (для Т2) и ≥ даты въезда (для Т6) |
| 4 | **Подписание УКЭП** | Подписание титулов с использованием УКЭП | Интеграция с КриптоПро CSP, проверка сертификата (срок, отзыв) |
| 5 | **История осмотров** | Просмотр истории всех проведённых осмотров | Фильтр по дате, по водителю, по результату, экспорт (PDF, XLSX) |
| 6 | **Интеграция с АДМК** | Автоматическая передача данных осмотра (алкотестер, ЭКГ, тонометр) | REST API или MQTT, автоматическое заполнение полей Т2/Т6 |
| 7 | **Уведомления** | Получение уведомлений о новых ЭПЛ для осмотра | Email / Push (в браузере) |

**Бизнес-правила для медработника:**
1. Медик имеет доступ только к Т2 и Т6 (не имеет доступа к другим титулам).
2. Подписание Т2 и Т6 осуществляется **только УКЭП**.
3. Сертификат УКЭП проверяется на валидность при каждом подписании.
4. При интеграции с АДМК данные осмотра передаются автоматически, медик только проверяет и подписывает.
5. Медик не имеет права редактировать Т1, Т3, Т4, Т5.
6. Все действия медика логируются (аудит).

### 5.4. Подсистема «Личный кабинет механика»

**Назначение:** Обеспечение доступа механика к ЭПЛ для проведения технических осмотров и фиксации одометра.

**Функциональные требования:**

| № | Функция | Описание | Требования |
| :--- | :--- | :--- | :--- |
| 1 | **Авторизация через ЕСИА** | Вход в систему через портал Госуслуг | Проверка прав механика |
| 2 | **Список ТС на выпуск** | Список ТС, ожидающих техосмотра и выезда | Фильтры: по организации, по статусу, по дате |
| 3 | **Заполнение Т3** | Внесение результатов техосмотра (чек-лист из 10 пунктов) | Все пункты обязательны |
| 4 | **Заполнение Т4** | Внесение показаний одометра при выезде | Показания ≥ 0 |
| 5 | **Заполнение Т5** | Внесение показаний одометра при въезде | Показания ≥ показаний Т4 |
| 6 | **Подписание УНЭП/УКЭП** | Подписание титулов через Госуслуги (УНЭП) или УКЭП | Интеграция с ЕСИА для УНЭП, с КриптоПро для УКЭП |
| 7 | **История техосмотров** | Просмотр истории всех проведённых техосмотров | Фильтр по дате, по ТС, по результату |
| 8 | **Уведомления** | Получение уведомлений о новых ТС для осмотра | Email / Push (в браузере) |

**Бизнес-правила для механика:**
1. Механик имеет доступ к Т3, Т4, Т5 (не имеет доступа к Т1, Т2, Т6).
2. Все 10 пунктов чек-листа Т3 обязательны для заполнения.
3. При результате «НЕИСПРАВНО» ЭПЛ блокируется.
4. Показания одометра Т5 не могут быть меньше показаний Т4.
5. Механик не имеет права редактировать Т1, Т2, Т6.
6. Все действия механика логируются (аудит).

### 5.5. Подсистема «Администрирование»

**Назначение:** Управление системой, пользователями, справочниками, настройка бизнес-правил, аудит и мониторинг.

**Функциональные требования:**

| № | Функция | Описание | Требования |
| :--- | :--- | :--- | :--- |
| 1 | **Управление пользователями** | Добавление, блокировка, назначение ролей | Интеграция с ЕСИА, роли: Администратор, Диспетчер, Медик, Механик, Водитель |
| 2 | **Управление справочниками** | ТС, водители, медорганизации, механики, организации | Импорт/экспорт справочников (XLSX, CSV), валидация данных |
| 3 | **Настройка бизнес-правил** | Настройка обязательности Т6, валидаций, сроков | Настройка параметров валидаций, сроков действия ЭПЛ, допустимых значений |
| 4 | **Настройка операторов ЭДО** | Выбор оператора для передачи в ГИС ЭПД | Список: СберКорус, Тензор, СКБ Контур, Такском, Калуга Астрал, Эдисофт, Э-КОМ |
| 5 | **Аудит и логирование** | Логирование всех действий пользователей | Хранение логов не менее 1 года (для критических — 3 года) |
| 6 | **Мониторинг** | Статусы ЭПЛ в реальном времени | Дашборд для администратора (количество ЭПЛ, статусы, ошибки) |
| 7 | **Управление доступом** | Настройка прав доступа для ролей | RBAC (Role-Based Access Control) |
| 8 | **Экспорт данных** | Выгрузка отчётов и логов | Форматы: XML, XLSX, PDF, CSV |
| 9 | **Резервное копирование** | Управление резервными копиями | Запуск вручную или по расписанию |

**Бизнес-правила для администрирования:**
1. Администратор не имеет права редактировать ЭПЛ (только просмотр и управление пользователями/справочниками).
2. Все действия администратора логируются с указанием времени и IP-адреса.
3. Импорт/экспорт справочников осуществляется в форматах XLSX и CSV.
4. Только администратор имеет право назначать роли пользователям.
5. Администратор может блокировать пользователей (при нарушении).

### 5.6. Подсистема «Отчётность и мониторинг»

**Назначение:** Формирование отчётов, дашбордов, статистики для анализа работы системы.

**Функциональные требования:**

| № | Функция | Описание | Требования |
| :--- | :--- | :--- | :--- |
| 1 | **Формирование отчётов по ЭПЛ** | Отчёты за день, месяц, квартал | По организации, по водителям, по ТС, по статусам |
| 2 | **Экспорт данных** | Выгрузка отчётов в форматы XML, XLSX, PDF | Автоматическая отправка по расписанию (опционально) |
| 3 | **Статистика нарушений** | Отсутствие осмотров, подписей, превышение сроков | Дашборд для контролирующих органов |
| 4 | **Мониторинг в реальном времени** | Статусы ЭПЛ, активные рейсы, задержки | Дашборд для администратора и диспетчеров |
| 5 | **Автоматические отчёты** | Отправка отчётов по Email | По расписанию (ежедневно, еженедельно, ежемесячно) |

**Бизнес-правила для отчётности:**
1. Отчёты формируются на основе данных из БД и XML-пакетов, переданных в ГИС ЭПД.
2. Экспорт данных доступен только администраторам и диспетчерам с правом экспорта.
3. Статистика нарушений доступна контролирующим органам через ГИС ЭПД.
4. Данные в отчётах обезличены (агрегированная информация, без ФИО и СНИЛС).
