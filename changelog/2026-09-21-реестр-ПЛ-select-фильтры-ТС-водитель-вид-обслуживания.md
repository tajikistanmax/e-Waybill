# 2026-09-21 — Реестр ПЛ: select-фильтры «ТС», «Водитель» и «Вид обслуживания 3-С» (MIGRATION.md §8.1)

## Что изменилось
- Web `/waybills` (реестр ПЛ): три новых фильтра рядом с компанией/статусом/типом —
  **ТС** (список госномеров из реестра с учётом выбранных компании и типа), **Водитель** (ФИО + РМА; учитывается и
  второй водитель), **Вид обслуживания (3-С)** — такси / маршрут / почасовой; активен только когда выбран тип 3-С
  или «все типы» (иначе отключён с подсказкой).
- Вид обслуживания читается из `typeData.serviceKind` (TAXI/ROUTE/HOURLY, живые ПЛ) или из числового
  `typeData.typeService` (1 такси, 2 хатсайр, 3 соатбай — мигрированные ПЛ Ф5).
- «Сбросить фильтры» очищает и новые поля. i18n ru/tj.

## Как было ДО
Legacy: реестры ПЛ компании имели select-фильтры `parking_id` (ТС) и `timesheet_id` (водитель), реестр 3-С — фильтр
`type_service` (1 такси, 2 хатсайр, 3 соатбай). В e-Waybill ТС/водителя можно было найти только текстовым поиском,
фильтра по виду обслуживания не было.

## Как стало
Паритет фильтров реестра. Фильтры клиентские — над загруженным реестром (без архива, лимит 1000 строк, как и
остальные фильтры страницы); серверная пагинация/фильтрация — отдельный пункт 8.4.

## Почему
MIGRATION.md 8.1 — гэп фильтров (пользователь особо подчёркивал §8).

## Кто решил
Агент Claude по промпту Шага 2 (однозначные фильтры legacy). Баги legacy-фильтров (Company «Шаҳр»→region_id) не
переносились.

## Как проверено
- web `tsc --noEmit` ✅; страница `/waybills` на пересобранном web — HTTP 200.
- **Live (API-предпосылки фильтров, реестр диспетчера org 025680800):** 603 ПЛ, 54 различных ТС, 53 водителя;
  3-С — 161 строка (вид: TAXI 13, HOURLY 1, без вида 147 — тестовые ПЛ до появления `serviceKind`, фильтр их не
  ломает); предикат «ТС = 0114TJ01» даёт 269 строк — тот же, что применяет клиентский фильтр.
