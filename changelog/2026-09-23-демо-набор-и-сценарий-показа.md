# 2026-09-23 — Демо-набор данных и сценарий показа заказчику 24.09.2026

## Что изменилось
Добавлен повторяемый скрипт `scripts/seed-demo-showcase.ps1`, который через обычный API
заводит 6 демонстрационных перевозчиков (городской автобусный парк с двумя филиалами, такси,
грузовой, междугородний/международный пассажирский, международный грузовой CMR), их
сотрудников, водителей, ТС, маршруты и клиентов, выдаёт 50 логинов с одним известным
постоянным паролем и создаёт на сегодня 38 путевых листов всех включённых форм во всех
статусах. Написан сценарий показа `spec/DEMO-сценарий-2026-09-24.md` для владельца.

## Как было ДО
- Старые сид-скрипты (`seed-demo-*.ps1`, `seed-edge-cases.ps1`, `seed-live-gps.ps1`) ходили в
  Keycloak, который больше не используется, и в контейнер `epd-postgres`, которого нет на
  текущем стенде; работать перестали.
- Демо-логины `dispatcher`, `doctor`, `company` и др. привязаны к организации `025680800`,
  которой после восстановления перенесённых данных нет — под ними пустые кабинеты.
- Путевых листов, созданных в самой платформе, на стенде не было: показать кабинеты врача,
  механика, бухгалтера, АЗС, водителя и отчёты «за сегодня» было нечем.

## Как стало
- `scripts/demo-showcase.json` — все данные демо-набора (русский текст, UTF-8): организации
  «(демо)» с РМА `99240…`, госномера `xxxxDM01`, сотрудники, водители, ТС, маршруты, клиенты,
  логины и 38 сценариев путевых листов (форма, ТС, водитель, целевой статус, пробег, топливо,
  накладная, GPS, акт инспектора).
- `scripts/seed-demo-showcase.ps1` (ASCII, для PowerShell 5.1):
  1. upsert организаций, сотрудников, водителей, ТС, маршрутов, клиентов (сроки документов —
     от сегодняшней даты);
  2. логины (`bus.admin`, `bus1.disp`, `taxi.doctor`, …, `intl.sender`) с паролем из JSON;
     временный пароль меняется на постоянный через `/api/v1/auth/password`;
  3. путевые листы: каждый действует **своей ролью** (диспетчер выписывает и выдаёт, врач —
     медосмотр, механик — техконтроль, бухгалтер — оплата, АЗС — топливо, инспектор —
     блокировка, водитель — приём), лист доводится до целевого статуса; метка
     `typeData.demoKey = "<дата>|<ключ>"`;
  4. повторный запуск в тот же день ничего не дублирует, а доделывает недоделанное; запуск в
     новый день сначала закрывает/аннулирует вчерашние незавершённые демо-листы (освобождает ТС
     и водителей) и строит свежий набор на сегодня;
  5. проверка каждого логина (вход + что видно в кабинете), сводный отчёт за сегодня, итоговые
     таблицы логинов и листов.
- `spec/DEMO-сценарий-2026-09-24.md` — адреса, логины, что где лежит, 22 шага показа с
  ожидаемым результатом, «что делать если…», подъём стенда с нуля (compose, MinIO с quay.io,
  перенос данных legacy, демо-скрипт), известные ограничения, вопросы к заказчику.

## Почему
Завтра демонстрация заказчику: разные компании, все виды путевых листов, отчёты, кабинеты
сотрудников, водителей и филиалов. Нужен набор данных, который поднимается одной командой,
не трогает перенесённые реальные записи и не дублируется при повторном запуске.

## Кто решил
Владелец 23.09.2026: «доведи платформу до запуска к демонстрации»; задачу на демо-набор и
сценарий поставил координатор агентов. Выбраны явно демонстрационные организации «(демо)», а не
реальные компании из перенесённых данных, — чтобы не менять реальные записи (реальные компании
используются в сценарии только для отчётов по архиву, без изменений).

## Как (техника)
- Только публичное API (`/api/v1/organizations|employees|drivers|vehicles|dictionaries/*`,
  `/api/v1/org-users`, `/api/v1/auth/*`, `/api/v1/waybills/*`, `/fuel-station`, `/mobile`, `/gps`).
- Идемпотентность: upsert мастер-данных по РМА/госномеру; логины — поиск в `/org-users`;
  путевые листы — поиск по `typeData.demoKey`, доводка конечным автоматом по текущему статусу.
- Одометр выезда/возврата берётся из карточки ТС (закрытие листа переносит одометр в карточку,
  и он не может уменьшаться).
- Ограничение частоты запросов (429 / 503 с `retryAfterSeconds`) — ожидание и повтор.
- Номер дозвола E-PERMIT для международных форм подбирается под страну рейса (тестовая система
  выдаёт страну по номеру).

## Как проверено
- Прогон на локальном стенде 23.09 (после пересборки master-data и waybill другими агентами):
  `Done without problems`, 38/38 листов в целевых статусах, 8 закрытых — расчёт 200 OK;
  все 50 демо-логинов входят постоянным паролем, кабинеты видят свои данные (врач — очередь,
  АЗС — листы на заправке, водитель — свои листы, грузоотправитель — 3 накладные CMR).
- Повторный запуск: число демо-листов 66 → 66 (дубликатов нет).
- Смена дня проверена параметром `-DemoDay 2026-09-22 -RetireOnly`: все незавершённые листы
  закрыты/аннулированы (заблокированные — разблокированы и закрыты), затем обычный запуск
  создал свежий набор.
- Интерфейс (Playwright, временный тест, не коммитился): 15 из 16 проверок прошли — реестры
  диспетчеров всех 6 компаний, администратор компании видит оба филиала, кабинеты механика,
  бухгалтера, АЗС, водителя, накладные грузоотправителя, «Доступы», карточка и печатная форма с
  QR, публичная проверка QR «ПУТЕВОЙ ЛИСТ ДЕЙСТВИТЕЛЕН», сводка аналитика. Кабинет врача
  открылся с очередью (проверка искала госномер, а в очереди показано ФИО — ошибка теста).

## Найдено по ходу (передано владельцу/QA, здесь не исправлялось)
1. Нет кнопки послерейсового медосмотра (Т6) в интерфейсе — пассажирские листы нельзя закрыть
   через интерфейс (политика требует Т6); через API работает.
2. Закрытие листа отвечает сырой 500, если одометр возврата меньше уже записанного в карточке
   ТС (ответ master-data 400 не обрабатывается); выезд берёт одометр из снимка ТС на момент
   выписки, а не из текущей карточки.
3. На печатной форме у Т4/Т5 вместо ФИО диспетчера — его РМА.
