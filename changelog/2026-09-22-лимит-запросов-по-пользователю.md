# 2026-09-22 — Ограничитель частоты считает по пользователю, а не по адресу

## Что изменилось
- Ограничитель частоты запросов в обеих службах (мастер-данные и путевые листы) теперь считает
  по **двум** ключам: основной предел — на пользователя (`general-capacity`, 300 запросов в
  минуту), внешняя граница — на сетевой адрес (`ip-capacity`, по умолчанию 3000).
- Ключ пользователя — субъект токена; токен при этом **не проверяется**, разбор нужен только
  для раскладки счётчиков (подпись проверяет фильтр аутентификации дальше по цепочке).
  Непарсимый токен получает отпечаток вместо субъекта.
- Число пользовательских корзин ограничено (`max-user-keys`, 50 000): поток с уникальными
  поддельными токенами иначе раздувал бы таблицу счётчиков. При переполнении новые корзины не
  заводятся, и запрос ограничивается только пределом по адресу.
- Публичные без-токенные пути (проверка по QR, ключи подписи, настройки страницы входа,
  изображения бренда) сохраняют отдельный строгий потолок по адресу (60).
- Миграция `V74` добавила в матрицу доступа разделов роль «Пункт выдачи топлива»: в таблице было
  13 ролей из 14, поэтому на странице «Настройки → Роли» этой роли просто не было в списке.

## Как было ДО
Счёт шёл только по сетевому адресу: 300 запросов в минуту на весь узел. За общим внешним
адресом предприятия (NAT) этот лимит делили **все** сотрудники сразу, а одна страница
интерфейса делает около десяти запросов — то есть примерно 30 открытий страницы в минуту на
всю организацию. Сводный отчёт Минтранса упирался в этот же предел и падал с 503.

Роль «Пункт выдачи топлива» работала по запасному пути (зашитый список разделов в коде), но
администратор не мог настроить ей меню — её не было среди ролей на странице настроек.

## Как стало
Каждый сотрудник получает свои 300 запросов в минуту; сосед по адресу на него не влияет.
Предел по адресу остаётся защитой от потока с поддельными токенами: субъект подделать можно,
адрес — нет.

## Почему
Находка сквозной приёмки (`AUDIT.md`, находка 4, блок A5). На боевой нагрузке министерства и
крупных автопредприятий прежний счёт по адресу давал бы постоянные отказы «слишком много
запросов» при совершенно нормальной работе.

## Кто решил
Владелец 22.09 поручил довести платформу до продакшена. Выбран двухуровневый счёт, а не простое
повышение общего потолка: поднять предел по адресу до значений, комфортных для большого
предприятия, значило бы снять защиту с единичного источника.

## Как
`RateLimitFilter` в обеих службах: две таблицы счётчиков (по адресу и по пользователю),
разбор субъекта из полезной нагрузки токена без проверки подписи, ограничение числа корзин,
общая уборка устаревших окон.

## Как проверено
- `RateLimitFilterTest` (6 проверок): субъект берётся из токена; без токена ключа пользователя
  нет; непарсимый токен даёт отпечаток; два сотрудника за одним адресом не делят лимит;
  предел по адресу продолжает ограничивать поток с разными токенами; публичный путь считается
  только по адресу со своим потолком.
- Наборы: `:master-data-service:test` **125/125 ✅**, `:waybill-service:test` **343/345 ✅**
  (2 падения — Testcontainers не идут на Windows), `tsc --noEmit` ✅.
- **Live**: первый пользователь получил отказ ровно на 301-м запросе; сразу после этого второй
  пользователь с того же адреса получил 200. Матрица ролей — 14 строк, появилась
  `FUEL_STATION / fuel / fuel`.
