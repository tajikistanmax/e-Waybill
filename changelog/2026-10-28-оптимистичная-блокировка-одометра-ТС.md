# 2026-10-28 — Оптимистичная блокировка ТС (одометр)

## Что изменилось
`Vehicle` получила JPA-поле `@Version` (миграция V90, столбец `version BIGINT NOT NULL
DEFAULT 0`). `VehicleController.updateOdometer` (`PATCH /api/v1/vehicles/{id}/odometer`)
теперь при конфликте версии перечитывает актуальную запись и повторяет попытку (до 5
раз) — лишний 409 наружу (к межсервисному вызывающему, который не умеет повторять сам)
не выпускается; если конфликт не удаётся разрешить за 5 попыток, возвращается понятный
409 вместо падения.

## Как было ДО
`updateOdometer` — классическое read-check-write без защиты: читает текущий одометр,
проверяет «не меньше прежнего» по прочитанному значению, сохраняет. Два параллельных
вызова (например два потока агрегатора/закрытия ПЛ на одно ТС) могли оба пройти
проверку по одному и тому же исходному значению, и более позднее сохранение молча
стирало результат более раннего — classic lost update, без какой-либо ошибки клиенту.

## Почему
Найдено при аудите кода master-data-service 27.10.2026 как самое острое место (`@Version`
отсутствовал на всех сущностях вообще). Остальные сущности (`Organization`/`Driver`/
`Employee`) трогать не стал — конкретной гонки там не найдено, а добавление `@Version`
без нужды увеличивает риск ложных 409 на обычных последовательных правках через UI.

## Кто решил
Владелец — автономный мандат «проходи по каждому пункту, закончи проект» (28.10.2026);
реализовал агент Claude.
