# 2026-10-23 — Серверная пагинация реестра ПЛ и отчётов: убраны искусственные ограничения выборок

## Что изменилось
Легаси-листинг `GET /api/v1/waybills` и реестр `GET /api/v1/waybills/page` больше не теряют
данные молча: жёсткие константы лимитов (`LIST_CAP`, `MAX_PAGE_SIZE`) стали настраиваемыми
(лимит РАЗМЕРА страницы/выборки — защита от OOM, не лимит общего числа доступных записей);
усечение легаси-листинга явно отражается заголовком ответа; пустая область видимости тенанта
(claim `organization_rma` отсутствует в токене) теперь честно отдаёт 403, а не пустой список/0;
один оставшийся неограниченный репозиторный запрос (`GpsController.live` для организаций
филиала) переведён на фильтр статуса в SQL вместо выгрузки всей истории организации в память.

## Как было ДО
- `WaybillController.LIST_CAP = 1000` — константа жёстко вшита в код, без признака усечения:
  фронт получал максимум 1000 строк и не мог понять, уместились ли все записи.
- `WaybillRegistryService.MAX_PAGE_SIZE = 1000` — та же проблема для `?size=` постраничного
  реестра: нельзя было поднять лимит страницы конфигурацией без пересборки.
- Пустая область тенанта (`tenantScope.rmas()` вернул `{"__none__"}`, т.е. у роли нет привязки
  к организации) приводила к `List.of()` / `PageResult(List.of(), …, 0, 0)` / нулевым счётчикам —
  неотличимо от «у организации действительно нет данных».
- `WaybillRepository` содержал 3 репозиторных метода без `Pageable`
  (`findByOrganizationRmaOrderByCreatedAtDesc`, `findByOrganizationRmaInOrderByCreatedAtDesc`,
  `findByStatusOrderByCreatedAtDesc`); два были мёртвым кодом, третий использовался в
  `GpsController.live()` для филиальной области — тянул ВСЮ историю организации (после миграции
  Ф5 — потенциально миллионы строк, включая архив) и фильтровал статус ISSUED/ACTIVE в памяти.

## Как стало
- `WaybillController`: `listCap` — поле, настраиваемое через `@Value("${epd.registry.list-cap:1000}")`
  (дефолт прежний, 1000). `GET /api/v1/waybills` теперь `ResponseEntity<List<Waybill>>`: тело
  ответа не изменилось (тот же массив — существующие вызовы фронта не ломаются), но если выборка
  на уровне БД упёрлась в `listCap`, ответ несёт заголовок `X-Waybills-Truncated: true` (константа
  `WaybillController.TRUNCATED_HEADER`). Усечение считается ДО последующих фильтров в памяти
  (водитель/статус в архиве), чтобы маленький результат после фильтра не маскировал факт, что
  уровень организации был усечён.
- Пустая область тенанта → `ApiErrors.ForbiddenException` (403, RFC 7807, понятный русский текст:
  «Учётная запись не привязана к организации… обратитесь к администратору платформы для настройки
  доступа») — и в `WaybillController.list()`, и в `WaybillRegistryService.page()`/`statusCounts()`.
  Рассмотрены оба сценария пустой области: `scoped.isEmpty()` структурно недостижим (defensive-код),
  реальный путь — только `{"__none__"}`, то есть у тенант-роли НЕТ claim `organization_rma» в
  токене, — это всегда ошибка привязки учётной записи в master-data, а не «у организации нет
  данных» (легитимный «нет доступа» уже отфильтрован выше: `@PreAuthorize(READ_ROLES)` не пускает
  роли без организации вовсе, кроме случая битой привязки у тенант-роли).
- `WaybillRegistryService.maxPageSize` — настраивается через `@Value("${epd.registry.max-page-size:1000}")`
  (дефолт прежний). Общее число записей НЕ ограничено: `PageResult.totalElements`/`totalPages`
  всегда настоящие (из `findAll(spec, pageable)`), на любую страницу можно перейти.
- `WaybillRepository`: убраны 2 неиспользуемых unbounded-метода; `findByOrganizationRmaInOrderByCreatedAtDesc(Collection)`
  заменён на `findByOrganizationRmaInAndStatusInOrderByCreatedAtDesc(Collection, Collection<WaybillStatus>)` —
  фильтр ISSUED/ACTIVE теперь в SQL. `GpsController.live()` обновлён на новый метод.
- `application.yml`: добавлены новые ключи `epd.registry.list-cap`, `epd.registry.max-page-size`,
  `epd.reports.max-rows` (последний — для явности; `WaybillPeriodScan` уже и раньше принимал его
  через `@Value` с тем же дефолтом 100000 и уже честно ОТКАЗЫВАЕТ построчным отчётам 422-м при
  превышении лимита периода — просмотр кода показал, что в этой части молчаливого усечения не
  было уже на момент начала задачи; изменение здесь — только явное объявление ключа в `application.yml`
  для обнаружимости).
- Фронт: `packages/shared/lib/api.ts` (реальный модуль, на который резолвится алиас `@/lib/api` —
  см. `apps/web/tsconfig.json`) — `wb.list()` теперь читает заголовок `X-Waybills-Truncated` и
  выставляет необязательное рантайм-свойство `.truncated` на возвращаемом массиве (тип
  `WaybillListResult = Waybill[] & { truncated?: boolean }`), не меняя форму ответа для уже
  существующих вызовов. Кабинет диспетчера (`apps/web/app/dispatcher/page.tsx`, самый вероятный
  кандидат на упор в лимит — вся активная очередь организации) показывает предупреждение
  (ключ i18n `wb.list.truncated`), когда признак выставлен. `apps/web/lib/api.ts` (дублирующий,
  НЕ импортируемый ни одним файлом — проверено: алиас `@/lib/*` в `tsconfig.json` ведёт в
  `packages/shared/lib`, а не сюда) синхронизирован тем же изменением на случай, если файл
  когда-нибудь снова станет актуальным.
- Контракт `/waybills/page` (страница+размер+общее число+totalPages) и `/status-counts` НЕ менялся
  в счастливом пути — фронт (`apps/web/app/waybills/page.tsx`, уже на серверной пагинации) работает
  без изменений; изменился только путь отказа (403 вместо пустого результата при битой привязке).

## Почему
После миграции Ф5 (~2.3 млн архивных ПЛ) жёсткие лимиты без признака усечения и без
возможности настройки были риском: пользователь не мог узнать, что видит не все данные, а
жёстко прибитые к коду константы нельзя было поднять без пересборки. Пустой список при
отсутствии claim организации маскировал реальную ошибку конфигурации доступа (находка
приёмочного тестирования 2026-09-04, §05, уже зафиксированная в комментариях кода) — тот же
класс проблемы нашёлся и здесь, в реестре.

## Кто решил
Владелец — задача поставлена 23.10.2026 («убрать искусственные ограничения выборок в реестре
путевых листов и отчётах»). Решения по неоднозначным местам (трактовка «пустой области тенанта»
как ошибки доступа, а не легитимного «нечего показывать»; сохранение легаси-листинга как
плоского массива с заголовком вместо полной переделки в пагинацию) принял агент Claude —
отмечены ниже, стоит перепроверить владельцу.

**Решения, которые стоит перепроверить:**
- Трактовка `scope.none()` (claim `organization_rma` отсутствует) как 403, а не пустого
  результата — затрагивает ВСЕ тенант-роли без привязки к организации, включая потенциально
  легитимные нестандартные конфигурации, если такие где-то заведены намеренно.
- Легаси-листинг `GET /api/v1/waybills` НЕ переведён на полноценную пагинацию (остался
  массивом + заголовок-признак) — осознанный компромисс: этот эндпоинт используют ~8 простых
  кабинетов «мои задачи» (диспетчер/врач/механик/инспектор/водитель/журналы), переписывать все
  сразу под `/page` не входило в заявленный объём и было бы значительно крупнее по риску.
  Предупреждение об усечении на фронте подключено только в кабинете диспетчера (наиболее
  вероятный кандидат на объём) — остальные кабинеты можно донастроить тем же паттерном позже.

## Как откатить
- Откат кода: `git checkout -- <файл>` по каждому файлу из списка выше (изменения не закоммичены,
  `git diff` покажет полный патч).
- Откат конфигурации: убрать добавленные ключи `epd.registry.*`/`epd.reports.max-rows` из
  `application.yml` — поведение вернётся к прежним хардкодным дефолтам 1000/100000 (значения не
  меняются, меняется только настраиваемость).
- Откат 403-поведения: если выяснится, что пустая область тенанта — легитимный сценарий для
  каких-то ролей, заменить `throw noOrganizationAccess()` обратно на пустой результат в
  `WaybillController.list()` и `WaybillRegistryService.page()`/`statusCounts()` — три точечных места.
