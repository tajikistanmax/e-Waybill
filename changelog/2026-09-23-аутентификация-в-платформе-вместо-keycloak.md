# 2026-09-23 — Аутентификация перенесена в платформу, хранение в PostgreSQL

> **Состояние: собрано и покрыто тестами, НО вживую не проверено.** Docker Desktop на машине
> перестал запускаться до того, как удалось выложить стек. Перед использованием обязательна
> живая проверка по списку в конце записи. **На боевой стенд не выкладывать, пока не проверено.**

## Что изменилось
Вход в платформу больше не зависит от внешнего сервера Keycloak. Учётные записи лежат в
PostgreSQL, токены выпускает и проверяет сама платформа.

- Таблицы (`V76`): `app_user` — учётные записи, `auth_refresh_token` — сессии (хранится только
  отпечаток токена), `auth_signing_key` — ключ подписи.
- Точки входа `/api/v1/auth`: `token`, `refresh`, `logout`, `password`, `jwks`.
- Пароли — BCrypt. Политика прежняя: не короче 12 символов, не совпадает с логином.
- Блокировка на 15 минут после 10 неудачных попыток входа.
- Смена временного пароля — **страница платформы** `/auth/password`, а не чужой сайт.
- Управление пользователями (страница «Доступы») работает с таблицей; её API не изменился.
- Межсервисные вызовы идут под служебной учётной записью с ролью `API_INTEGRATOR`.
- Разовый перенос учётных записей из существующего экспорта realm при первом запуске с пустой
  таблицей. Отдельного файла с паролями не создаётся — читается тот, что уже есть.

## Ключевое решение: состав токена не изменился

Обе службы проверяют JWT и берут роли из `realm_access.roles`, организацию из
`organization_rma`. Платформа выпускает **такой же** токен, поэтому вся проверка прав —
`@PreAuthorize`, мультиарендность, область филиала, кабинеты накладных — осталась нетронутой.
Именно это позволило заменить систему аутентификации, не переписывая права во всём приложении.

## Как было ДО
Отдельный сервер Keycloak: свой контейнер, свой realm, свои пользователи. Три следствия,
из-за которых владелец решил от него отказаться 23.09.2026:

1. учётные записи лежали в базе **внутри контейнера**, без тома: передеплой стирал всех
   заведённых пользователей;
2. страницы входа и смены пароля открывались по адресу Keycloak, а не платформы;
3. вторая база данных рядом с PostgreSQL, который и так есть.

## Почему пароли сохранены при переносе
Переносятся те же логины и пароли, которыми пользовались до перехода. Принудительная смена
для всех разом оборвала бы работу пользователей в момент обновления.

## Кто решил
Владелец 23.09.2026: «Keycloak нам не нужен». Решение принято после того, как был изложен
объём работ и предложен более дешёвый вариант (перенос хранилища Keycloak в PostgreSQL);
владелец подтвердил отказ от Keycloak.

## Что обязательно проверить вживую перед использованием
1. Служба стартует, миграция `V76` применяется, в журнале — «Перенос учётных записей завершён».
2. Вход прежним логином и паролем выдаёт токен; API обеих служб отвечает 200.
3. Создание пользователя → вход временным паролем → страница `/auth/password` → смена →
   вход новым паролем.
4. Межсервизный вызов (закрытие путевого листа переносит одометр в карточку ТС).
5. Выход отзывает сессию: старый токен обновления больше не принимается.
6. Блокировка после серии неудачных попыток.

## Что ещё не сделано
- **Второй фактор** для администратора, инспектора и аналитика: признак перенесён, проверка
  не реализована. До неё эти роли входят по паролю — временное ослабление, отмечено здесь
  намеренно.
- Контейнер Keycloak и классы прежней интеграции пока не удалены: интеграция отключена
  (`epd.keycloak.enabled=false`), классы не вызываются. Удаление — отдельным шагом.
