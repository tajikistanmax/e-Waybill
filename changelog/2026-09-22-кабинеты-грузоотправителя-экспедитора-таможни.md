# 2026-09-22 — Кабинеты внешних пользователей накладных: грузоотправитель, экспедитор, таможенник (MIGRATION.md §1.1, §3.11)

## Что изменилось
- **Keycloak** (`infra/keycloak/epd-realm.json`): роли `CLIENT_SENDER`, `CLIENT_FORWARDER`, `CUSTOMS_OFFICER`; атрибут
  пользователя `clientIds` (id контрагентов `Client` через запятую) в декларативном профиле; маппер claim `client_ids`;
  демо-пользователи `sender`, `forwarder`, `customs` (пароли в `scripts/demo-credentials.ps1`).
- **waybill-service** `/api/v1/consignments` (только эти три роли): список накладных с фильтрами период/поиск/
  «только неподтверждённые», карточка, `PUT` (правка груза/объёма/статкода/документов/адресов/операций/числа рейсов —
  только отправитель/экспедитор своей накладной; стороны и id справочников менять нельзя), `print.pdf` (борхат
  2-Б или СМР), `POST /{id}/customs-confirm` (таможенник, только 5Б-БМ, повтор идемпотентен — как legacy
  «Тасдиқ шудааст»). Область — **не организация**, а клиенты из claim `client_ids` (отправитель: `typeData.senderId`,
  экспедитор: `typeData.forwarderId`) или роль таможни (все СМР с оформленной накладной). Чужие ПЛ — 404.
  `ConsignmentAccess` (правила), `ConsignmentCabinetService`, `WaybillService.updateConsignmentByClient/confirmCustoms`,
  `WaybillPrintService.renderConsignmentPdf`, `CurrentUser.clientIds()/fullName()`.
- **master-data** V70: `role_access` для трёх ролей (раздел `consignments`); `RoleAccessController.KNOWN_NAV` + `consignments`.
- **Web**: кабинет `/consignments` (список, карточка с правкой, PDF, кнопка «Тасдиқ кардан» у таможенника, фильтр
  неподтверждённых); навигация/стартовая страница ролей (`roles.ts`, `roleaccess`, `profile`, `shell`, `sidebar`,
  Настройки → Роли). i18n ru/tj.

## Как было ДО
Legacy: роли `client_sender`/`client_forwarder` (внешние пользователи, привязанные к записям `clients`; видят
борхаты/СМР, где их клиент — отправитель/экспедитор, `RoleTrait::cargoWaybillHasRole`) и `customs_officer`
(список СМР, действие «Тасдиқ кардан» → `customs_officer_id`). В e-Waybill накладные вёл только диспетчер, таможенник
вписывался текстом (Вопрос 2).

## Как стало
Паритет: внешние пользователи работают со своими накладными в отдельном кабинете, таможня подтверждает СМР сама
(имя/логин/момент в `typeData.customsOfficerName/customsOfficerUser/customsConfirmedAt`, печатается в CMR).

## Почему
MIGRATION.md 1.1/3.11 — решение владельца 22.09 «делать все пять» (Вопросы 1/2).

## Кто решил
Владелец (22.09). Привязка «пользователь → клиенты» сделана атрибутом Keycloak (как `organizationRma` у тенантов),
а не таблицей в master-data — единый механизм скоупа по токену. На стенде realm импортируется только при первом
старте Keycloak: роли/маппер/атрибут нужно **добавить в существующий realm** (или пересоздать Keycloak) — см. «Как проверено».

## Как проверено
- `ConsignmentAccessTest` (2), `WaybillServiceCustomsTest` (2), `ConsignmentCabinetControllerSecurityTest` (14:
  3 внешние роли — 200, внутренние — 403; подтверждение только CUSTOMS_OFFICER). Suites: waybill **301**
  (299 ✅ + 2 `initializationError` Testcontainers — окружение), master-data **80/80**, `tsc --noEmit` ✅.
- **Live** на локальном стеке (`scratchpad/live-11.ps1`, после пересоздания Keycloak с новым realm, master-data V70):
  три клиента через `POST /dictionaries/clients`; диспетчер оформил накладные (2-Б: sender+forwarder, 5Б-БМ: sender,
  третья — чужой клиент); атрибут `clientIds` выставлен через admin REST; в токене `client_ids` + роль.
  Диспетчер на `/consignments` → **403**. Sender: список `scope=sender`, 2 свои, чужая не видна и по id → **404**,
  поиск `q=Cotton` → 1, `PUT` меняет груз/объём/операции, подмена `senderId`/`senderName` игнорируется,
  `customs-confirm` → **403**, PDF 2-Б и CMR → 200. Forwarder: только 2-Б (1), 5Б-БМ → **404**, `PUT` → 200.
  Customs: только `WB_TRUCK_INTL` (3), `PUT` → **403**, подтверждение 2-Б → **404**, подтверждение СМР → 200
  (`customsConfirmedAt`, `customsOfficerName`=«Гумрукчӣ Тестовый», `customsOfficerUser=customs`), повтор — та же
  метка, фильтр `unconfirmed=true` после — не содержит; диспетчер видит отметку в ПЛ.
- **Инфра-находка (не legacy):** после переимпорта realm все API отвечали 401 «The iss claim is not valid»:
  realm несёт `frontendUrl=http://10.10.29.70:8180`, а сервисы сверяют `iss` с `KEYCLOAK_EXPECTED_ISSUER`
  (по умолчанию localhost); prod-compose передаёт `KEYCLOAK_ISSUER_URI`, который сервисы не читают. Для локального
  стека добавлен override в `infra/docker-compose.local.yml`. Сервер не трогал — **MIGRATION.md Вопрос 23**.
