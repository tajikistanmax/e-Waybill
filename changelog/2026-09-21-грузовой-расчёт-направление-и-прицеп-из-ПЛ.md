# 2026-09-21 — Грузовой расчёт 2-Б: коэффициенты направления и прицеп берутся из данных самого ПЛ (MIGRATION.md §5.2)

## Что изменилось
Расчёт грузового ПЛ (`WaybillCalcAssembler.buildCargo`, форма 2-Б / 5Б-БМ) перестал зависеть от того, передал ли
вызывающий дополнительное тело запроса (`Supplement`) в `POST /api/v1/waybills/{id}/calculation`:
- **Коэффициенты направления.** Если в `Supplement` не заданы `directionWinterCoefId / directionMountainCoefId /
  directionInCityCoefId`, они берутся из справочника «Направление» master-data (`GET /api/v1/legacy-ref/directions/{id}`)
  по `typeData.directionId` самого ПЛ — как в оригинале `CargoFuelBase::getCoef()` (`$waybill2b->direction->winter_coef_id`
  и т. д.). Направление не найдено → коэффициенты направления не применяются, в лог пишется предупреждение.
- **Прицеп.** Если в `Supplement` не заданы `trailerWeight / trailerCarrying / trailerWeight2`, они берутся из снимка ТС
  ПЛ (`vehicleSnapshot.trailer1Weight / trailer1Carrying / trailer2Weight`) — как в оригинале `parkings.weight_ydak /
  carrying_ydak / weight_ydak_2`.
- `MasterDataClient.findDirection(id)` теперь кэшируется 60 с на контекст вызывающего (`directionsCache`, по образцу
  маршрутов/организаций из фикса OOM/429) — отчёты зовут расчёт по каждому грузовому ПЛ.
- Новый тест `WaybillCalcAssemblerCargoTest` (3 кейса: направление+прицеп из ПЛ; без них — прежнее поведение;
  `Supplement` переопределяет оба источника).

## Как было ДО
`buildCargo` брал коэффициенты направления и данные прицепа **только** из `Supplement`. Штатные вызовы без тела
(карточка ПЛ, печать, отчёты) получали `K = только износ` (зима/горы/город игнорировались) и надбавку за прицеп 0,
хотя направление выбрано в ПЛ, а прицеп заведён в карточке ТС. Норма топлива по грузовым ПЛ занижалась относительно
legacy на весь коэффициент направления и надбавку за прицеп.

## Как стало
Расчёт по грузовому ПЛ без тела совпадает с legacy: `K = winter(по сезону) + mountain + city + used` из направления ПЛ;
`множитель = 1 + 0.01·K`; надбавка за прицеп `weight_ydak · l_dist/100 · m_tkm` (Labador) — из снимка ТС. Явные
значения в `Supplement` по-прежнему имеют приоритет (обратная совместимость).

## Почему
Пункт MIGRATION.md 5.2 «Расчёты — критично 1-в-1»: при спот-чеке веток формулы по типу кузова (Labador / SelfUnload /
Special / SpecialMover ↔ `WaybillCalcEngine.cargo`) формулы совпали дословно, но обнаружилось, что **входы** формулы в
живом пути расходятся с оригиналом: направление и прицеп не доходили до движка.

## Что сверено и намеренно НЕ перенесено (зафиксировано в MIGRATION.md 5.2)
- Формулы по кузову (первая цифра кода марки: 1/2/4 бортовой, 3 самосвал, 5 спецтехника, 8 спецтягач; 5-й символ > 0 →
  прицеп) — 1-в-1, залочены `WaybillCalcEngineTest`.
- Неизвестный код кузова: legacy расчёт не выполняет (пустой результат), e-Waybill считает по бортовой формуле с
  предупреждением в `notes` — осознанно мягче, не баг legacy для переноса (Вопрос 18).
- Транспортная работа P (т·км) и число ездок Z в legacy собираются из строк борхата (накладных) — у нас вводятся при
  возврате вручную; автосбор из накладных — вместе с 3.11 (кабинеты грузоотправителя).
- Посуточная цепочка остатка топлива по дням 2-Б — как B10, удержано (Вопрос 4).

## Кто решил
Агент Claude по промпту Шага 2 (перенос 1-в-1 без вопросов там, где legacy однозначен); владелец — постановка задачи
«перенести всю старую платформу». Спорных вариантов нет: источники данных совпадают с оригиналом дословно.

## Как проверено
- `WaybillCalcAssemblerCargoTest` (3): направление id=7 (зима 5 + горы 10 + город 10 = K 25, ×1.25) и прицеп 4 т из
  снимка ТС → норма 36.45 л, остаток 63.55; без направления/прицепа → K 0, норма 25.0; `Supplement` переопределяет →
  K 10, норма 35.3.
- Полный `:waybill-service:test`: **242 = 240 ✅ + 2 Testcontainers-окружение** (`WaybillLifecycleIntegrationTest`,
  `WaybillConcurrencyIntegrationTest` — известное ограничение Docker Desktop, не регрессия). Web не менялся.
- **Live 1 (локальный стек, направление из ПЛ):** ТС `5555TT01` Volvo (код марки 40000, без прицепа), направление id=3
  (зима id=2 — период 01.11–01.04, в сентябре 0; горы id=4 = 20 %; город id=1 = 5 %), одометр 50000 → 50200, P=1800 т·км,
  Z=2, дизель 150 л. `POST /calculation` без тела → `winter=0 mountain=20 city=5 used=0 K=25 x1.25`, норма
  `0.01·(28·200 + 1.3·1800)·1.25 = 99.25 л`, остаток на въезде 50.75 — **совпало с ожиданием legacy**. До правки те же
  данные давали K=0 (×1.0) и норму 79.4 л.
- **Live 2 (прицеп из снимка ТС):** тестовая марка `TestTrailer` (код 10001, 25 л/100 км, 1.3 л/100 т·км) и ТС
  `5556TT01` с `trailer1Weight=4`, `trailer1Carrying=8`; та же цепочка → `hasTrailer=True`, норма
  `0.01·(25·200 + 1.3·1800)·1.25 + 4·200/100·1.3 = 91.75 + 10.4 = 102.15 л`, остаток 47.85 — **совпало**.
  (В боевом справочнике марок 498 записей и ни одной с флагом прицепа в 5-м символе кода — проверено скриптом; тестовая
  марка оставлена на локальном стенде, на прод не попадает.)
