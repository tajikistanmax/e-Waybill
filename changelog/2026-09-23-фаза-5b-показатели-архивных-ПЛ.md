# 2026-09-23 — Фаза 5b: показатели работы архивных путевых листов (рейсы, выручка, касса, топливо)

## Что изменилось
Новая фаза переноса данных legacy. Она дозагружает в архив путевых листов показатели работы:
рабочие дни (`work_day`) и строки топлива (`fuel_record`). Сами листы не меняются, строки
только добавляются. Заодно исправлен скрипт фазы 5 для будущих загрузок: водитель берётся из
листа, а снимки несут поля, которые нужны расчёту отчёта.

Файлы:
- `scripts/migration/16_staging_phase5b_ddl.sql` — новый: staging `stg_wd5b` (дни), `stg_fr5b` (топливо);
- `scripts/migration/17_phase5b_metrics.sql` — новый: staging → `work_day`, `fuel_record` (только INSERT);
- `scripts/migration/run_phase5b.ps1` — новый оркестратор (ASCII, для PowerShell 5.1);
- `scripts/migration/run_phase5.ps1`, `14_staging_phase5_ddl.sql`, `15_phase5_waybills.sql` —
  фаза 5 для будущих загрузок: водитель по `timesheet_id` и 7 новых полей снимков.

## Как было ДО
Фаза 5 (21.09) переносила только шапку листа: номер, даты, одометр, ТС, водителя, маршрут. В
комментарии скрипта было записано: «work_day/fuel_record НЕ переносятся (legacy хранит как
сериализованный TEXT)». Отчёты за прошлые периоды показывали нули по рейсам, выручке, кассе,
пассажирообороту и топливу. Например, в сводке за июль 2026 выручка была 0, а в legacy 2 512 559,01
(AUDIT, находка 11).

Кроме того, фаза 5 брала водителя листа из привязки «ТС → водитель» (`parking_driver`, последний
водитель ТС), а не из самого листа (`timesheet_id`). В июле 2026 у автобусов 1-АД они совпадали в
668 листах из 10 047. Листы, у последнего водителя ТС которых вместо РМА записана строка `'NULL'`,
в архив не попали вовсе: ~86 тыс. листов окна, в том числе 3 335 листов 1-А «Сорбон» за июль.

**Фаза 5 для будущих загрузок** (на сервере и при локальной перезаливке):
- водитель листа — `timesheet_id` (как во всех отчётах legacy), запасной — водитель ТС; строка `'NULL'`
  в РМА считается пустой. Проверено выгрузкой: 1-АД 119 750 листов (117 204 — по `timesheet_id`),
  1-А 174 881, 3-С 252 194, 2-Б 104 296 против вставленных сейчас 115 359 / 144 557 / 215 248 / 90 207;
- в снимки добавлены вместимость ТС (`brands.capacity`, для такси «по счётчику» — `parkings.capacity`),
  доля дохода, надбавки `cat_1..3`, регион организации и разряд водителя. Пустые значения не пишутся
  (`jsonb_strip_nulls`). Проверено пробным `SELECT` в транзакции с `ROLLBACK`: у «Троллейбус»
  получилось `percentIncome 0.33, cat1 100, cat2 40, regionId 1`, `capacity 92`, `degree 1`;
- повторный прогон `run_phase5.ps1` с окном 21.09.2025: выгрузка прошла, `INSERT 0 0` (уже вставленные листы
  не меняются — `ON CONFLICT DO NOTHING`). Чтобы исправления легли на локальный архив, нужна перезаливка —
  решение владельца (AUDIT §6 п. 1).

## Почему
Завтра, 24.09, заказчик сверяет отчёты за прошлые периоды со старой системой: пассажиропоток,
выручку, заработок водителей и топливо. С нулями сверка невозможна. Массовый UPDATE 2,28 млн
листов владелец не разрешал. Показатели в модели e-Waybill хранятся в отдельных таблицах
(`work_day`, `fuel_record`), поэтому их можно добавить, не трогая сами листы.

## Кто решил
Владелец 23.09.2026: «доведи платформу до запуска к демонстрации». Руководитель поставил задачу
закрыть находку 11 новой фазой 5b: только INSERT, без UPDATE/DELETE над waybill. Поля, которые
живут в самом листе (снимки, водитель), — только через скрипт фазы 5 для будущих загрузок.
Реализовал агент Claude. Перезаливку локального архива не делал: это массовое удаление, решение
за владельцем.

## Как
- MySQL 8 `JSON_TABLE` разбирает JSON-текст прямо в выгрузке. Вложенный `work_days[].fuels` — это
  JSON-строка внутри JSON; она раскрывается вторым `JSON_TABLE` по `JSON_UNQUOTE`.
- Конвейер как в фазе 5: `mysql -N -B` → TSV → `docker cp` → серверный `COPY` в staging →
  `INSERT … SELECT` с привязкой по `waybill.number = 'MG'||src||legacy_id`. Берутся только листы
  `source='MIGRATED'` и `status='ARCHIVED'`.
- Касты через безопасные SQL-функции `pg_temp.try_date/try_time/try_num/try_int` на вложенных
  `CASE`. Мусор legacy (`''`, `'0000-00-00'`, `'begin_path_a'`) превращается в NULL и не роняет загрузку.
- Идемпотентность: лист, у которого уже есть рабочие дни (строки топлива), пропускается целиком,
  плюс `ON CONFLICT (waybill_id, work_date) DO NOTHING`. `created_at` строк топлива = дата листа
  (+мс по порядку строк), поэтому архив не подменяет живые листы в подстановке остатка топлива.
- В данных legacy есть мусорные значения рейсов (4 дня 3-С > 1 000, максимум 61 504 202). Перенесены
  как есть: legacy суммирует их так же.

## Как проверено
- Пилот `-Window 2026-08-01` (13 784 дня, 2 080 строк топлива), затем полный `-Window 2025-09-21`:
  августовские листы пропущены как уже загруженные.
- Сверка SQL-запросами в обеих базах: таблица выше, июль 2026, в целом и по организациям 040000796,
  123456789, 610000109, 630023624.
