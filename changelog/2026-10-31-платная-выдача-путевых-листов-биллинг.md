# 2026-10-31 — Платная выдача путевых листов (тариф + баланс организации)

## Что изменилось
Добавлена платная выдача путевого листа: ставка по типу ПЛ (национальная,
переопределяемая по организации) и баланс организации, который списывается
автоматически при выдаче (Т1).

## Как было ДО
Выдача ПЛ любого типа была бесплатной — платформа не считала и не
начисляла плату за документ.

## Как стало
Модель — **пост-оплата, не блокирующая выдачу** (прямое решение владельца
31.10.2026, через AskUserQuestion):
- Плата **не блокирует** выдачу: даже при недостатке средств документ
  выпускается, баланс организации может уйти в минус (как счёт за связь).
- Баланс — **предоплаченный, внутри платформы** (не внешний
  эквайринг): пополняет только SYSTEM_ADMIN по факту внешнего банковского
  перевода (как сейчас лицензии/контрольные карточки — деньги двигаются вне
  системы, платформа лишь фиксирует факт).
- Тариф **можно переопределить по организации** — тот же принцип
  приоритета, что у движка политик (ORGANIZATION переопределяет NATIONAL),
  но **отдельная таблица**, не Policy: в `PolicyController.assertCanWrite`
  организация (`COMPANY_ADMIN`) сама может писать свои ORGANIZATION-правила
  — для денежной ставки это недопустимо (компания не должна сама себе
  назначать скидку), поэтому тариф пишет **только SYSTEM_ADMIN**.

### Backend (master-data-service)
- Миграция V92: `waybill_fee_tariff` (ставка по типу ПЛ, `organization_id
  IS NULL` = национальная), `organization_balance` (текущий баланс),
  `billing_ledger` (выписка CREDIT/DEBIT; уникальный индекс на `waybill_id`
  среди DEBIT — идемпотентность списания).
- `WaybillFeeTariffService.effectiveFee(type, orgId)`: переопределение
  организации, если задано, иначе национальная ставка, иначе `ZERO`
  (ставка не настроена → выдача этого типа бесплатна — как и прочие правила
  платформы по умолчанию выключены до настройки).
- `OrganizationBalanceService`: `topUp` (CREDIT, SYSTEM_ADMIN) и
  `debitForWaybill` (DEBIT, идемпотентно по `waybillId`, **никогда не
  бросает исключение по недостатку средств** — иначе выдача стала бы
  предоплатой-гейтом, чего владелец явно не хотел). Строка баланса
  блокируется `SELECT … FOR UPDATE` (`OrganizationBalanceRepository.
  findByIdForUpdate`, тот же приём, что `Waybill.findByIdForUpdate`) —
  конкурентные списания/пополнения одной организации сериализуются.
- `WaybillFeeTariffController` — `GET /waybill-fee-tariffs/effective`
  (любой аутентифицированный, нужен waybill-service), остальное
  (`list`/`national`/`organization`/`delete`) — только SYSTEM_ADMIN.
- `OrganizationBalanceController` — `GET .../balance` (своя организация
  или SYSTEM_ADMIN), `POST .../balance/topup` (SYSTEM_ADMIN), `POST
  .../balance/debit` (сервисный токен API_INTEGRATOR — межсервисный вызов
  waybill-service, по аналогии с `PATCH /vehicles/{id}/odometer`).

### Backend (waybill-service)
- `MasterDataClient.effectiveFee`/`debitBalance` — `debitBalance` форсирует
  сервисный токен (как `updateVehicleOdometer`), не токен диспетчера:
  иначе дебет чужого баланса был бы доступен любому пользователю с ролью
  диспетчера через прямой HTTP-запрос.
- `WaybillService.signT1` — после подписания Т1 (черновик становится
  действующим документом) вызывает `chargeIssuanceFee`: берёт эффективную
  ставку и списывает. Обёрнуто в try/catch — сбой биллинга (сеть,
  недоступность master-data) только логируется, документ уже подписан и
  откатывать его из-за биллинга нельзя.

### Frontend
- Настройки → «Тарифы и баланс» (`/settings/billing`, только
  SYSTEM_ADMIN): национальные ставки по 11 типам ПЛ, переопределения по
  организации (поиск по названию/ИНН — тот же паттерн, что A16), просмотр
  баланса любой организации + пополнение с реквизитами платежа + выписка
  (банковская история).
- `packages/shared/lib/api.ts` — `md.feeTariffs/setNationalFee/
  setOrganizationFee/deleteFeeTariff/balance/topUpBalance`.

## Почему
Прямое решение владельца 31.10.2026 (три явных развилки — модель оплаты,
механизм, тарифная сетка — через AskUserQuestion): пост-оплата +
предоплаченный внутренний баланс + тариф с переопределением по
организации.

## Что сознательно НЕ сделано (для владельца)
- Нет внешнего платёжного эквайринга (банковская карта/QR) — пополнение
  баланса только вручную SYSTEM_ADMIN по факту перевода вне платформы, как
  и обсуждалось. Если понадобится самообслуживание организаций (оплата
  картой прямо в кабинете) — отдельное решение и интеграция с банком/
  платёжным провайдером Таджикистана.
- Нет автоматического возврата при аннулировании ПЛ после списания —
  списание происходит один раз при Т1 и не отменяется автоматически при
  последующей аннуляции документа; при необходимости возврата SYSTEM_ADMIN
  делает это вручную через «Пополнить» с пояснением в примечании.
- Межрегиональное переопределение тарифа (по региону, не только по
  организации) не реализовано — явно не запрашивалось; при необходимости
  добавляется тем же способом, что и региональный скоуп аналитика (F10).
