# 2026-09-21 — Карточка ТС: год выпуска 1900…текущий+1 и уникальный номер стоянки в организации (MIGRATION.md §12.3, §12.13)

## Что изменилось
- master-data, новый компонент `VehicleCardRules`:
  - `assertYearManufacture(year)` — пусто допустимо; иначе 1900 … текущий год + 1, иначе **422** «Год выпуска: 1900–YYYY»;
  - `assertParkingNumberUnique(org, number, current)` — номер стоянки (если задан) не должен принадлежать другому ТС
    той же организации, иначе **409** «Номер стоянки N уже занят другим ТС этой организации»; при обновлении
    собственный номер ТС не считается конфликтом.
- `VehicleRepository.findByOrganizationIdAndParkingNumber`.
- Применение: `POST /api/v1/vehicles` (оба правила) и `POST /api/v1/sync/vehicle` (только номер стоянки — год выпуска
  приходит из базы ГАИ, внешние данные не блокируем).
- Тест `VehicleCardRulesTest` (2): границы года (null/1900/текущий+1 — ок; 1899 и текущий+2 — 422 с текстом);
  номер стоянки занят другим ТС → 409, свой номер при обновлении / пустой — ок.

## Как было ДО
Legacy: `kvd/StoreTransportRequest: year_manufacture … integer|digits:4|min:1900|max:(Y+1)`;
`ParkingRequest: number … Rule::unique('parkings')->where(number, company_id)->ignore(id)`. В e-Waybill год выпуска
(`Short`) не ограничивался, номер стоянки проверялся только на формат (4 цифры) — два ТС одной организации могли
получить один номер стоянки.

## Как стало
Оба правила legacy действуют на сервере с понятными кодами/текстами; формат номера стоянки (4 цифры) — как прежде.

## Почему
MIGRATION.md 12.3 и 12.13 — правила валидации legacy, отсутствовавшие в e-Waybill (Шаг 1, §12).

## Кто решил
Агент Claude по промпту Шага 2 (однозначные правила). Год выпуска при sync из ГАИ не валидируем — решение агента
(внешний источник истины), зафиксировано в коде.
