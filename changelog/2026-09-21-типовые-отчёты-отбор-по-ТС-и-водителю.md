# 2026-09-21 — Типовые отчёты: отбор по одному ТС / водителю (legacy `report_details`, MIGRATION.md §6.7)

## Что изменилось
- `GET /api/v1/reports/passenger|cargo` и `…/passenger.xlsx|cargo.xlsx` — два новых необязательных параметра
  `vehicleRegNumber` (госномер, сравнение без регистра и пробелов) и `driverRma`; можно вместе (пересечение).
- `WaybillReportService.Filter` (record, `Filter.of(vehicle, driver)`, пустые → `Filter.NONE`), отбор применяется
  внутри потокового прохода по периоду (`WaybillPeriodScan`) до расчёта ПЛ — лишние листы не считаются.
  Прежние 4-аргументные `passenger/cargo` сохранены (= без отбора).
- Web `/reports/typed`: два поля в панели типового отчёта — «Госномер ТС (отбор)», «РМА водителя (отбор)»;
  участвуют и в запросе, и в выгрузке XLSX. i18n ru/tj.
- Тест `WaybillReportServiceTest` (4): без отбора; по ТС (регистр/пробелы); по водителю и пересечение; пустой отбор.

## Как было ДО
В legacy `admin/report_details?company=&parking_id=&dates=` строил отчёт типа 10 (топливо по ПЛ) по **одному ТС**
(`ReportDetailsCrudController::adt` → `where parking_id`). В e-Waybill типовые отчёты принимали только тип, период и
организацию — детализация по ТС/водителю была невозможна (только группировка по всем).

## Как стало
Любой из 11 типовых разрезов (пассажирский/грузовой) можно сузить до одного ТС и/или одного водителя — это
покрывает legacy `report_details` (тип 10 + ТС) и симметрично даёт то же по водителю.

## Почему
MIGRATION.md 6.7 — гэп паритета отчётов (Шаг 1 инвентаризации). Решение шире legacy (любой тип + водитель) — так
дешевле и естественнее, чем отдельный экран под один тип; legacy-сценарий покрыт полностью.

## Кто решил
Агент Claude по промпту Шага 2 (перенос без вопросов там, где legacy однозначен). Расширение до всех типов и
водителя — решение агента (паритет + минимальная стоимость), владельцу доложено в этой записи.
