# 2026-09-23 — Первый вход нового пользователя, блокировка после неудач и обновление сессии

## Что изменилось
Живая проверка входа, перенесённого в платформу (коммит `77f7fe1`), нашла, что **ни один новый
пользователь не мог войти**, а защита от подбора пароля не работала. Исправлено:
- ключ смены временного пароля и счётчик неудачных попыток теперь сохраняются;
- страница смены пароля `/auth/password` открывается без входа (раньше сразу уводила на `/login`);
- после смены временного пароля вход выполняется сразу, пользователь попадает в свой кабинет;
- ключ смены пароля нельзя предъявить как токен обновления, а токен обновления — как ключ смены;
- смена пароля без ключа и без входа отвечает 401 вместо 500;
- интерфейс обновляет сессию надёжнее: проверка срока каждые 20 с, при возврате на вкладку и по
  ответу 401; одновременные обновления не гасят друг друга; соседняя вкладка не выбивает сессию;
- в шапке появилась ссылка «Сменить пароль» (своего пароля из интерфейса сменить было нельзя).

## Как было ДО
- `AuthService.login` помечен `@Transactional`, а отказ во входе сообщается исключением. Spring
  откатывал транзакцию вместе с записями, сделанными до исключения:
  - **ключ смены временного пароля** (строка в `auth_refresh_token`) не сохранялся. Вход с
    временным паролем отвечал 428 и выдавал ключ, а `/auth/password` отвечал «Ключ смены пароля
    недействителен». Проверено вживую: новый пользователь войти не мог **вообще**;
  - **счётчик неудачных попыток** не рос: 11 неверных паролей подряд, затем верный — вход
    разрешён. Блокировки после 10 неудач не было.
- `shell.tsx` пускал без входа только `/login` и `/verify/*`. Страница `/auth/password` для
  невошедшего пользователя сразу перенаправляла на `/login` — круг «вход → смена → вход».
- Ключ смены пароля лежит в той же таблице, что и токены обновления: `/auth/refresh` принимал
  его и выдавал полноценную сессию, минуя смену временного пароля. Обратное тоже работало: токен
  обновления годился как «ключ смены» — пароль менялся без знания текущего.
- `POST /auth/password` без ключа и без токена падал в 500 (`findById(null)`).
- Интерфейс обновлял токен одним таймером на 29-ю минуту. Браузер придерживает таймеры фоновых
  вкладок и останавливает их во сне ноутбука — после возврата все запросы получали 401.
- Ссылки на смену своего пароля в интерфейсе не было.

## Как стало
- `login` — `@Transactional(noRollbackFor = {ResponseStatusException, PasswordChangeRequired})`:
  отказ по-прежнему сообщается исключением, но записи сохраняются.
- `refresh` отвергает учётку с `must_change_password`; `changePassword` по ключу работает только
  пока пароль временный; без ключа и без входа — 401.
- Несуществующий логин проверяется настоящим BCrypt-хешем (заглушка неверного формата отвечала
  мгновенно и выдавала, что логина нет).
- Веб: `/auth/*` — публичные страницы; после смены временного пароля — автоматический вход
  (логин запоминается в `sessionStorage` на время смены, пароль не хранится); после смены своего
  пароля — выход (сервер гасит все сессии). `AuthProvider`: интервал, `visibilitychange`, `focus`,
  событие `epd-auth-expired` из `api.ts` на 401, защита от параллельного обмена токена, повтор
  с токеном, который уже обменяла соседняя вкладка.

## Почему
Завтра показ заказчику, сценарий «новый перевозчик» (администратор платформы заводит компанию и
её администратора, тот — сотрудников) упирался в невозможность первого входа. Блокировка после
неудач заявлена в требованиях ИБ и описана в журнале `77f7fe1`, но не работала.

## Кто решил
Владелец 23.09: «доведи платформу до запуска к демонстрации», проверить вход, перенесённый с
Keycloak, вживую. Исправления — агент (роли и доступы). Второй фактор (TOTP) для admin/inspector/
analyst сознательно **не** делался этой ночью: включение без отработанного восстановления доступа
рискует оставить администратора без входа на показе (см. «Что осталось»).

## Как
- master-data: `auth/AuthService.java` (+ `AuthServiceTest`, 8 тестов: контракт транзакции,
  блокировка, сохранение ключа, ключ ≠ токен обновления, токен обновления ≠ ключ, 401 без ключа).
- web: `packages/shared/lib/auth.tsx`, `packages/shared/lib/api.ts` (событие 401),
  `apps/web/app/shell.tsx` (`/auth/*` публичные), `apps/web/app/auth/password/page.tsx`,
  `apps/web/app/topbar.tsx` (ссылка), `packages/shared/lib/i18n.tsx` (`pwd.*`).

## Как проверено
- `gradle :master-data-service:test` — 146 тестов, провалов по этим изменениям нет (2 провала —
  чужой незавершённый `AuthBootstrapServiceAccountTest`, не относится); `tsc --noEmit` — чисто.
- Живьём, API (`localhost:8081`), временная учётка: вход временным паролем → 428 + ключ; ключ
  как токен обновления → 401; смена по ключу → 204; повтор ключа → 401; смена без ключа → 401;
  вход новым паролем → 200 (`expires_in=1800`, `refresh_expires_in=43200`); токен обновления
  как ключ смены → 401; обновление → 200; повтор старого токена → 401; выход → 204; обновление
  после выхода → 401; смена своего пароля с неверным текущим → 422, с верным → 204; 10 неверных
  паролей → 11-я попытка с верным паролем → 429. Учётка удалена.
- Живьём, браузер (Playwright, `apps/web/e2e/roles-cabinets.spec.ts`): администратор компании и
  7 выданных им логинов входят временным паролем, попадают на `/auth/password`, меняют пароль и
  оказываются в своём кабинете; плановое обновление токена в браузере (часы вкладки переведены
  на 29,5 мин) — запрос `/auth/refresh` 200, старый токен обновления после этого отвергается,
  после «Выход» сохранённый токен обновления → 401.
