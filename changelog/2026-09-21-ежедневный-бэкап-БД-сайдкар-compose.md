# 2026-09-21 — Ежедневное резервное копирование БД: сайдкар `backup` в docker-compose (MIGRATION.md §11.8)

## Что изменилось
- Новый сервис `backup` в `infra/docker-compose.prod.yml` (образ `epd/backup:0.1.0` из `infra/backup/Dockerfile` =
  `postgres:16-alpine` + `openssl` + `tzdata`): каждый день в `BACKUP_TIME` (по умолчанию 00:00, `TZ` по умолчанию
  `Asia/Dushanbe`) делает `pg_dump -Fc` баз `masterdata` и `waybill` в том `backups` (`/backups/<db>-<штамп>.dump[.enc]`),
  затем удаляет копии старше `BACKUP_RETENTION_DAYS` (по умолчанию 30). При заданном `BACKUP_ENCRYPTION_KEY`
  (тот же ключ из `infra/.env`, что у `scripts/backup-postgres.ps1`) дамп шифруется `openssl enc -aes-256-cbc -pbkdf2`;
  без ключа — открытый дамп с предупреждением в логе. `BACKUP_RUN_NOW=1` — копия сразу при старте (проверка).
- Скрипт цикла — `infra/backup/backup-loop.sh` (POSIX sh, busybox), там же команда восстановления.

## Как было ДО
Legacy `app/Console/Kernel.php`: `db:backup` ежедневно в 00:00 (планировщик Laravel) и раз в неделю
`find storage/backups -type f -mtime +10 -delete`. В e-Waybill был только ручной `scripts/backup-postgres.ps1`
(Windows, шифрование AES+HMAC) и `/settings/backup`; расписания на стенде не было (осознанно — см. комментарий в скрипте).

## Как стало
Расписание и ротация живут в самом compose-стеке (переносимо на любой узел, не зависит от Task Scheduler/cron хоста).
Срок хранения 30 суток (строже legacy 10, по ИБ-13.8.5), ротация ежедневно. Это по-прежнему суточный снапшот
(RPO ≤ 24 ч), не WAL-архивация, и копии лежат на том же узле (3-2-1 не реализовано) — как честно оговорено в PS-скрипте.

## Почему
MIGRATION.md 11.8 — единственная строка §11 «инфраструктурного» характера; без расписания резервных копий у стенда нет.

## Кто решил
Агент Claude по промпту Шага 2. Вариант «сайдкар в compose» вместо cron хоста — чтобы не менять систему сервера втихую
и чтобы расписание уезжало вместе со стеком. Ключ шифрования переиспользован (не заводится второй секрет).
**На боевом стенде** сервис поднимется при следующем `docker compose up -d --build` — владельцу решить, задать ли
`BACKUP_ENCRYPTION_KEY` в `infra/.env` (рекомендуется; без него дампы открытые).

## Как проверено
- Локально: `docker compose … build backup` ✅; `BACKUP_RUN_NOW=1 … up -d --force-recreate backup` → лог:
  `encrypted=yes`, `[OK] /backups/masterdata-20260921-212141.dump.enc (27 431 152 bytes, aes-256-cbc)`,
  `[OK] /backups/waybill-20260921-212141.dump.enc (223 433 648 bytes, aes-256-cbc)`, `OK=2 FAIL=0 (retention 30d)`,
  `next backup in 9475s (at 00:00 +05)` — расписание по TZ Asia/Dushanbe работает.
- Путь восстановления: внутри контейнера `openssl enc -d … | pg_restore -l` → валидный архив (`dbname: masterdata`,
  `TOC Entries: 241`, 98 секций `TABLE DATA`).
