# 2026-09-22 — Реестры ТС/водителей/сотрудников листаются на сервере

## Что изменилось
- master-data получил три постраничных эндпоинта: `GET /api/v1/{vehicles|drivers|employees}/page`
  с параметрами `page`, `size`, `q`, `organizationRma`, `regionId`, `cityName`, а также
  `transportType` (ТС) и `type` (должность сотрудника). Ответ — `{content, total, page, size,
  totalPages}`; у водителей дополнительно `assignedVehicles` (`id ТС → госномер`) для строк
  текущей страницы.
- Общая часть отбора вынесена в `service/RegistryQuery`: область организаций считается как
  пересечение мультиарендности, выбранной организации и географии; размер страницы ограничен
  потолком 200; поиск идёт по текстовым полям сущности **или** по названию организации.
- Веб-реестр (`/registry/vehicles|drivers|employees`) больше не фильтрует в браузере: строка
  поиска уходит на сервер с задержкой 300 мс, фильтры «регион / город / компания / вид / должность»
  — параметрами запроса, страницы переключаются запросами. Выгрузка CSV добирает выборку
  страницами по 200 строк с потолком 5000 и сообщает, если выборка обрезана.

## Как было ДО
Страница реестра вызывала `GET /api/v1/vehicles` (или `/drivers`, `/employees`) **без фильтров**
и фильтровала весь массив в браузере. На боевых данных стенда это:

| Запрос | Объём | Время |
|---|---|---|
| `GET /api/v1/vehicles` (89 287 ТС) | 87 МБ | 42 с |
| `GET /api/v1/drivers` (68 006 водителей) | 56 МБ | 27 с |

Реестр водителей дополнительно грузил **весь** справочник ТС (те же 87 МБ) ради одной колонки
«Номер транспорта», то есть открытие страницы стоило ~143 МБ и больше минуты ожидания.

## Как стало
Та же страница реестра ТС: **19,7 КБ за 242 мс** (в 4400 раз меньше трафика). Водители —
16,7 КБ за 120 мс, справочник ТС не запрашивается вовсе.

## Почему
Находка сквозной приёмки перед продакшеном (`AUDIT.md`, блок B18): страница администратора
платформы практически не открывалась на боевом объёме данных, а браузер вставал на отрисовке.

## Кто решил
Владелец 22.09 поручил сквозную проверку «каждой страницы» и исправление всего, что работает
неидеально. Решение — серверная пагинация вместо увеличения лимитов браузера: отбор по
89 тысячам строк это работа БД, а не JavaScript.

## Как
Три репозитория получили `JpaSpecificationExecutor`, спецификация собирается в `RegistryQuery`.
Географический отбор резолвится в список id организаций отдельным запросом (`OrganizationRepository`).
Неограниченные списки `GET /api/v1/vehicles` и др. **сохранены** — на них опираются интеграции
(`API_INTEGRATOR`) и внутренние вызовы waybill-service с фильтрами; изменение их семантики
молча урезало бы выгрузку интегратору.

## Инцидент при выкладке
Первый вариант географического запроса `(:city is null or lower(o.cityName) = lower(:city))`
падал на PostgreSQL с `function lower(bytea) does not exist`: null-строка уходит в драйвер без
типа и получает тип `bytea`. Заменено на явные ветки (`findIdsByRegion` / `findIdsByCityName` /
`findIdsByRegionAndCityName`). Урок: «или null» в SQL для строковых параметров не использовать.
