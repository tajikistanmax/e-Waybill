# 2026-09-24 — Второй фактор входа (код из телефона) для администратора, инспектора и аналитика

## Что изменилось
Вход в платформу для учётных записей с обязательным вторым фактором стал двухшаговым: пароль,
затем 6-значный код из приложения-аутентификатора на телефоне (TOTP, RFC 6238). При первом
входе пользователь подключает приложение по QR-коду прямо на странице входа. В «Доступах»
видно, подключён ли второй фактор у сотрудника, и есть кнопки «Требовать 2FA» / «Сбросить 2FA».
Закрыта находка 27 AUDIT.md.

Файлы:
- `apps/backend/master-data-service/.../auth/Totp.java` (новый) — коды RFC 6238 без сторонних библиотек;
- `.../auth/AuthService.java` — второй шаг входа `verifySecondFactor`, назначение одноразовых ключей;
- `.../auth/AuthController.java` — `POST /api/v1/auth/second-factor`, ответ 428 `second_factor_setup` / `second_factor_required`;
- `.../auth/UserDirectory.java`, `.../web/OrgUserController.java` — `POST /org-users/{id}/reset-second-factor`, `PATCH /org-users/{id}/second-factor`;
- `.../domain/AppUser.java`, `.../domain/AuthRefreshToken.java`, `.../config/SecurityConfig.java`;
- `db/migration/V81__second_factor.sql` — назначение ключа (`purpose`), неподтверждённый секрет, шаг последнего кода, дата подключения;
- `packages/shared/lib/auth.tsx`, `api.ts`, `i18n.tsx`; `apps/web/app/login/page.tsx`, `apps/web/app/company/access/page.tsx`;
- тесты: `TotpTest` (эталонные значения RFC 6238), `AuthServiceTest` (+9), `apps/web/e2e/second-factor.spec.ts` (новый);
- автопроверки переведены на учётки `*-automation`: `apps/web/e2e/roles-cabinets.spec.ts`, `form-fields.spec.ts`,
  `scripts/e2e-all-forms.ps1`, `scripts/e2e-reports.ps1`, `scripts/seed-demo-showcase.ps1`.

## Как было ДО
У `admin`, `inspector`, `analyst` в базе стоял признак «второй фактор обязателен» (перенесён из
Keycloak 23.09), но его никто не проверял: после отказа от Keycloak эти роли — полный доступ
к платформе, надзор и аналитика по всей республике — входили одним паролем. Сбросить или
включить второй фактор было негде.

Кроме того, в таблице одноразовых ключей лежали вперемешку токены обновления сессии и ключи
смены временного пароля; различались они только косвенно (по признаку «пароль временный»).

## Как стало
- Пароль верен, второй фактор обязателен, но не подключён → страница входа показывает QR-код,
  ключ для ручного ввода и поле кода. Первый верный код подключает второй фактор и впускает.
- Второй фактор подключён → после пароля спрашивается только код.
- Сессия (токен обновления) выдаётся **только** после верного кода. Ключ второго шага живёт
  15 минут, одноразовый и не принимается как токен обновления.
- Один и тот же код дважды не принимается; допускается расхождение часов телефона ±30 секунд.
- Неверный код — неудачная попытка входа; 10 подряд блокируют учётную запись на 15 минут
  (как подбор пароля). Верный пароль счётчик у таких учёток не обнуляет — только верный код.
- Временный пароль сначала меняется, потом подключается второй фактор.
- «Доступы» (администратор компании, филиала, платформы): колонка «2FA» — подключена /
  обязательна, не подключена / нет; кнопки «Требовать 2FA», «Не требовать 2FA», «Сбросить 2FA»
  (сброс гасит все сессии сотрудника; при следующем входе он подключит приложение заново).
- Каждая точка входа принимает только ключи своего назначения: обновление сессии —
  `REFRESH`, смена временного пароля — `PASSWORD_CHANGE`, второй шаг — `SECOND_FACTOR`.

## Почему
ТЗ ИБ-13.2.2: для привилегированных ролей второй фактор обязателен. Без него перехват одного
пароля администратора даёт полный доступ к государственной системе. Это был один из
блокеров выхода в прод из вердикта готовности 24.09.

## Кто решил
Владелец 24.09.2026: «начинай, приготовь платформу к пилоту и продакшену». Состав и порядок
работ предложил разработчик (Claude), второй фактор взят первым как главный пробел безопасности.

Спорные решения разработчика:
- **Своя реализация TOTP, а не библиотека.** Алгоритм — 30 строк, проверен на эталонных
  значениях RFC 6238. Меньше внешних зависимостей в контуре входа.
- **Секрет хранится в базе открытым**, как было в Keycloak. Шифровать его ключом из
  переменной окружения — отдельная доработка (ещё один секрет стенда); при утечке базы
  второй фактор всё равно требует ещё и пароль (в базе только BCrypt-хеш).
- **Администратор компании может сбросить 2FA своему сотруднику** — у него уже есть право
  сбросить пароль; права те же, что у сброса пароля.
- **Автопроверки входят дублями `admin-automation`, `inspector-automation`,
  `analyst-automation`** (та же роль, без второго фактора). На промышленном стенде эти
  учётки нужно отключить — внесено в инструкцию выкладки.

## Как
- `Totp`: HMAC-SHA1, 6 цифр, шаг 30 с, окно ±1 шаг, сравнение за постоянное время, Base32.
- `AuthService.login`: после пароля и временного пароля — `SecondFactorRequired` (428) с
  ключом второго шага; при первой настройке — секрет и `otpauth://`-ссылка. Повторная попытка
  отдаёт тот же неподтверждённый секрет (уже отсканированный код не «протухает»).
- `AuthService.verifySecondFactor`: ключ назначения `SECOND_FACTOR`, проверка блокировки,
  кода, запись шага последнего кода, подтверждение подключения, аудит `TOTP_ENROLL` и `LOGIN`.
- `refresh` и смена временного пароля принимают только ключи своего назначения.
- Фронт: `auth.tsx` — `SecondFactorRequired`, `verifySecondFactor`, незавершённый вход в
  `sessionStorage` (после смены временного пароля страница входа сразу показывает шаг кода);
  QR рисуется в браузере библиотекой `qrcode` из сборки — секрет никуда не уходит.

## Восстановление доступа
- Сотрудник потерял телефон → администратор компании / платформы: «Доступы» → «Сбросить 2FA».
- Администратор платформы (`admin`, без организации в «Доступах») потерял телефон → другой
  администратор платформы через API `POST /api/v1/org-users/{id}/reset-second-factor`, либо на
  сервере в БД:
  `update app_user set totp_secret=null, totp_pending_secret=null, totp_last_step=null, totp_enrolled_at=null where username='admin';`
  При следующем входе (с паролем) он подключит приложение заново.
- Часы сервера должны идти точно (NTP): при расхождении больше 30 с коды не принимаются.

## Важно для показа и стенда
После выкладки `admin`, `inspector`, `analyst` при первом входе попросят подключить
приложение-аутентификатор — нужен телефон с Google Authenticator / Microsoft Authenticator /
FreeOTP. Если показывать без телефона — входить `admin-automation` / `inspector-automation` /
`analyst-automation` (та же роль).
