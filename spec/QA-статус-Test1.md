## ВЕРДИКТ (критерии запуска, §28)

Основной сквозной сценарий (§1) **проходит полностью** — проверено сквозным smoke-тестом
и вручную (организация→водитель→ТС→создание→медосмотр→техосмотр→маршрут→оплата→подпись→
номер+QR→Выдан→Активен→рейс→GPS→возврат→завершение→архив→аудит).

**P0-блокеры (§2) закрыты, КРОМЕ одного:** квалифицированная ЭЦП — сейчас SHA-256-заглушка
(юридически значимая подпись требует боевого УЦ РТ). Это единственный оставшийся P0, и он
**внешне заблокирован**. Остальные P0 закрыты и проверены (см. ниже).

**НЕ готово к боевому запуску по §28** из-за: нет нагрузочного тестирования, резервного
копирования/восстановления, боевого мониторинга, плана отката, UAT, инструкции пользователя,
реальных интеграций (налоговая/реестры/SMS/ЭЦП). Функционально этап 1 готов; остаётся
прод-инфраструктура и внешние интеграции.

**Обновление 03.09.2026** — целевой аудит перед возможным запуском (3 параллельных агента):
функциональность (10/10 типов ПЛ, полный жизненный цикл + 10/10 негативных сценариев — без

#### 03.09.2026 — целевой аудит безопасности перед возможным запуском (3 параллельных агента + ручная проверка)

Полный прогон `security-matrix.ps1` (23/23) и `smoke-test.ps1` (35/35) подтверждён, плюс целевой поиск новых дыр сверх регресс-щита. Найдено и **закрыто в тот же день**:

1. **IDOR: водитель мог читать чужой рейс той же организации по прямому GET.**
   `WaybillController.get()/titles()/statusHistory()/fuelCalculation()/qr()/payment()` проверяли
   только принадлежность организации (`checkTenant`), но не то, что вызывающий водитель —
   реальный участник рейса (в отличие от списка `GET /waybills`, который такой фильтр уже
   применял — сам код был внутренне противоречив). Живой репро подтверждён и закрыт:
   `checkTenant()` в `WaybillService.java` теперь дополнительно сверяет РМА водителя
   (основного/второго) при роли DRIVER, зеркалируя то, что `MobileController.ownWaybill()`
   уже делал для мобильного канала. Проверено живьём дважды: чужой рейс → 404, свой рейс → 200
   (регрессии нет).
2. **Swagger/OpenAPI были публично доступны без токена на этом «прод»-стенде.**
   `DOCS_OPEN` не был явно выставлен в `infra/docker-compose.prod.yml` → действовал
   небезопасный дефолт `true` из `application.yml` обоих сервисов. Добавлен явный
   `DOCS_OPEN: ${DOCS_OPEN:-false}` в оба блока compose-файла. При этом для
   **master-data-service** обнаружена более глубокая причина: `docs-open`/`required-audience`
   были по ошибке вложены в YAML под `epd.keycloak.*`, а код читает `epd.security.*` —
   свойство тихо не резолвилось НИКАКИМ значением `DOCS_OPEN`, всегда молча падая на
   дефолт `true` из `@Value`. Перенесено в правильный блок `epd.security.*`
   (заодно чинит и `required-audience`, который был так же не подключён). Проверено
   живьём на обоих сервисах: `GET /v3/api-docs` и `/swagger-ui/index.html` → 401.
3. **`PAYMENT_WEBHOOK_SECRET`: fail-fast проверка не ловила реальный дефолт этого compose-файла.**
   Проверка в `PaymentWebhookController` сравнивала секрет только с дефолтом из
   `application.yml` (`dev_webhook_secret`), а `docker-compose.prod.yml` подставляет
   **другой** дефолт (`epd_webhook_dev_secret`) — тоже опубликованный открытым текстом,
   но не распознаваемый проверкой. Расширен список запрещённых значений на оба варианта.
   Проверено живьём: пересборка с этим дефолтом теперь ПАДАЕТ на старте с понятной
   ошибкой (было — тихо стартовало и принимало вебхуки с публично известным секретом).
4. **`AGGREGATOR_OPEN` по умолчанию (в коде) был `true` (fail-open).**
   В этом самом compose-файле уже стоял безопасный override (`false`), поэтому живой
   стенд не был уязвим, но любой другой способ развёртывания (голый `java -jar`,
   другой compose/K8s-манифест без этой переменной) тихо открывал API агрегатора без
   аутентификации. Дефолт в `application.yml` перевёрнут на `false` (fail-closed) —
   для локального запуска без Keycloak нужно явно выставить `AGGREGATOR_OPEN=true`.

**Дополнительно — минорные находки, оставлены на решение продукта (не исправлялись без
явного запроса, тот же принцип, что и по остальным решениям в сессии):**
- `SubjectDocumentController.delete()` не имеет собственного `@PreAuthorize` и наследует
  более широкий классовый набор ролей (включая DISPATCHER), тогда как `approve()`/`reject()`
  сужены до SYSTEM_ADMIN/COMPANY_ADMIN — возможно, DISPATCHER не должен уметь удалять
  документы, только загружать. Межарендной утечки нет.
- `SyncController.GET /permit/{number}` (просмотр дозвола E-PERMIT по номеру) не имеет
  `@PreAuthorize` — любая аутентифицированная роль может посмотреть любой номер дозвола.
  Вероятно нормально (национальный реестр, как номер техпаспорта), но стоит явно
  подтвердить, что это не считается орг-чувствительными данными.

**Полный чек-лист готовности к боевому запуску (инфраструктура/секреты)** — не исправлялось
(требует реальных значений/доступов, не код-ревью):
- Все секреты в `infra/docker-compose.prod.yml`/`infra/keycloak/epd-realm.json` — дефолтные,
  опубликованы открытым текстом в репозитории: `DB_PASSWORD`, `KC_ADMIN_PASSWORD`,
  `MINIO_PASSWORD` (совпадает с `DB_PASSWORD` — переиспользование пароля между сервисами),
  `PAYMENT_WEBHOOK_SECRET`, секреты клиентов `epd-aggregator`/`epd-provisioner`
  (у `epd-provisioner` — права Keycloak Admin API `manage-users`, самый чувствительный
  секрет в файле). Все требуют ротации + переноса в секрет-хранилище (Vault/Docker
  secrets) перед боевым запуском.
- Keycloak в режиме `start-dev --import-realm`, не `start` — уже отмечено `TODO(prod)`
  в самом файле: нужны внешняя БД, HTTPS-терминация на reverse-proxy, управляемая
  миграция вместо импорта файла реалма.
- `KC_HOSTNAME_STRICT=false`, `attributes.frontendUrl=http://localhost:8180`,
  `redirectUris`/`webOrigins` содержат dev-адреса (`localhost`, LAN IP) — всё завязано
  на единый внешний HTTPS-домен, которого пока нет.
- TLS нигде в стеке не терминируется — весь трафик (включая Keycloak) сейчас plain HTTP.
- Порты сервисов (8180/8081/8082/3000) опубликованы напрямую на хост вместо reverse-proxy.
- `epd-web` (публичный клиент) имеет `directAccessGrantsEnabled: true` (Resource Owner
  Password grant) — удобно для скриптов/тестов этой сессии, но не рекомендуется для
  публичного клиента в проде (нет MFA-хука, приучает пользователей вводить пароль
  напрямую в клиент).
- Тестовые логины (`username == password`, без принудительной смены) — весь блок `users`
  в `epd-realm.json` не должен попасть в боевой реалм.
- `minio/minio:latest` — единственный незафиксированный тег образа в compose-файле.

Ничего из этого блока не тронуто — это внешние/организационные решения (реальные пароли,
домен, сертификаты, УЦ), а не то, что можно закрыть чтением кода.
