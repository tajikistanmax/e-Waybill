## 1. Общие сведения

Назначение — юридически значимый электронный путевой лист (роҳхат) всех типов, включая международный, с предрейсовым/послерейсовым медосмотром и техконтролем, QR-проверкой на дороге, тарификацией и передачей в госконтур. Мастер-данные (организации, водители, ТС, лицензии) — из **единой платформы Минтранса** (наш же проект), а не дублируются.

**Охват (1-я очередь):** веб-кабинеты по ролям, оформление и жизненный цикл ПЛ, титулы Т1–Т6, QR/проверка, тарификация/оплата, справочники, отчёты, API агрегаторов такси (ЧУРА/НЕРУ). **2-я очередь:** мобильные приложения (Flutter), GPS-контроль, реальные госинтеграции, квалифицированная ЭЦП, э-ТТН/e-CMR. **3-я очередь:** тахографы, топливные карты, ТОиР, страхование, штрафы, электронные билеты, английский язык.

Решения заказчика (учтены): миграция данных из rohkhat.tj **не требуется** (с чистого листа); мобильные приложения — **в самом конце**, после продакшн-пилота; проверка QR инспектором — через веб-страницу `/verify` (QR кодирует URL).

## 5. Титульная модель Т1–Т6

Реализовано: ✅ Т1 выпуск (диспетчер) → Т2 предрейсовый медосмотр (врач) → Т3 техконтроль (механик) → Т4 одометр на выезде → Т5 одометр на возврате → Т6 послерейсовый медосмотр. Строгая последовательность; «Не годен»/«Неисправно» блокируют выпуск; QR доступен после готовности.

Уточнения из ТЗ (◑ проверить/дозаполнить):
- **Т3 — структурированный чек-лист из 10 пунктов** (тормоза, руль, свет, шины, двигатель, трансмиссия, электрика, стеклоочистители, зеркала, звук), +2 при прицепе (сцепка, тормоза прицепа), + сигнализация/заземление при опасном грузе. У нас чек-лист есть — сверить состав на 10 обязательных булевых пунктов.
- **Т2/Т6 — приборные показатели:** давление, пульс, температура, алкоголь, **признак наркотиков**, вердикт. ✅ реализовано (АД/пульс/темп/алкотест); ◑ добавить поле «наркотест».
- **Одометр:** Т5 ≥ Т4 ✅; ➕ **проверка разумности пробега** (город ≤500 / пригород ≤1000 / межгород ≤5000 км → предупреждение) и ➕ **непрерывность одометра между ПЛ** (стартовый пробег ≥ последнего завершённого) — из docx, у нас нет.
- **Автопризнак послерейсового осмотра** при международном сообщении / сроке > 1 суток / опасном грузе / перевозке детей / пассажиров — ◑ формализовать правило.

## 9. QR-код и проверка на дороге

Реализовано: ✅ QR как **JWS ES256** (подписанная полезная нагрузка), офлайн-проверка публичной страницей `/verify/{jws}` без авторизации (модель Индии/ISO 18013-5), JWKS для ключей. Инспектор сканирует камерой телефона → открывается проверка подписи.

Замечания ТЗ: РФ-черновики требуют **динамический QR (обновление каждые 60 с)** как антискриншот-меру. **Решение:** остаёмся на статичном JWS — он объективно лучше для офлайн-проверки без сети; при необходимости добавить TTL/срок в полезную нагрузку. ◑ Проверить, что `/verify` отдаёт **обезличенные данные** (без ПД) и просроченный QR → ошибка.

## 10. Электронная подпись — ГЛАВНЫЙ ПРОБЕЛ

Реализовано: ◑ титулы фиксируют `signed_hash` (хэш ключевых полей ПЛ на момент подписи) + метаданные (подписант, роль, время) — это уровень «подтверждение аккаунтом». В коде — **sha256-заглушка** вместо криптографической подписи.

○ **Требуется (двухуровневая модель, из docx + RF-детали):**
1. Уровень 1 (есть): `signature_type` = PIN/SMS/OTP/подтверждение аккаунтом, `signed_hash`, `signature_meta` (device/ip/method).
2. Уровень 2 (нужно): **квалифицированная ЭЦП** через национальный УЦ РТ (Закон РТ «Об электронном документе и ЭЦП» № 1965): проверка сертификата (срок/отзыв/принадлежность), **метка времени TSP**, контейнер **PKCS#7/CAdES**, ключи в **HSM**. По ТЗ РФ: медик Т2/Т6 — **только квалифицированная**, диспетчер/механик — допускается неквалифицированная.
Модель «подтверждение сейчас → гос-ЭЦП позже» позволяет добавить крипту без переписывания. Зависит от готовности УЦ РТ. **Приоритет №1 из несделанного.**

## 16. Миграция e-Роҳхат (справочно)

Нужна отдельная **административная подсистема «Настройки»** с ядром — **движком бизнес-правил/политик (§7)** и **конструктором полей/типов** (§3–4).
