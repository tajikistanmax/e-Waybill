# 14. Требования к интерфейсу пользователя

Настоящий раздел устанавливает требования к пользовательским интерфейсам Платформы: веб-кабинетам, мобильным приложениям и печатным формам. Требования согласованы с ролевой моделью (раздел 7), статусной моделью ЭПЛ (`spec/data/waybill-statuses.yaml`), типами путевых листов (`spec/data/waybill-types.yaml`) и нефункциональными требованиями (раздел 9), в том числе с ограничениями каналов связи (раздел 9.4).

## 14.1. Общие принципы

| № | Требование |
|---|---|
| ИП-14.1.1 | Все интерфейсы проектируются mobile-first: макет сначала разрабатывается для экрана смартфона (ширина от 360 px), затем адаптируется для планшета и настольного экрана. Основной канал доступа пользователей — мобильные устройства на каналах 2G/3G (раздел 9.4). |
| ИП-14.1.2 | Интерфейс рассчитан на пользователей с невысокой цифровой грамотностью: один экран — одна задача; линейные пошаговые сценарии; формулировки без технического жаргона; подтверждение необратимых действий простым языком с описанием последствий. |
| ИП-14.1.3 | Минимум ручного ввода: реквизиты автозаполняются из государственных реестров по идентификаторам — РМА (организация, водитель, сотрудник) и госномеру ТС (модель ЭТТН Узбекистана, раздел 3.4). Пользователь вводит идентификатор и подтверждает подставленные данные; повторный ввод сведений, уже известных Платформе, запрещён. |
| ИП-14.1.4 | Крупные элементы управления: минимальный размер области касания — 48×48 px, расстояние между соседними целями — не менее 8 px; базовый размер шрифта — не менее 16 px; ключевое действие экрана — одна крупная кнопка в зоне досягаемости большого пальца. |
| ИП-14.1.5 | Статусы документов кодируются цветом, пиктограммой и текстовой меткой одновременно (НФ-9.7.2) по единой палитре: серый — DRAFT/ARCHIVED; жёлтый — CREATED, AWAITING_MED, AWAITING_TECH, AWAITING_PAYMENT; синий — READY, ISSUED, PAID; зелёный — MED_PASSED, TECH_PASSED, ACTIVE, IN_TRIP, COMPLETED; красный — MED_REJECTED, TECH_REJECTED, BLOCKED; тёмно-серый — CANCELLED; бордовый — EXPIRED, RETURNED — голубой. Палитра фиксируется в дизайн-системе и едина во всех кабинетах, приложениях и печатных формах. |
| ИП-14.1.6 | Единая дизайн-система Платформы: библиотека компонентов (кнопки, поля, таблицы, бейджи статусов, таймлайн титулов, карточки), государственный бренд Минтранса РТ (герб, логотип, фирменные цвета, требования к госсимволике), типографика с полной поддержкой таджикского алфавита; все компоненты — в трёх локалях tg/ru/en (раздел 9.5). |
| ИП-14.1.7 | Все экраны разрабатываются с учётом трёх локалей: длина строк tg/ru/en различается — запрещены макеты, ломающиеся при удлинении текста на 40%. |
| ИП-14.1.8 | Единообразие сквозных элементов: карточка ПЛ, таймлайн титулов Т1–Т6, бейдж статуса и QR-блок выглядят и работают одинаково во всех кабинетах и приложениях. |

## 14.2. Структура интерфейсов по кабинетам

| № | Требование |
|---|---|
| ИП-14.2.1 | Состав кабинетов и доступных экранов определяется активной ролью и скоупом пользователя (раздел 7.1); экраны и действия, недоступные роли, не отображаются (при этом контроль доступа выполняется на сервере, РП-7.1.4). |

### 14.2.1. Кабинет компании (администратор перевозчика)

| Экран | Ключевые элементы |
|---|---|
| Главная (дашборд компании) | Сводка: ПЛ за сегодня по статусам, задолженность, истекающие документы (техосмотры, лицензии, медсправки водителей) с предупреждающими бейджами |
| Реестр сотрудников | Таблица с фильтрами (роль, статус), приглашение сотрудника по РМА, назначение ролей, деактивация |
| Реестры ТС и водителей | Таблицы-реестры с фильтрами и поиском; карточки с данными из единой платформы (только просмотр, ИП-14.1.3); индикаторы истечения техосмотра/медсправки |
| Шаблоны ПЛ | Список шаблонов компании по типам ПЛ с предзаполненными полями |
| Договоры с аутсорсерами | Список договоров с медпунктами/СТО, статусы, период действия |
| Финансы | Счета, история оплат, задолженность, скачивание актов |
| Отчёты | Отчёты организации с фильтрами и выгрузкой XLSX/CSV |

### 14.2.2. АРМ диспетчера

| Экран | Ключевые элементы |
|---|---|
| Реестр ПЛ | Таблица-реестр с фильтрами: статус, тип ПЛ, дата, ТС, водитель, маршрут; цветные бейджи статусов; быстрые действия из строки; счётчики по статусам над таблицей |
| Создание ПЛ (мастер) | Пошаговая форма: тип ПЛ → ТС (по госномеру/номеру стоянки) → водитель (по табельному/РМА) → маршрут/срок → проверка → подписание Т1; динамические поля по типу ПЛ (п. 14.3.3); предупреждения о блокирующих проверках (активный ПЛ на ТС/водителя, истёкший техосмотр) до подписания |
| Карточка ПЛ | Шапка (номер, тип, статус, QR), **таймлайн титулов Т1–Т6** с подписантами, временем и состоянием каждого титула; блоки данных по титулам; панель действий по текущему статусу (направить на осмотр, зафиксировать Т4/Т5, продлить, аннулировать); история изменений |
| Выпуск на линию | Очередь ПЛ в статусе ISSUED: фиксация Т4 (одометр — автоподстановка, топливо), массовый режим для утреннего пика |
| Возврат | Очередь ACTIVE: фиксация Т5 (одометр возврата, круги, выручка, время работы), направление на послерейсовый осмотр |

### 14.2.3. АРМ медицинского работника

| Экран | Ключевые элементы |
|---|---|
| Лента заявок на осмотр | Список заявок с бейджами: «ожидает», «срочный» (выезд ближе часа), «послерейсовый»; фото и данные водителя; сортировка по времени выезда; звуковое/визуальное оповещение о новых заявках |
| Форма осмотра | Крупные поля: АД (маска NNN/NNN), пульс, температура, результат алкотеста, общее состояние; решение «Допущен / Не допущен» двумя крупными кнопками; при недопуске — обязательная причина из справочника + комментарий; подписание Т2/Т6 (ЭП + муҳр) |
| Журнал медосмотров | Электронный журнал собственных записей с фильтрами по дате/водителю, выгрузка; чужие записи недоступны (РП-7.1.8) |

### 14.2.4. АРМ механика

| Экран | Ключевые элементы |
|---|---|
| Лента заявок на техконтроль | Список ТС с бейджами ожидания, данные ТС, предыдущий пробег |
| Форма техконтроля | Чек-лист исправности; одометр (автоподстановка из предыдущего ПЛ), топливо; решение «Исправен / Неисправен»; при отклонении — акт с обязательной фотофиксацией неисправности (камера, до N фото, клиентское сжатие НФ-9.4.7); подписание Т3 (ЭП + муҳр) |
| Журнал техконтроля | Реестр своих осмотров и актов с фильтрами |

### 14.2.5. Кабинет бухгалтера

| Экран | Ключевые элементы |
|---|---|
| Счета | Реестр счетов с фильтрами (период, статус оплаты), подтверждение оплаты (переход AWAITING_PAYMENT → PAID при ручном сценарии) |
| Задолженность | Сводка задолженности, блокирующие лимиты, уведомления |
| Финансовые отчёты | Отчёты по услугам и абонементам, выгрузка XLSX |

### 14.2.6. Мобильное приложение водителя

| Экран | Ключевые элементы |
|---|---|
| Главный экран | Активный ПЛ: номер, статус цветом, маршрут, срок; крупная кнопка «Показать QR»; индикатор актуальности медосмотра на текущий день (многодневные ПЛ) |
| Подтверждение получения | Карточка нового ПЛ → подтверждение Face ID/PIN (простая ЭП, переход READY → ISSUED); подтверждение приёма/сдачи ТС |
| Экран QR | QR-код на весь экран с автоповышением яркости (п. 14.4); работает офлайн |
| Завершение рейса | Отправка завершения, фото/комментарии; работает офлайн с очередью отправки |
| История | Список своих ПЛ со статусами; уведомления (готовность ПЛ, недопуск с причиной, блокировка) |

Кабинет ИП (SELF_EMPLOYED) строится на базе приложения водителя и дополняется: упрощённой заявкой на ПЛ на себя (упрощённый Т1), выбором аккредитованного медпункта/СТО на карте и по расстоянию, оплатой (Корти милли, кошельки) и автоактивацией после Т2+Т3.

### 14.2.7. Мобильное приложение инспектора

| Экран | Ключевые элементы |
|---|---|
| Сканер QR | Полноэкранная камера с рамкой наведения; офлайн-криптопроверка подписи без входа (НФ-9.4.5); онлайн-режим — актуальный статус |

| Фиксация проверки | Автозаполнение геопозиции и времени; фиксация нарушения (справочник видов) с фото; блокировка документа с подтверждением |
| Журнал проверок | Собственные проверки за смену/период, статус синхронизации офлайн-записей |

## 14.3. Формы ввода

### 14.3.1. Маски ввода

Маски унаследованы от действующих бумажных форм и legacy-платформы rohkhat.tj и обязательны к применению во всех формах Платформы.

| Поле | Маска/формат | Примечание |
|---|---|---|
| Номер ПЛ | 7 цифр | Присваивается Платформой, ручной ввод — только в поиске |
| Номер стоянки ТС (рақами таваққуфгоҳ) | 4 цифры | Автоподстановка ТС по номеру: 1-я цифра — колонна, 3–4-я — бригада |
| Табельный номер водителя/сотрудника | 4 цифры | Автоподстановка карточки по номеру |
| РМА | 9–10 цифр, только цифры | Ключ автозаполнения из реестров |
| Госномер ТС | Форматы регистрационных знаков РТ | Автозаполнение карточки ТС |
| Время | HH:mm, 24 часа | Выезд, возврат, время клиента |
| Дата | dd.mm.yyyy | Календарь + ручной ввод |
| Одометр | до 6 цифр | Для автобуса — поле заблокировано, значение из предыдущего ПЛ |
| Номер маршрута | до 3 цифр | Автодополнение из справочника маршрутов |
| График (реҷа) | до 2 цифр | |
| Код клиента (мизоҷ) | 6 цифр | Автодополнение по справочнику клиентов |
| Топливо (литры) | до 3 цифр | До 2 видов топлива (1 — для 2-Б/5Б-БМ) |
| Круги (гардиш) | до 2 цифр | |
| Выручка (маблағ) | до 5 цифр: 3 сомони + 2 дирама | Формат NNN,NN TJS |
| АД (медосмотр) | NNN/NNN | Форма осмотра |

| № | Требование |
|---|---|
| ИП-14.3.1 | Маски применяются на клиенте (запрет ввода недопустимых символов, автоформатирование) и дублируются серверной валидацией; числовые поля вызывают цифровую клавиатуру на мобильных устройствах. |
| ИП-14.3.2 | Поля с автоподстановкой (одометр из предыдущего ПЛ, остаток топлива remain_fuel_before_exit, данные по РМА/госномеру) отображаются заполненными и заблокированными с пометкой источника («из предыдущего ПЛ», «из реестра»); редактирование запрещено, если запрещено бизнес-правилом. |

### 14.3.2. Автодополнения

| № | Требование |
|---|---|
| ИП-14.3.3 | Автодополнение обязательно для полей: марка ТС (brand), город (city, external_city), маршрут (номер, описание, тип ТС), клиент, направление (самт), страна визы, страны/города погрузки и разгрузки, транзитные страны, наименование груза (cargo). |
| ИП-14.3.4 | Правила автодополнения (по образцу legacy): подсказки с первого введённого символа, поиск по началу строки, не более 10 позиций в списке, выбор только из справочника (свободный ввод недопустим для ссылочных полей); на слабых каналах — кэш последних использованных значений. |
| ИП-14.3.5 | Часто используемые значения пользователя (последние маршруты, клиенты, ТС) показываются первыми до начала ввода. |

### 14.3.3. Динамические поля по типам ПЛ

| № | Требование |
|---|---|
| ИП-14.3.6 | Состав и активность полей формы определяются типом ПЛ (`waybill-types.yaml`): для 3-С поле «вид услуги» (type_service) управляет формой — при «хатсайр/маршрут» активны маршрут и график, а территория деятельности (regions_id) пассивна; при «такси» и «почасовой» — наоборот. |
| ИП-14.3.7 | Ограничения по типам отражаются в форме: рабочие дни (work_days) — до 4 (1-А), до 7 (3-С), до 15 (2-Б); лимиты одометра за период (650 — 1-А, 2800 — 3-С); прицепы — до 2 (2-Б); два водителя и блок визы/маршрута/груза/ББА — 5Б-БМ; список пассажиров — 4М-БМ; класс опасности ADR и свидетельства — WB_DANGEROUS; моточасы — WB_SPECIAL; троллейбус — без блока топлива и клиента. |
| ИП-14.3.8 | Поля, обязательность которых зависит от условий (лицензия — только для type_company_id=1; route_id — только при type_service=2), помечаются как обязательные динамически, с пояснением условия. |

### 14.3.4. Валидация и черновики

| № | Требование |
|---|---|
| ИП-14.3.9 | Валидация выполняется «на лету»: по завершении ввода поля (on blur) и перед отправкой; сообщения об ошибках выводятся под соответствующим полем, поле подсвечивается; список ошибок дублируется сводкой вверху формы со ссылками-переходами к полям. |
| ИП-14.3.10 | Серверные ошибки валидации (модель HTTP 422 с ошибками по полям — по образцу legacy) отображаются в том же виде, что и клиентские: под полями, на языке интерфейса пользователя. Конфликты (409 — «медосмотр не пройден», «уже подтверждено», активный ПЛ существует) отображаются как блокирующие уведомления с объяснением и доступным следующим действием. |
| ИП-14.3.11 | Черновики сохраняются автоматически (локально и на сервере — статус DRAFT) не реже чем каждые 30 секунд и при каждом переходе между шагами мастера; при обрыве связи или закрытии формы введённые данные не теряются; при возврате пользователю предлагается продолжить черновик. |
| ИП-14.3.12 | Блокирующие проверки против реестров (активный ПЛ на ТС/водителя, истёкший техосмотр, отсутствие лицензии) выполняются до подписания Т1 и отображаются в шаге проверки мастера с указанием причины и способа устранения. |

## 14.4. Мобильные приложения

| № | Требование |
|---|---|
| ИП-14.4.1 | Индикатор офлайн-режима: постоянный ненавязчивый баннер «Нет связи — данные от ЧЧ:мм»; операции, поставленные в очередь отправки, помечаются значком ожидания синхронизации; после восстановления связи — автоматическая отправка и уведомление о результате (НФ-9.4.4). |
| ИП-14.4.2 | Экран QR: код занимает не менее 80% ширины экрана, яркость экрана автоматически повышается до максимума при открытии; под кодом — номер ПЛ, статус цветом и срок действия; экран доступен в один жест с главного экрана и работает офлайн. |
| ИП-14.4.3 | Биометрия: Face ID / отпечаток / PIN устройства — для входа и обязательно перед каждым юридически значимым подтверждением (получение ПЛ, приём/сдача ТС) (РП-7.5.17). |
| ИП-14.4.4 | Push-уведомления: готовность ПЛ, недопуск (с причиной), блокировка, истечение срока; при недоставке push — SMS-резерв (НФ-9.4.6); уведомления открывают соответствующий экран (deep link). |
| ИП-14.4.5 | Тёмная тема: обязательна для приложений водителя и инспектора (работа ночью и в кабине); переключение — системное и ручное; контраст в обеих темах соответствует НФ-9.7.1. |
| ИП-14.4.6 | Приложение инспектора: режим непрерывного сканирования (серия проверок без возврата в меню), работа одной рукой, крупный цветовой вердикт, различимый при солнечном свете. |
| ИП-14.4.7 | Приложения должны сохранять работоспособность на устройствах Android 8+ с 2 ГБ ОЗУ (НФ-9.6.2); размер установочного пакета — не более 40 МБ. |

## 14.5. Печатные формы

| № | Требование |

| ИП-14.5.1 | Каждый ЭПЛ имеет печатную форму PDF (архивный экземпляр — PDF/A, НФ-9.6.5) с QR-кодом, идентичным QR мобильного предъявления; QR читается при печати A4 и A5 на монохромном принтере (НФ-9.6.3). |
| ИП-14.5.2 | Печатные формы соответствуют утверждённым бланкам форм: Т(1-АД) — автобус/троллейбус, 1-А — микроавтобус, 3-С — легковой/такси, 2-Б — грузовой, 5Б-БМ — международный грузовой, 4М-БМ — международный пассажирский; расположение реквизитов согласуется с Минтрансом РТ до ввода в эксплуатацию. |
| ИП-14.5.3 | Печатная форма содержит государственные статистические коды и обязательные реквизиты (номер, срок действия, сведения о собственнике, ТС с показаниями одометра, водитель, вид сообщения и вид перевозки), отметки титулов Т1–Т6 с ФИО подписантов и метками времени, а также надпись о юридической значимости электронного оригинала. |
| ИП-14.5.4 | Языки печатных форм — по НФ-9.5.3: национальные формы тадж./рус., международные (5Б-БМ, 4М-БМ) — двуязычное представление тадж./англ. или рус./англ. |
| ИП-14.5.5 | Генерация PDF — не более 5 с (НФ-9.1.6); скачивание доступно из карточки ПЛ ролям согласно матрице 7.3. |

## 14.6. Навигация, уведомления, ошибки, обучение

### 14.6.1. Навигация

| № | Требование |
|---|---|
| ИП-14.6.1 | Мобильные интерфейсы — нижняя панель навигации не более чем с 5 пунктами; веб-кабинеты — боковое меню с группировкой по функциям и строкой глобального поиска (номер ПЛ, госномер, РМА, ФИО). |
| ИП-14.6.2 | Пользователь с несколькими ролями/организациями переключает активный контекст явным переключателем в шапке; активный контекст всегда виден (РП-7.1.3). |
| ИП-14.6.3 | Хлебные крошки в веб-кабинетах для вложенных экранов; возврат из карточки сохраняет позицию и фильтры реестра. |

### 14.6.2. Уведомления в интерфейсе

| № | Требование |
|---|---|
| ИП-14.6.4 | Центр уведомлений в каждом кабинете: события по документам (смена статуса, отказ Т2/Т3, блокировка), истечение сроков (техосмотр, медсправка, лицензия), финансовые события; непрочитанные — счётчиком на значке. |
| ИП-14.6.5 | Ленты заявок (медработник, механик) обновляются без действий пользователя (push/поллинг с учётом канала); новые заявки выделяются и сопровождаются настраиваемым звуковым сигналом. |
| ИП-14.6.6 | Критические уведомления (блокировка документа, недопуск) отображаются немедленно модально и дублируются по каналам push/SMS (НФ-9.4.6). |

### 14.6.3. Обработка ошибок и пустые состояния

| № | Требование |
|---|---|
| ИП-14.6.7 | Сообщения об ошибках формулируются на языке пользователя (tg/ru/en) и содержат: что произошло, почему, что делать дальше; технические коды скрываются за ссылкой «подробнее» и включаются в обращение в поддержку (8808) автоматически. |
| ИП-14.6.8 | При ошибке сети введённые данные сохраняются; пользователю предлагается повторить отправку; повторная отправка не создаёт дублей (идемпотентность, НФ-9.2.9). |
| ИП-14.6.9 | Пустые состояния экранов содержат пояснение и следующее действие («Путевых листов пока нет — создайте первый», кнопка создания), а не пустую таблицу; для фильтров без результатов — кнопка сброса фильтров. |
| ИП-14.6.10 | Долгие операции (формирование отчёта, PDF) сопровождаются индикатором прогресса и выполняются в фоне с уведомлением о готовности (НФ-9.1.8); блокирующие «крутилки» дольше 3 секунд не допускаются. |

### 14.6.4. Обучающие подсказки

| № | Требование |
|---|---|
| ИП-14.6.11 | При первом входе в каждый кабинет — короткое обучение (3–5 экранов) по ключевому сценарию роли (диспетчер — выпуск ПЛ; врач — осмотр; водитель — QR; инспектор — сканирование); обучение можно пропустить и вызвать повторно из меню помощи. |
