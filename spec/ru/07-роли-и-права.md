# 7. Роли пользователей и права доступа

Настоящий раздел определяет ролевую модель платформы «Электронные перевозочные документы Республики Таджикистан» (далее — Платформа), состав ролей, права доступа к операциям, порядок подписания титулов электронного путевого листа (далее — ЭПЛ) и жизненный цикл учётных записей. Источником истины по составу ролей и прав является машиночитаемый реестр `spec/data/roles-matrix.yaml`; при расхождении текст раздела приводится в соответствие с реестром.

## 7.1. Модель доступа

### 7.1.1. Общие положения

Платформа реализует комбинированную модель управления доступом: ролевую (RBAC) с атрибутными ограничениями (ABAC).

| № | Требование |
|---|---|
| РП-7.1.1 | Доступ к операциям Платформы должен предоставляться исключительно через роли (RBAC). Прямое назначение отдельных прав пользователю в обход роли не допускается. |
| РП-7.1.2 | Каждая роль должна дополняться атрибутными ограничениями (ABAC) по следующим атрибутам: организация (РМА), пункт обслуживания (медпункт/техпункт), регион (справочник регионов 1–7), тип перевозки, признак «свои документы». |
| РП-7.1.3 | Один пользователь (физическое лицо, идентифицируемое по РМА) может иметь несколько ролей, в том числе в разных организациях. При входе и при каждой операции должен фиксироваться активный контекст «роль + организация/пункт». |
| РП-7.1.4 | Проверка прав должна выполняться на стороне сервера при каждом обращении к API. Скрытие элементов интерфейса не является механизмом контроля доступа. |
| РП-7.1.5 | Все решения о предоставлении/отказе в доступе к защищаемым операциям должны журналироваться в append-only журнале аудита (субъект, роль, контекст, операция, объект, результат, метка времени). |
| РП-7.1.6 | Роли и права должны быть вынесены в конфигурацию (реестр ролей) и изменяться администратором системы без модификации программного кода, с версионированием и аудитом изменений. |

### 7.1.2. Скоупы (зоны видимости данных)

| Скоуп | Содержание | Роли |
|---|---|---|
| «Свои документы» | Только документы, в которых пользователь является субъектом (водитель, ИП) | DRIVER, SELF_EMPLOYED |
| «Своя организация» | Объекты организации, к которой привязана учётная запись (по РМА организации) | COMPANY_ADMIN, DISPATCHER, DOCTOR, MECHANIC, ACCOUNTANT |
| «Свой пункт» | Заявки и записи своего аккредитованного медпункта/техпункта, включая заявки сторонних клиентов (ИП, компании-заказчики по договору) | MED_ORG_ADMIN, TECH_ORG_ADMIN, DOCTOR (аутсорс), MECHANIC (аутсорс) |
| «Предъявленные документы» | Только документ, предъявленный по QR-коду, + собственный журнал проверок | INSPECTOR |
| «Объекты своих клиентов» | Объекты компаний-клиентов в пределах выданного scoped-токена | API_INTEGRATOR |
| «Вся страна (агрегаты)» | Агрегированные показатели по стране; детальные данные — по обоснованному запросу с аудитом | MINTRANS_ANALYST |
| «Вся система» | Полный административный доступ с полным аудитом действий | SYSTEM_ADMIN |
| «По обращению» | Ограниченная карточка документа/пользователя, найденная по номеру ПЛ/РМА в рамках зарегистрированного обращения | CALL_OPERATOR |

| № | Требование |
|---|---|
| РП-7.1.7 | Скоуп «своя организация» должен вычисляться по привязке учётной записи к организации (РМА организации) и не может быть расширен пользователем самостоятельно. |
| РП-7.1.8 | Медицинский работник должен видеть медицинские данные только собственных записей осмотров; доступ к чужим медицинским данным запрещён (минимизация данных о здоровье). |
| РП-7.1.9 | Инспектору при проверке должен показываться минимально необходимый состав данных: статус документа, водитель, ТС, маршрут, актуальность медосмотра на текущий день. Иные персональные данные не раскрываются (принцип минимизации ПДн). |
| РП-7.1.10 | Доступ аналитика Минтранса к детальным (неагрегированным) данным должен предоставляться только по обоснованному запросу с фиксацией цели и обязательным аудитом каждого обращения. |

## 7.2. Перечень ролей

Платформа поддерживает 16 ролей. Роли CONSIGNOR и CONSIGNEE вводятся на этапе 2 (э-ТТН).

### 7.2.1. Администратор перевозчика (COMPANY_ADMIN)

| Параметр | Содержание |
|---|---|
| Наименование | Администратор перевозчика (компания/ЮЛ) / Маъмури корхонаи боркашон |
| Зона ответственности | Своя организация: учётные данные, персонал, договоры, финансы |
| Ключевые операции | Регистрация организации и ведение данных компании (с проверкой через государственные реестры); управление сотрудниками и назначение ролей внутри компании; просмотр своих ТС и водителей (мастер-данные из единой платформы Минтранса); ведение шаблонов путевых листов компании; договоры с аутсорс-медпунктами и СТО; оплата, счета, история операций, отчёты организации, скачивание ПЛ |
| Подписывает | Титулы ЭПЛ не подписывает; подписывает заявку на регистрацию организации и договоры (ЭП) |
| Ограничения | Не участвует в операционном цикле ЭПЛ (создание/подписание титулов); не видит медицинские данные осмотров |

### 7.2.2. Диспетчер (DISPATCHER)

| Параметр | Содержание |
|---|---|
| Наименование | Диспетчер / Танзимгар |
| Зона ответственности | Операционный выпуск ТС на линию в своей организации |
| Ключевые операции | Создание ПЛ (выбор ТС, водителя, типа ПЛ, маршрута, срока); направление на медосмотр и техосмотр; фиксация выезда и возврата; продление многодневного ПЛ в пределах лимита срока; закрытие рейса; отмена/аннулирование ПЛ (до выдачи — самостоятельно, после выдачи — с подтверждением) |
| Подписывает | Т1 (выпуск: рейс, ТС, водитель, маршрут, срок), Т4 (одометр/топливо на выезде), Т5 (одометр на возврате, результаты) |
| Ограничения | Не может править показания одометра автобуса (значение подставляется автоматически из предыдущего ПЛ данного ТС); не может подписывать Т2 и Т3 |

### 7.2.3. Медицинский работник (DOCTOR)

| Параметр | Содержание |
|---|---|
| Наименование | Медицинский работник / Духтур |
| Зона ответственности | Допуск водителей: своя организация либо свой аккредитованный медпункт (аутсорс) |

| Подписывает | Т2 (предрейсовый медосмотр), Т6 (послерейсовый медосмотр) — ЭП с электронной печатью (муҳр) |
| Ограничения | Не видит чужие медицинские данные, кроме собственных записей осмотров; не имеет доступа к финансовым и диспетчерским операциям |

### 7.2.4. Механик — контролёр технического состояния (MECHANIC)

| Параметр | Содержание |
|---|---|
| Наименование | Механик (контролёр техсостояния) / Механик |

## 7.3. Матрица «роль × операция»

Условные обозначения: **С** — создание/изменение; **Ч** — чтение; **П** — подпись (ЭП); **У** — утверждение/подтверждение; **–** — операция недоступна. Составное значение (например, «С/П») означает совокупность прав. Все права действуют в пределах скоупа роли (п. 7.1.2).

### 7.3.1. Роли перевозчика и партнёров

| Операция | COMPANY_ADMIN | DISPATCHER | DOCTOR | MECHANIC | DRIVER | ACCOUNTANT | SELF_EMPLOYED | API_INTEGRATOR |
|---|---|---|---|---|---|---|---|---|
| Регистрация организации, данные компании | С/П | – | – | – | – | – | С¹ | – |
| Управление сотрудниками и ролями компании | С | – | – | – | – | – | – | – |

## 7.4. Подписание титулов

Титульная модель ЭПЛ (Т1–Т6) принята по образцу ГИС ЭПД (раздел 3.1). Виды электронной подписи применяются в соответствии с Законом РТ № 1965 от 15.03.2023 «Об электронном документе и электронной подписи».

| Титул | Содержание | Подписант (роль) | Вид подписи | Обязательность |
|---|---|---|---|---|
| Т1 | Выпуск ПЛ: рейс, ТС, водитель, маршрут, срок действия | Диспетчер (DISPATCHER); для ИП — упрощённый Т1 (SELF_EMPLOYED) | Квалифицированная/защищённая ЭП сотрудника | Обязателен для всех типов ПЛ |
| Т2 | Предрейсовый медицинский осмотр (АД, пульс, температура, алкотест, состояние; допуск/недопуск) | Медицинский работник (DOCTOR) | ЭП + электронная печать (муҳр) медработника | Обязателен для всех типов ПЛ; для многодневных пассажирских — ежедневно |
| Т3 | Предрейсовый контроль технического состояния, разрешение выпуска | Механик (MECHANIC) | ЭП + электронная печать (муҳр) | Обязателен для всех типов ПЛ |
| Т4 | Показания одометра и топлива на выезде | Диспетчер (DISPATCHER) | ЭП сотрудника | Обязателен; для автобусов одометр подставляется автоматически и диспетчером не редактируется |
| Т5 | Показания одометра на возврате, результаты дня/рейса | Диспетчер (DISPATCHER) | ЭП сотрудника | Обязателен при закрытии |
| Т6 | Послерейсовый медицинский осмотр | Медицинский работник (DOCTOR) | ЭП + электронная печать (муҳр) | Обязателен для пассажирских перевозок и перевозок опасных грузов (WB_BUS, WB_TROLLEYBUS, WB_MINIBUS, WB_PAX_INTL, WB_DANGEROUS) |
| Подтверждение водителя | Получение ПЛ, приём/сдача ТС | Водитель (DRIVER) / ИП (SELF_EMPLOYED) | Простая ЭП: Face ID / PIN в мобильном приложении | Обязательно для перехода READY → ISSUED; **титулом не является** |

| № | Требование |
|---|---|
| РП-7.4.1 | Подписанные титулы неизменяемы. Исправления оформляются только корректирующими титулами со ссылкой на исправляемый титул (инвариант статусной модели, раздел `waybill-statuses.yaml`). |
| РП-7.4.2 | Каждая роль подписывает только собственные титулы; подписание чужого титула должно блокироваться на уровне сервера независимо от интерфейса. |
| РП-7.4.3 | Водитель не подписывает титулы ЭПЛ; юридически значимое участие водителя ограничено подтверждением получения ПЛ и приёма/сдачи ТС простой ЭП (Face ID/PIN) с фиксацией времени и устройства. |
| РП-7.4.4 | Повторное подтверждение одного титула одним сотрудником должно отклоняться с конфликтом (совместимость с legacy-семантикой: HTTP 409 «This employee has already confirmed this waybill»). |
| РП-7.4.5 | Для сменного ПЛ (shift_mode, 2 водителя) блоки Т2/Т6 оформляются на каждого водителя отдельно. |
| РП-7.4.6 | Каждая подпись титула должна содержать метку доверенного времени, идентификатор подписанта (РМА), роль, контекст организации/пункта и заноситься в append-only журнал аудита. |

## 7.5. Регистрация и жизненный цикл учётных записей

### 7.5.1. Статусная модель учётной записи

`Заявка → На модерации → Активна → (Заблокирована ⇄ Активна) → Архив`

| № | Требование |
|---|---|
| РП-7.5.1 | Учётные записи всех типов должны иметь единый жизненный цикл со статусами «Заявка», «На модерации», «Активна», «Заблокирована», «Архив»; переходы журналируются с указанием инициатора и основания. |
| РП-7.5.2 | Идентификатором физического лица является РМА (9–10 цифр), организации — РМА организации, ТС — государственный регистрационный номер. Дублирование учётных записей по одному РМА в одном контексте не допускается (upsert-семантика). |

### 7.5.2. Регистрация организации (перевозчик, аутсорсер)

| № | Требование |
|---|---|
| РП-7.5.3 | Регистрация организации выполняется будущим администратором перевозчика: ввод РМА организации, автозаполнение реквизитов из реестра налогового органа, подтверждение данных, загрузка недостающих документов (лицензия и контрольная карточка — обязательны только для перевозчиков общего пользования, type_company_id=1). |
| РП-7.5.4 | Заявка на регистрацию организации проходит модерацию администратором системы (ГУП ЦЦТО) с проверками против государственных реестров (налоговый орган, лицензионный реестр Госслужбы, реестр ТС ГАИ). Срок модерации — не более 3 рабочих дней; отказ — с указанием причины из справочника. |
| РП-7.5.5 | Регистрация медорганизаций и СТО-аутсорсеров завершается процедурой аккредитации (проверка права на меддеятельность/техконтроль); без аккредитации приём заявок на Т2/Т3 недоступен. |
| РП-7.5.6 | Регистрация API-интегратора включает: заявку, аккредитацию администратором системы, выдачу scoped-токена с перечнем компаний-клиентов, тестовый контур. Компания-клиент подтверждает делегирование интегратору в своём кабинете. |
