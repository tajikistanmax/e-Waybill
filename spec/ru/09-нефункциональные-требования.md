# 9. Нефункциональные требования

Настоящий раздел устанавливает требования к производительности, надёжности, масштабируемости, работе в условиях слабых каналов связи, многоязычности, совместимости, доступности и эксплуатации Платформы. Требования обязательны для всех компонентов: веб-кабинеты, мобильные приложения, серверный контур, API, печатные формы.

## 9.1. Производительность

### 9.1.1. Расчётная нагрузка

Расчёт выполнен для горизонта полной обязательности электронных путевых листов (цель отрасли — 100% перевозочных документов в электронном виде к 2030 году; парк — 666 074 ТС по данным ГАИ МВД на 01.03.2024).

| Параметр | Значение | Основание |
|---|---|---|
| Выдача ЭПЛ, документов/сутки | 100 000 – 170 000 | Оценка активного коммерческого парка на горизонте обязательности |
| Операций записи на один ЭПЛ | ~8 (Т1–Т6, подтверждение водителя, оплата) + статусные переходы | Титульная модель, раздел 7.4 |
| Среднесуточный поток записи | 1,0–1,4 млн операций/сутки ≈ 12–16 оп/с | Расчёт |
| Утренний пик (06:00–09:00) | 3–5 × среднесуточной интенсивности: массовый выпуск на линию, медосмотры, техконтроль | Профиль выпуска ТС на линию |
| Расчётная пиковая нагрузка | **100 rps запись / 500 rps чтение** | Пик записи ~50–80 оп/с, округлено вверх; чтение (ленты заявок, реестры, статусы, интеграции) ≥ 5 × записи |
| Проектный запас | × 5: **500 rps запись / 2 500 rps чтение** | Требование к нагрузочному тестированию |
| QR-проверки | до 100 000 проверок/сутки; пиковые окна совпадают с рейдами дорожного контроля | Оценка Госслужбы |

| № | Требование |
|---|---|
| НФ-9.1.1 | Платформа должна обрабатывать не менее 100 rps операций записи и 500 rps операций чтения в устойчивом режиме без деградации показателей отклика (п. НФ-9.1.4). |
| НФ-9.1.2 | Платформа должна проходить нагрузочное тестирование с пятикратным запасом: 500 rps запись / 2 500 rps чтение в течение не менее 1 часа без ошибок и деградации. |
| НФ-9.1.3 | Контур проверки QR должен обрабатывать до 100 000 онлайн-проверок в сутки; офлайн-проверка выполняется на устройстве инспектора и нагрузки на серверный контур не создаёт. |
| НФ-9.1.4 | Время отклика API: p95 < 500 мс, p99 < 1 000 мс (измеряется на стороне сервера, без учёта канала связи). |
| НФ-9.1.5 | Выдача ЭПЛ end-to-end (от подписания последнего необходимого титула до статуса READY с присвоенным номером и QR-кодом, включая уведомления) — не более 10 секунд. |
| НФ-9.1.6 | Генерация печатной формы PDF — не более 5 секунд на документ. |
| НФ-9.1.7 | Онлайн-проверка QR инспектором: ответ сервера p95 ≤ 1 с; полный цикл на устройстве в сети 3G — не более 5 с. |
| НФ-9.1.8 | Массовые и отчётные выгрузки (реестры, статистика) должны выполняться асинхронно (очередь заданий) и не влиять на показатели интерактивных операций. |
| НФ-9.1.9 | Утренний пик 06:00–09:00 является расчётным режимом, а не исключением: автоматическое масштабирование должно опережать пик по расписанию (pre-scaling), а не только реагировать на нагрузку. |

## 9.2. Доступность и надёжность

| № | Требование |
|---|---|
| НФ-9.2.1 | Доступность Платформы — не менее 99,9% в месяц (допустимая недоступность ≤ 43 мин/мес), исключая согласованные окна обслуживания. |
| НФ-9.2.2 | Плановые окна обслуживания назначаются в период минимальной активности (ночные часы, ориентир 23:00–05:00 — по образцу технологического окна legacy-системы) и публикуются не менее чем за 3 календарных дня. |
| НФ-9.2.3 | Целевое время восстановления после аварии RTO ≤ 1 час; целевая точка восстановления RPO ≤ 5 минут (потеря данных не более чем за 5 минут). |
| НФ-9.2.4 | Должен быть развёрнут зеркальный резервный контур (по образцу E-Way Bill 2.0, раздел 3.2): при недоступности основного контура выдача и проверка документов продолжается на резервном; синхронизация двунаправленная, автоматическая. |
| НФ-9.2.5 | Резервное копирование: непрерывная репликация СУБД + инкрементальные копии не реже 1 раза в час + полная копия ежесуточно; копии хранятся территориально отдельно от основного контура; восстановление регулярно проверяется учениями (не реже 1 раза в квартал). |
| НФ-9.2.6 | Деградация при недоступности внешних систем (реестры налогового органа, ГАИ, лицензий, платёжный шлюз): Платформа должна продолжать выдачу ЭПЛ по последним кэшированным данным реестров с установкой на документе флага «отложенная сверка»; после восстановления связи сверка выполняется автоматически, расхождения направляются на разбор. Перечень операций, допустимых в режиме деградации, и предельная длительность режима определяются политикой, утверждаемой Минтрансом РТ. |
| НФ-9.2.7 | Офлайн-проверка QR (криптографическая, по модели ISO 18013-5) должна оставаться полностью работоспособной при недоступности серверного контура. |
| НФ-9.2.8 | Отказ любого одиночного компонента (сервер приложений, узел СУБД, брокер очередей) не должен приводить к недоступности Платформы (отсутствие единой точки отказа). |
| НФ-9.2.9 | Все критичные операции (подписание титулов, платежи, блокировки) должны быть идемпотентными: повторная отправка запроса при обрыве связи не создаёт дублей. |

| НФ-9.3.4 | Компоненты с независимыми профилями нагрузки (выдача, QR-проверка, биллинг, уведомления, генерация PDF, интеграции) должны масштабироваться независимо друг от друга. |

## 9.4. Работа на слабых каналах связи

Контекст: фиксированный широкополосный доступ — около 0,07% населения РТ; основной доступ — мобильный (2G/3G, частично 4G). Платформа проектируется по принципу mobile-first (раздел 14.1).

| № | Требование |
|---|---|
| НФ-9.4.1 | Все пользовательские интерфейсы проектируются mobile-first; веб-кабинеты реализуются как PWA с офлайн-кэшем оболочки (app shell), справочников и последних рабочих данных. |
| НФ-9.4.2 | Бюджет первичной загрузки страницы веб-кабинета — не более 500 КБ (передаваемый объём с учётом сжатия), включая критический CSS/JS; последующие переходы — не более 100 КБ. |
| НФ-9.4.3 | Платформа должна оставаться работоспособной на каналах 2G/3G: интерактивность ключевых экранов (лента заявок, карточка ПЛ, форма осмотра) на канале 384 кбит/с с RTT 400 мс — не более 10 с при первом входе и не более 3 с при повторных (кэш). |
| НФ-9.4.4 | Мобильные приложения (водитель, инспектор) должны работать офлайн: просмотр активного ПЛ и QR-кода, подготовка подтверждений и фиксаций с постановкой в очередь отправки; синхронизация — автоматическая при появлении сети, с явным индикатором состояния (раздел 14.4). |
| НФ-9.4.5 | Офлайн-верификация QR инспектором выполняется без сети: полезная нагрузка QR подписана ключом Платформы, подпись проверяется локально (модель ISO 18013-5); ключи проверки обновляются при наличии сети и имеют срок действия. |
| НФ-9.4.6 | SMS-резерв: критические уведомления (готовность ПЛ, недопуск, блокировка) доставляются по SMS при недоставке push в течение заданного интервала; должен быть предусмотрен SMS/USSD-канал справочной проверки статуса ПЛ по номеру (по образцу E-Way Bill). |
| НФ-9.4.7 | Изображения (фото актов, документов) сжимаются на клиенте до передачи (целевой размер ≤ 300 КБ на снимок) с фоновой отправкой и докачкой при обрыве. |
| НФ-9.4.8 | API должно поддерживать сжатие ответов, пагинацию и инкрементальные выборки (`updated_after` — по образцу legacy), исключая передачу полных реестров при каждой синхронизации. |

## 9.5. Многоязычность

| № | Требование |
|---|---|
| НФ-9.5.1 | Платформа должна поддерживать три локали: tg-TJ (таджикский, основной язык государственного делопроизводства), ru-RU (русский), en-US (английский — международный контур). Полнота перевода интерфейсов tg-TJ и ru-RU — 100%; en-US — 100% для международного контура (международные ПЛ, интеграции eCMR/eTIR/E-PERMIT, кабинет интегратора) и не менее справочного уровня для остальных экранов. |
| НФ-9.5.2 | Все справочники (НСИ) ведутся трёхъязычно (tg/ru/en); отсутствие перевода значения справочника блокирует его публикацию. |
| НФ-9.5.3 | Печатные формы формируются трёхъязычно: национальные формы — тадж./рус.; международные формы (5Б-БМ, 4М-БМ) — двуязычное представление тадж./англ. или рус./англ. (по типу документа). |
| НФ-9.5.4 | Переключение языка выполняется без перезагрузки страницы и без потери введённых данных; выбор языка сохраняется в профиле пользователя и применяется ко всем каналам (веб, мобильные, уведомления, SMS). |
| НФ-9.5.5 | Форматы дат, времени и чисел соответствуют локали: дата — dd.mm.yyyy (tg/ru), время — 24-часовое HH:mm, десятичный разделитель — запятая (tg/ru) / точка (en); денежные суммы — в сомони и дирамах (TJS). |
| НФ-9.5.6 | Хранение и обработка текста — Unicode (UTF-8) с полной поддержкой букв таджикского алфавита (ӣ, ӯ, ҳ, ҷ, қ, ғ) во всех полях, поиске, сортировке и печатных формах. |
| НФ-9.5.7 | Пользовательский ввод (наименования, комментарии) не переводится и хранится на языке ввода; системные атрибуты (статусы, типы, причины) отображаются в локали пользователя из трёхъязычных справочников. |

## 9.6. Совместимость

| № | Требование |
|---|---|

| НФ-9.6.3 | Печать документов должна поддерживать форматы A4 и A5 без потери обязательных реквизитов и читаемости QR-кода (раздел 14.5), включая печать на монохромных принтерах. |
| НФ-9.6.4 | Публичное API должно быть совместимо с моделью данных профиля UN/CEFACT MMT-RDM (раздел 3.5) и версионироваться; изменения, нарушающие обратную совместимость, выпускаются только новой версией API. |
| НФ-9.6.5 | Экспортные форматы: PDF/A (долговременное хранение печатных форм), XLSX/CSV (реестры и отчёты), JSON (API). |

## 9.7. Доступность (a11y)

| № | Требование |
|---|---|
| НФ-9.7.1 | Веб-кабинеты должны соответствовать WCAG 2.1 уровня AA в объёме базового набора: контраст текста ≥ 4,5:1 (крупный текст ≥ 3:1), полная работа с клавиатуры, видимый индикатор фокуса, текстовые метки всех полей и кнопок, альтернативный текст значимых изображений. |
| НФ-9.7.2 | Статусы не должны кодироваться только цветом: каждый статус сопровождается текстовой меткой и/или пиктограммой (существенно для монохромной печати и нарушений цветовосприятия). |
| НФ-9.7.3 | Интерфейс должен сохранять работоспособность при увеличении масштаба текста до 200% без потери функциональности и горизонтальной прокрутки основных сценариев. |
| НФ-9.7.4 | Мобильные приложения должны поддерживать системные средства доступности (TalkBack/VoiceOver) для ключевых сценариев водителя и инспектора. |

## 9.8. Эксплуатационные требования

| № | Требование |
|---|---|
| НФ-9.8.1 | Журналирование: структурированные логи (JSON) всех запросов API со сквозным идентификатором корреляции (request id), без записи ПДн и медданных в открытом виде; уровни логирования переключаются без перезапуска. |
| НФ-9.8.2 | Аудит бизнес-операций ведётся отдельно от технических логов в append-only журнале (раздел 7, РП-7.1.5); срок хранения аудита — не менее срока ретенции документов (п. 9.9). |
| НФ-9.8.3 | Мониторинг: метрики доступности, отклика (p50/p95/p99), ошибок, очередей, интеграций и бизнес-показателей (выдано ПЛ/час, доля отказов Т2/Т3, QR-проверки) с дашбордами и автоматическими оповещениями дежурной службе ГУП ЦЦТО; оповещение о нарушении SLA — не позднее 5 минут с момента события. |
| НФ-9.8.4 | Развёртывание релиза — не более 30 минут, без простоя (rolling-обновление либо blue-green); миграции БД обратно совместимы минимум на одну версию; предусмотрен автоматический откат при неуспехе. |
| НФ-9.8.5 | Обновление мобильных приложений не должно блокировать работу предыдущих версий в течение не менее 3 месяцев с даты выпуска; принудительное обновление допускается только по причинам безопасности; совместимость API с приложениями обеспечивается версионированием (НФ-9.6.4). |
| НФ-9.8.6 | Конфигурация (тарифы, лимиты, справочники, фиче-флаги, тексты уведомлений) изменяется без выпуска релиза, с версионированием и аудитом изменений. |
| НФ-9.8.7 | Должны быть развёрнуты контуры: производственный, резервный (НФ-9.2.4), тестовый (staging) и песочница для API-интеграторов с тестовыми данными. |
| НФ-9.8.8 | Синтетический мониторинг ключевых сценариев (выдача ПЛ, QR-проверка, вход) выполняется извне не реже 1 раза в минуту, в том числе с эмуляцией канала 3G. |

## 9.9. Ёмкость хранения и ретенция

### 9.9.1. Оценка объёмов

Расчёт для устойчивого режима 30–50 млн документов/год (горизонт 2030 г.); значения подлежат уточнению по результатам пилота.

| Категория данных | Допущение | Объём/год |
|---|---|---|
| Структурированные данные ЭПЛ (титулы, подписи, статусные переходы) | ~60 КБ/документ | 1,8 – 3,0 ТБ |
| Печатные формы PDF/A с QR | ~200 КБ/документ | 6 – 10 ТБ |
| Фото- и файловые вложения (акты неисправностей, документы, инциденты) | ~20% документов × 2 МБ | 12 – 20 ТБ |
| Журнал аудита и журналы медосмотров | ~35 КБ/документ | 1,0 – 1,8 ТБ |
| **Итого логический прирост** | | **≈ 21 – 35 ТБ/год** |
| С учётом индексов, репликации (×2) и резервных копий | | ≈ 45 – 75 ТБ/год инфраструктурно |
| Накопление за 5 лет ретенции (логически) | | ≈ 110 – 175 ТБ |

| № | Требование |
|---|---|
| НФ-9.9.1 | Система хранения должна быть рассчитана на логический прирост не менее 35 ТБ/год с возможностью расширения без остановки Платформы. |
| НФ-9.9.2 | Срок хранения перевозочных документов, подписей и журналов аудита — не менее 5 лет с даты закрытия документа (с возможностью продления нормативным актом); удаление ранее срока запрещено. |
| НФ-9.9.3 | Ярусное хранение: «горячий» ярус (операционная БД) — документы текущих 13 месяцев; «тёплый» ярус — до 3 лет (доступ из кабинетов с задержкой до 5 с); «холодный» архив (объектное хранилище со сжатием, статус ARCHIVED) — от 3 лет до конца срока ретенции, доступ по запросу до 1 мин. |
| НФ-9.9.4 | Перемещение в архив выполняется автоматически по политике ретенции; архивные документы доступны только для чтения, их целостность защищается контрольными суммами и периодической проверкой (не реже 1 раза в год). |
| НФ-9.9.5 | Печатные формы хранятся в формате PDF/A; криптографические подписи хранятся с данными, достаточными для долгосрочной проверки (метки времени, цепочки сертификатов), с учётом смены ключей за срок ретенции. |
| НФ-9.9.6 | По истечении срока ретенции данные обезличиваются либо уничтожаются по акту в соответствии с политикой, утверждаемой Минтрансом РТ; агрегированная статистика сохраняется бессрочно. |
