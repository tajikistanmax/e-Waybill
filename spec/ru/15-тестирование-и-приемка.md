# 15. Требования к тестированию и приёмке

Настоящий раздел устанавливает обязательные виды тестирования, порядок приёмочных испытаний и требования к тестовым средам и данным Платформы. Требования раздела (ТП-15.x) распространяются на все этапы разработки и внедрения (раздел 16) и подлежат проверке в составе программы и методики испытаний (ПМИ).

## 15.1. Виды тестирования

**ТП-15.1.** Для Платформы являются обязательными следующие виды тестирования:

| № | Вид тестирования | Объект | Момент выполнения |
|---|---|---|---|
| 1 | Модульное | Исходный код микросервисов, мобильных и веб-приложений | Непрерывно, в конвейере CI |
| 2 | Интеграционное и контрактное | API Платформы, включая legacy-контракт агрегаторов; интеграции с внешними системами | Непрерывно и перед каждым релизом |
| 3 | Сквозное (e2e) по ролям | Пользовательские сценарии всех ролей | Перед каждым релизом и в составе испытаний |
| 4 | Нагрузочное | Прикладные сервисы, БД, сервис QR-проверки | Перед приёмочными испытаниями каждого этапа; при изменении архитектуры |
| 5 | Отказоустойчивость и восстановление | Кластер Kubernetes, PostgreSQL, Integration Gateway, резервный контур | Перед приёмочными испытаниями; учения — не реже 2 раз в год |
| 6 | Безопасность | Весь контур Платформы | SAST/DAST — непрерывно; пентест — перед приёмкой и ежегодно |
| 7 | Офлайн-сценарии мобильных приложений | Приложения водителя и инспектора | Перед каждым релизом мобильных приложений |
| 8 | Юзабилити | Кабинеты и мобильные приложения | До начала пилота (этап 1а) и при существенных изменениях UI |
| 9 | Локализация (трёхъязычность) | Все интерфейсы, печатные формы, уведомления | Перед каждым релизом |

### 15.1.1. Модульное тестирование

**ТП-15.2.** Покрытие модульными тестами кода ядра Платформы (сервисы жизненного цикла путевого листа и титулов Т1–Т6, валидации и блокирующие проверки, расчёты одометра и топливных остатков, формирование и подпись QR-нагрузки) должно составлять **не менее 80 %** по строкам кода; для остального прикладного кода — не менее 60 %. Порог покрытия контролируется в конвейере CI; сборка, не достигающая порога, не допускается к развёртыванию.

**ТП-15.3.** Модульные тесты должны покрывать бизнес-правила, унаследованные из legacy-системы и закреплённые настоящим ТЗ, в том числе: сроки действия путевых листов по типам, правило единственного активного путевого листа, перенос топливного остатка `remain_fuel_before_exit` из предыдущего путевого листа того же ТС, запрет изменения показаний одометра диспетчером для автобусов, условную обязательность лицензии и контрольной карточки для перевозчиков общего пользования (type_company_id = 1).

### 15.1.2. Интеграционное и контрактное тестирование

**ТП-15.4.** Для всех публичных API Платформы должны быть разработаны контрактные тесты на основе спецификаций OpenAPI. Изменение, нарушающее контракт без объявления новой версии, должно блокироваться конвейером CI (см. политику совместимости СП-17.11).

**ТП-15.5.** Отдельный обязательный набор контрактных тестов фиксирует **legacy-совместимый контракт агрегаторов** (ЧУРА, НЕРУ; эндпоинт выдачи путевого листа такси по образцу `waybill_neru`), включая проверку следующего поведения:

| Проверка | Ожидаемое поведение |
|---|---|
| Повторная заявка агрегатора | Предыдущий путевой лист закрывается, создаётся новый в статусе «Ожидает» |
| Запрос до подтверждения врача и механика | Отказ с кодом 409 («необходимо пройти медосмотр/техосмотр») |
| Расчёт одометра | `indication_counter_entry = indication_counter_exit + distance` |
| Срок действия | Отклонение `entry_date` позднее 7 дней от даты выезда (код 422) |
| Дата въезда раньше даты выезда | Код 422 с текстом ошибки |
| Отсутствующие организация/ТС/водитель/ПЛ | Код 404 |
| Получение путевого листа по идентификатору | Возвращается только подтверждённый путевой лист |

**ТП-15.6.** Интеграции с внешними системами (единая платформа мастер-данных, E-PERMIT, eTIR, ГАИ МВД, Налоговый комитет, национальный УЦ, платёжный шлюз, реестр медработников, ГУП-агрегаторы) тестируются на эмуляторах (заглушках), воспроизводящих контракты, задержки и коды ошибок реальных систем. Для каждой интеграции обязателен тест деградации: недоступность внешней системы не должна блокировать функции ядра (кэш последних валидных ответов, очереди повторов, ручные режимы).

### 15.1.3. Сквозное тестирование по ролям

**ТП-15.7.** Должны быть автоматизированы сквозные (e2e) сценарии для каждой роли: диспетчер (танзимгар), медицинский работник (духтур), механик, водитель, инспектор, оператор ГУП ЦЦТО, администратор Платформы, внешний интегратор (агрегатор). Сценарии охватывают полный жизненный цикл путевого листа с титулами Т1–Т6 для каждого типа документа: Т(1-АД) автобус и троллейбус, 1-А, 3-С (все виды обслуживания), 2-Б, 5Б-БМ, 4М-БМ, а на этапе 2 — э-ТТН (борхати замимаи 1/2, CMR/eCMR).

**ТП-15.8.** В e2e-набор включаются негативные сценарии: попытка выдачи путевого листа без подтверждения врача или механика, просроченные медсправка/техосмотр/контрольная карточка, отозванная лицензия, ТС в розыске, недействительное водительское удостоверение, повторное подтверждение титула одним и тем же сотрудником.

### 15.1.4. Нагрузочное тестирование

**ТП-15.9.** Нагрузочное тестирование должно подтвердить следующие целевые показатели:

| Показатель | Целевое значение | Условия |
|---|---|---|
| Операции записи (создание/подписание титулов) | ≥ 100 запросов/с | Устойчиво, без деградации, ошибки < 0,1 % |
| Операции чтения (кабинеты, API, реестры) | ≥ 500 запросов/с | Одновременно с потоком записи |
| QR-проверки | ≥ 100 000 проверок/сутки | С учётом неравномерности в течение суток |
| Утренний пик выдачи путевых листов | Профиль 04:00–09:00, ≥ 60 % суточного объёма выдачи | Моделируется отдельным сценарием «утро автобусных парков» |
| Длительная стабильность | 24 часа под целевой нагрузкой | Отсутствие утечек ресурсов и роста времени отклика |
| Запас масштабирования | ×5 от целевой нагрузки | Подтверждается горизонтальным масштабированием в Kubernetes |

**ТП-15.10.** Времена отклика под целевой нагрузкой должны соответствовать нефункциональным требованиям настоящего ТЗ; отчёт о нагрузочном тестировании (методика, профили, результаты, узкие места) входит в комплект приёмочной документации этапа.

### 15.1.5. Тестирование отказоустойчивости

**ТП-15.11.** Проверяются сценарии: поочерёдное отключение каждой внешней системы (мастер-данные, УЦ, E-PERMIT, ГАИ, налоговая, платёжный шлюз, SMS-провайдер) с подтверждением деградационного поведения по ТП-15.6; отказ узла Kubernetes; отказ основного экземпляра PostgreSQL с переключением на реплику; потеря связности с госЦОД.

**ТП-15.12.** Переключение на **резервный (зеркальный) контур** проверяется учениями с фиксацией фактических RTO/RPO; выдача путевых листов и QR-проверка должны продолжаться на резервном контуре. Офлайн-проверка QR инспектором должна сохранять работоспособность при полной недоступности обоих контуров.

### 15.1.6. Тестирование безопасности

**ТП-15.13.** В конвейер CI встраиваются SAST (статический анализ кода и зависимостей, включая контроль уязвимых библиотек) и DAST (динамическое сканирование развёрнутых сред). Сборки с непринятыми критическими и высокими уязвимостями к продуктивному развёртыванию не допускаются.

**ТП-15.14.** Перед приёмочными испытаниями этапа 1а и далее ежегодно проводится тестирование на проникновение (пентест) независимой организацией, согласованной с заказчиком. Область: внешний периметр, веб-кабинеты, мобильные приложения, публичные API (включая sandbox), сервис QR-проверки. Критерий: отсутствие неустранённых уязвимостей критического и высокого уровня. Дополнительно проверяется матрица ролевого доступа: недоступность операций и данных вне полномочий роли.

### 15.1.7. Офлайн-сценарии мобильных приложений

**ТП-15.15.** Мобильные приложения водителя и инспектора тестируются в условиях: сеть 2G/3G с высокими задержками и потерями пакетов; полное отсутствие сети; восстановление связи после длительного офлайна. Обязательные проверки: офлайн-верификация подписанной QR-нагрузки инспектором без входа в систему и без сети; предъявление путевого листа водителем из локального кэша; накопление и корректная синхронизация очереди событий; разрешение конфликтов синхронизации; получение номера путевого листа по SMS-резерву.

**ТП-15.16.** Тестирование проводится на реальных устройствах, репрезентативных для парка пользователей (бюджетные Android-устройства не новее применяемых в отрасли), а не только на эмуляторах.

### 15.1.8. Юзабилити-тестирование

**ТП-15.17.** До начала пилота проводится юзабилити-тестирование с реальными пользователями: диспетчерами, медицинскими работниками, механиками и водителями автотранспортных предприятий (суммарно не менее 20 участников, охватывающих все перечисленные роли), а также с инспекторами. Метрики: время оформления путевого листа не выше времени оформления бумажной формы; доля успешно выполненных задач без подсказки — не менее 90 %. Выявленные замечания включаются в бэклог и устраняются до начала пилота (блокирующие и высокие — обязательно).

### 15.1.9. Тестирование локализации (трёхъязычность)

**ТП-15.18.** Проверяется полнота и корректность языковых версий: таджикский и русский — 100 % строк всех интерфейсов, печатных форм, SMS- и push-уведомлений, текстов ошибок; английский — для международного контура (международные путевые листы, eCMR/eTIR, портал разработчика). Проверяются переключение языка без потери контекста, форматы дат и чисел, отображение таджикских символов (ӣ, ӯ, ҳ, қ, ҷ, ғ) во всех каналах, включая SMS и генерируемые PDF.

## 15.2. Приёмочные испытания

**ТП-15.19.** Приёмка каждого этапа (раздел 16) выполняется в последовательности:

| Стадия | Содержание | Результат |
|---|---|---|
| 1. Предварительные испытания | Проверка по ПМИ на стенде, приближённом к продуктивному; полный прогон автоматизированных наборов | Протокол предварительных испытаний; допуск к опытной эксплуатации |
| 2. Опытная эксплуатация (пилот) | Эксплуатация на реальных пользователях и данных в объёме этапа (для этапа 1а — пилот в г. Душанбе); ведение журнала опытной эксплуатации | Акт о завершении опытной эксплуатации; перечень замечаний и отметки об устранении |
| 3. Приёмочные испытания | Проверка приёмочной комиссией по ПМИ, включая критерии ТП-15.22 | Акт приёмочных испытаний; решение о вводе в промышленную эксплуатацию |

**ТП-15.20.** Программа и методика испытаний (ПМИ) разрабатывается исполнителем и согласуется заказчиком не позднее чем за 30 календарных дней до начала предварительных испытаний этапа. ПМИ содержит: перечень проверок с привязкой к требованиям ТЗ, сценарии и исходные данные, ожидаемые результаты, критерии успешности, состав и роли участников, порядок фиксации и классификации замечаний (блокирующее / высокое / среднее / низкое).

**ТП-15.21.** В период опытной эксплуатации блокирующие и высокие замечания устраняются до её завершения; наличие неустранённых блокирующих замечаний исключает переход к приёмочным испытаниям.

**ТП-15.22.** Критерии приёмки этапа:

| № | Критерий | Способ проверки |
|---|---|---|
| 1 | Все сквозные сценарии ролей (ТП-15.7, ТП-15.8) выполняются успешно | Прогон e2e-набора в присутствии комиссии; 100 % критических сценариев |
| 2 | Нагрузочные показатели подтверждены (ТП-15.9) | Отчёт о нагрузочном тестировании; контрольный прогон |
| 3 | Пентест завершён, критические и высокие уязвимости отсутствуют либо устранены | Отчёт независимой организации; повторная проверка устранения |
| 4 | Офлайн-проверка QR работает без доступа к сети | Полевая демонстрация: устройство инспектора в авиарежиме верифицирует подлинный QR и отклоняет поддельный |
| 5 | Обе языковые версии (таджикская и русская) полны и корректны | Проверка по чек-листу локализации ТП-15.18 |
| 6 | Миграция данных rohkhat.tj сверена | Контрольные суммы и счётчики по сущностям (организации, ТС, водители, сотрудники, путевые листы); выборочная ручная сверка; расхождения ≤ 0,1 % с протоколом причин |
| 7 | Комплект документации этапа передан (раздел 18) | Проверка по описи |
| 8 | Служба поддержки готова к сопровождению этапа (раздел 17) | Проверка регламентов, укомплектованности L1–L3, обученности персонала |

**ТП-15.23.** Для этапов 1б–2 критерии таблицы ТП-15.22 применяются в объёме функциональности этапа; критерий 6 (миграция) применяется к этапам, в которых выполняется перенос данных.

## 15.3. Тестовые среды и данные

**ТП-15.24.** Должны быть развёрнуты и поддерживаться следующие среды:

| Среда | Назначение | Данные |
|---|---|---|
| Разработка (dev) | Сборки разработчиков | Синтетические |
| Тестирование (test) | Функциональное, интеграционное, e2e | Синтетические и обезличенные |
| Нагрузочная (load) | Нагрузочные и отказоустойчивые испытания; конфигурация, соразмерная продуктивной | Синтетические полного объёма |
| **Sandbox интеграторов** | Публичная песочница для агрегаторов и учётных систем перевозчиков | Синтетические |
| Предпродуктивная (staging) | Предварительные испытания, репетиция миграций и релизов | Обезличенные |
| Продуктивная (prod) и резервный контур | Промышленная эксплуатация | Продуктивные |

**ТП-15.25.** Sandbox для интеграторов: доступна в режиме 24/7 (независимо от регламентных работ продуктивного контура); самостоятельная регистрация аккредитованных интеграторов с выдачей тестовых учётных данных; полный набор API, включая legacy-совместимый контракт агрегаторов; тестовые контуры ЭЦП и платёжного шлюза (без реальных списаний); синтетические реестры организаций, ТС и водителей; периодический сброс данных с уведомлением; документация — на портале разработчика (раздел 18).

**ТП-15.26.** Использование продуктивных данных (в том числе мигрированных из rohkhat.tj) вне продуктивного контура допускается **только в обезличенном виде**: РМА, ФИО, номера документов, госномера, телефоны и адреса подвергаются псевдонимизации с сохранением форматов, контрольных правил и ссылочной связности между сущностями. Процедура обезличивания автоматизирована и документирована.

**ТП-15.27.** Для нагрузочных испытаний применяются генераторы синтетических данных, воспроизводящие продуктивные объёмы и распределения не ниже: 700 тыс. транспортных средств, 100 тыс. водителей, 30 тыс. организаций, годовой объём путевых листов с учётом целевого показателя 100 % электронных документов к 2030 году, суточный профиль с утренним пиком выдачи.
