# 12. API и интеграции

Настоящий раздел определяет требования к программным интерфейсам Платформы (публичный API, API аккредитованных интеграторов, массовая загрузка) и к интеграциям с внешними системами. Технологическая база: микросервисы Java 21 / Spring Boot 3, API Gateway, брокер Kafka, IAM Keycloak (OAuth2/OIDC). Все внешние интеграции изолируются в подсистеме Integration Gateway: сбой внешней системы не должен блокировать ядро Платформы.

## 12.1. Принципы построения API

| № | Требование | Содержание |
|---|---|---|
| ИН-12.1.1 | REST + OpenAPI 3.1 | Все синхронные интерфейсы — REST/HTTP 1.1+ (TLS 1.2+). Контракт каждого сервиса описывается спецификацией OpenAPI 3.1 (contract-first); спецификации публикуются на портале разработчика и версионируются вместе с кодом. |
| ИН-12.1.2 | Версионирование | Версия — в пути: `/api/v1/...`. Обратная совместимость внутри мажорной версии обязательна (добавление полей — не ломающее изменение). Ломающие изменения — только в `/api/v2`. Вывод версии из эксплуатации: анонс ≥ 12 месяцев, заголовки `Deprecation` и `Sunset`. Legacy-совместимые эндпоинты агрегаторов (12.3) — отдельный контур с собственным графиком вывода. |
| ИН-12.1.3 | Форматы | Основной формат — JSON (UTF-8). Для международного контура и профилей UN/CEFACT (eCMR, eTIR, э-ТТН, eFTI) дополнительно поддерживается XML; выбор — заголовком `Accept` (content negotiation). Дата/время — ISO 8601 с явным смещением (нормативный пояс Asia/Dushanbe, UTC+05:00). |
| ИН-12.1.4 | Пагинация, фильтрация, сортировка | Единообразно для всех списков: `page`, `per_page` (по умолчанию 20, максимум 100) с метаблоком `meta {current_page, last_page, per_page, total}` (совместимо с legacy); для больших/часто изменяющихся наборов — курсорная пагинация (`cursor`, `limit`). Фильтры — именованными query-параметрами (в т.ч. `updated_after` для инкрементальных выгрузок — legacy-совместимо); сортировка — `sort=field,-field2`. |
| ИН-12.1.5 | Идемпотентность | Все POST-операции создания принимают заголовок `Idempotency-Key` (UUID клиента); повтор с тем же ключом в течение 24 ч возвращает результат первичного запроса без побочных эффектов. Для платёжных колбэков и webhooks идемпотентность обязательна по `external_tx_id`/`event_id`. |
| ИН-12.1.6 | Rate limiting | Ограничение частоты — на уровне API Gateway, по клиенту (client_id токена) и по IP: базовые лимиты публичного API — 10 rps / 100 000 запросов в сутки (уточняются по ролям и уровням аккредитации, 12.6). Превышение — `429 Too Many Requests` + `Retry-After`; заголовки `X-RateLimit-Limit/Remaining/Reset`. Ночное «окно выгрузок» legacy (API только 23:00–05:00 для массовых операций) **не переносится**: API доступен 24/7, массовые операции переводятся в асинхронный контур (12.5). |
| ИН-12.1.7 | Единая модель ошибок | Ошибки — RFC 7807 (`application/problem+json`): `type`, `title`, `status`, `detail`, `instance`, расширения `code` (машинный код), `errors[]` (по полям), `request_id`. Сопоставление с legacy-кодами: 400 — ошибка запроса (текст пользователю); 404 — объект не найден (организация/водитель/ТС/ПЛ); 409 — конфликт (не подтверждён врачом/механиком, повторное подтверждение, активный ПЛ существует); 422 — ошибки валидации по полям; 500 — внутренняя ошибка. Тексты ошибок — трёхъязычные (заголовок `Accept-Language`: tg по умолчанию, ru, en). |
| ИН-12.1.8 | Аутентификация и авторизация | OAuth2/OIDC через Keycloak: пользовательские сценарии — Authorization Code + PKCE; системные — Client Credentials. Токен — JWT (Bearer), время жизни ≤ 15 мин + refresh. Авторизация — по ролям (roles-matrix.yaml) и скоупам. Межведомственные системные каналы — дополнительно mTLS. |
| ИН-12.1.9 | Трассировка | Каждый запрос получает `X-Request-Id` (принимается от клиента или генерируется); идентификатор сквозной через все сервисы, входит в журнал аудита и в тело ошибки. |
| ИН-12.1.10 | Файлы | Загрузка файлов — до создания сущности (legacy-паттерн `/api/files/upload` сохраняется семантически): `POST /api/v1/files` возвращает `file_id` (и/или presigned-URL прямой загрузки в S3); сущности ссылаются на `file_id`. Проверки: MIME, размер (≤ 10 МБ, конфигурируемо), антивирус. |
| ИН-12.1.11 | Webhooks | Исходящие уведомления подписываются HMAC-SHA256 (заголовок `X-Signature`, секрет подписки); доставка — at-least-once с экспоненциальными повторами (до 24 ч), затем DLQ и уведомление интегратору; события идемпотентны по `event_id`. |
| ИН-12.1.12 | Автодополнение | Единый паттерн подсказок: `GET /api/v1/suggest/{dictionary}?query=` — префиксный поиск, ≤ 10 результатов (legacy-совместимо: brand, city, external_city, route, client, direction, remain_fuel и др.). |

## 12.2. Публичный API Платформы

Требование ИН-12.2.1: публичный API реализует следующие группы эндпоинтов (базовый префикс `/api/v1`). Доступ к каждой операции ограничен ролями (roles-matrix.yaml); ниже указаны основные операции групп.

| Группа | Базовый путь | Основные операции | Примечания |
|---|---|---|---|
| Организации | `/organizations` | GET список/карточка; POST регистрация; PATCH данные; GET `/organizations/{id}/employees|vehicles|drivers` | мастер-данные — чтение из локальной копии единой платформы; изменения — заявкой в единую платформу |
| Водители | `/drivers` | GET список/карточка (фильтры: `rma`, `organization_id`, `updated_after`); POST/PATCH (upsert по РМА); GET `/drivers/{id}/waybills` | документы (ВУ, медсправка, 20-часовые занятия) — вложениями file_id |
| Транспортные средства | `/vehicles` | GET список/карточка (фильтр `registration_number`); POST/PATCH (upsert по госномеру); GET `/vehicles/{id}/waybills`; подресурс `/vehicles/{id}/trailers` | одометр автобуса недоступен для записи диспетчеру |
| Сотрудники | `/employees` | GET/POST/PATCH (upsert по РМА); фильтр по типу (врач/механик/диспетчер) | подпись/печать — file_id |
| Путевые листы | `/waybills` | POST создать (тип — в теле; черновик или сразу Т1); GET список (фильтры: статус, тип, период, ТС, водитель, организация); GET `/{id}`; PATCH `/{id}` (только DRAFT); POST `/{id}/titles/{t1..t6}` — подписание титула; POST `/{id}/confirm-med`, `/{id}/confirm-tech` (упрощённые фасады Т2/Т3, семантика legacy `/waybill/confirm`); POST `/{id}/issue` (выдача водителю), `/{id}/activate` (Т4), `/{id}/return` (Т5), `/{id}/close` (Т6/закрытие), `/{id}/cancel` (причина из справочника), `/{id}/extend`; подресурсы `/{id}/work-days` (POST/PATCH адресно по дню), `/{id}/fuel-records`; GET `/{id}/qr`, `/{id}/pdf`, `/{id}/status-history` | переходы — строго по статусной модели; ошибки конфликтов — 409; блокирующие проверки (checks.yaml) — при подписании Т1 и выдаче |
| Медосмотры | `/med-checks` | GET лента заявок (роль DOCTOR); POST результат осмотра (АД, пульс, температура, алкотест, вердикт) → подписание Т2/Т6; GET журнал | аутсорс-медпункты видят заявки своих клиентов |
| Техосмотры | `/tech-checks` | GET лента заявок (роль MECHANIC); POST результат (чек-лист, дефекты, акт/фото) → Т3; GET журнал | |
| Оплата | `/invoices`, `/payments` | GET счета/задолженность; POST `/invoices/{id}/pay` (переадресация в платёжный шлюз); колбэк `/payments/callback` (идемпотентный); GET история | биллинг — контур E-PERMIT (12.4.6) |
| QR-верификация | `/verify` | GET `/verify/{jws}` — публичная проверка (без аутентификации): статус, минимальный состав данных; POST `/verify/{jws}/inspection` — фиксация проверки инспектором (гео, время, результат, нарушение); GET `/.well-known/jwks.json` — ключи офлайн-проверки | публичный высокодоступный контур, изолированный от ядра |
| Отчёты | `/reports` | GET параметризованные отчёты: по ТС, водителям, маркам, маршрутам, зарплате водителя, журнал диспетчера, топливо; общие (по месяцам, видам перевозок); экспорт CSV/XLSX/PDF; асинхронные — `/reports/jobs` | состав — наследие «НА ва ХЛ» (пассажирские/грузовые/общие) |
| Файлы | `/files` | POST загрузка (file, file_type); GET метаданные/скачивание; DELETE (до привязки к сущности) | ИН-12.1.10 |
| Справочники | `/dictionaries` | GET `/dictionaries` (перечень); GET `/dictionaries/{code}?updated_after=&page=` — записи с версиями; GET `/suggest/{code}?query=` | чтение — все аутентифицированные; изменение — SYSTEM_ADMIN |
| Webhooks | `/webhooks` | POST/GET/DELETE подписки (URL, события, секрет); GET `/webhooks/{id}/deliveries` — журнал доставок | события: смена статуса ПЛ, результаты Т2/Т3, оплата, блокировка |

Требование ИН-12.2.2: мобильные приложения (кабинет водителя, приложение инспектора) используют тот же публичный API; специфичные операции — подтверждение получения ПЛ (Face ID/PIN → `POST /waybills/{id}/acknowledge`), приём/сдача ТС, офлайн-кэш QR.

## 12.3. API для аккредитованных интеграторов (агрегаторы ЧУРА, НЕРУ и др.)

### 12.3.1. Модель доступа

- ИН-12.3.1: интегратор получает OAuth2-клиент (Client Credentials) со **scoped-токенами**: скоупы вида `aggregator:waybill.create`, `aggregator:waybill.read`, `webhook:manage`; область данных ограничена перечнем организаций-клиентов интегратора (список РМА в атрибутах клиента Keycloak, подтверждается договором организации с интегратором). Запрос вне области — 403.
- ИН-12.3.2: все вызовы интеграторов журналируются с client_id; лимиты и квоты — по уровню аккредитации (12.6).

### 12.3.2. Legacy-совместимый контракт (`waybill_neru`)

Требование ИН-12.3.3: на переходный период Платформа предоставляет контракт, семантически идентичный legacy `POST /api/waybill_neru` (новый путь `POST /api/v1/aggregator/waybills`, алиас старого пути сохраняется на срок вывода legacy).

Запрос: `organization_rma` (обяз.), `transport_registration_number` (обяз.), `driver_rma` (обяз.), `employee_rma`, `exit_date` (обяз.), `entry_date`, `distance` (обяз., км).

Поведение (legacy-семантика, сохраняется полностью):

1. При поступлении новой заявки **предыдущий активный ПЛ** данного водителя/ТС **закрывается**, создаётся новый со статусом «Ожидает» (CREATED → AWAITING_MED/AWAITING_TECH).
2. Пока врач и механик не подписали Т2 и Т3, любой повторный запрос возвращает ошибку «необходимо пройти медосмотр/техосмотр» (409).
3. После подтверждений — `201` с объектом ПЛ: `id`, `number`, `exit_date`, `entry_date`, `indication_counter_exit`, `company {id, rma, name, kpp}`, `parking {id, registration_number, vincode}`, `timesheet {id, full_name, rma}`, статус «Активный».
4. Одометр возврата вычисляется: `indication_counter_entry = indication_counter_exit + distance`.
5. `GET /api/v1/aggregator/waybills/{id}` — возвращает **только подтверждённый** (Т2+Т3) ПЛ; неподтверждённый — 404/409 по legacy-семантике.
6. Правило срока: `entry_date − exit_date ≤ 7 дней`; `entry_date > exit_date` (422).

Коды ошибок legacy-контракта (обязательны к воспроизведению):

| HTTP | Условие | Сообщение (семантика legacy) |
|---|---|---|
| 404 | организация не найдена по РМА | «Организация не найдена» |
| 404 | ТС не найдено по госномеру | «Транспорт не найден» |
| 404 | водитель не найден по РМА | «Водитель не найден» |
| 404 | ПЛ не найден / не подтверждён (GET) | «Путевой лист не найден» |
| 409 | врач не подтвердил | «Доктор не подтвердил путёвку» |
| 409 | механик не подтвердил | «Механик не подтвердил путёвку» |
| 409 | повторное подтверждение тем же сотрудником | «This employee has already confirmed this waybill» |
| 422 | нарушение обязательности полей | ошибки по полям |
| 422 | `entry_date` ≤ `exit_date` | «дата въезда должна быть больше даты выезда» |
| 422 | срок более 7 дней | «не более 7 дней от даты выезда» |

### 12.3.3. Расширенный контракт v2

Требование ИН-12.3.4: параллельно предоставляется расширенный контракт `/api/v2/aggregator/*`: явное управление жизненным циклом (создание черновика, запрос Т2/Т3, отдельное закрытие без автозакрытия предыдущего), предварительные проверки (`POST /precheck` — прогон блокирующих проверок checks.yaml без создания документа), многодневные ПЛ, получение QR-нагрузки, RFC 7807-ошибки, пагинация и `updated_after`-выгрузки. Новые интеграторы подключаются сразу к v2; legacy-контракт закрывается для новых подключений.

### 12.3.4. Webhooks статусов

Требование ИН-12.3.5: интегратор подписывается на события своих документов: `waybill.created`, `waybill.med.passed|rejected`, `waybill.tech.passed|rejected`, `waybill.ready`, `waybill.issued`, `waybill.active`, `waybill.closed`, `waybill.cancelled`, `waybill.blocked`, `waybill.expired`. Формат — JSON (event_id, тип, время, waybill_id, номер, статус, минимальный дифф); подпись и повторы — по ИН-12.1.11. Polling-модель legacy (повторные GET) сохраняется, но webhooks — рекомендуемый механизм.

## 12.4. Интеграции с внешними системами

Требование ИН-12.4.1: каждая интеграция реализуется через Integration Gateway с изоляцией отказов (circuit breaker), кэшем последних валидных ответов, очередями повторов (Kafka/outbox) и документированным ручным режимом. Сводная матрица (по integrations.yaml):

| Код | Назначение | Инициатор | Протокол / формат | Режим | SLA (цель) | Деградация при недоступности |
|---|---|---|---|---|---|---|
| UNIFIED_PLATFORM | мастер-данные: реестры ЮЛ/ИП, водителей, ТС, лицензий, сертификатов, контрольных карточек, международных разрешений | двусторонний | REST/gRPC + Kafka / JSON | онлайн + события + батч-снимки | 99,9%, p95 ≤ 300 мс | локальная SCD-2-копия — работа продолжается по последним валидным данным; помеченные «непроверенными» изменения досверяются очередью |
| SSO_IAM | аутентификация, роли, 2FA | Платформа | OIDC/OAuth2 | онлайн | 99,95% | вход невозможен (критический компонент — кластер HA); действующие токены живут до истечения |
| LICENSE_REGISTRY | активная лицензия на вид перевозки (transcontrol.tj) | Платформа | REST / JSON | онлайн, кэш | 99,5%, p95 ≤ 1 с | кэш последнего ответа ≤ 72 ч; при отсутствии — ручной режим с пометкой и отложенной досверкой |
| CONTROL_CARD | действительность контрольной карточки (варақаи назоратӣ) | Платформа | REST / JSON | онлайн, кэш | 99,5% | как LICENSE_REGISTRY |
| CERT_REGISTRY | сертификаты соответствия/компетентности | Платформа | REST / JSON | онлайн, кэш | 99,5% | как LICENSE_REGISTRY |
| E_PERMIT | валидация дозвола международного ПЛ; централизованный биллинг | Платформа | REST / JSON | онлайн | 99,7%, p95 ≤ 2 с | дозвол: кэш ранее провалидированных дозволов; без валидации выдача международного ПЛ блокируется (проверка 17), допускается ручное подтверждение SYSTEM_ADMIN с аудитом; биллинг: очередь счетов, оплата «в ожидании» |
| E_CMR | привязка международного ПЛ/э-ТТН к eCMR | двусторонний | AS4/eDelivery / XML (профиль MMT-RDM) | события + батч | 99% | очередь исходящих сообщений с повторами; ПЛ выдаётся, привязка досылается |
| E_TIR | обмен данными транзита с национальным приложением eTIR | двусторонний | AS4 + REST (ЕЭК ООН) / XML | события | 99% | очередь повторов; операции eTIR не блокируют выдачу ПЛ |
| GPS_MONITORING | трек рейса, контроль маршрута/пробега, сверка одометра | внешняя система → Платформа | REST push/Kafka / JSON | события/поток | 99% | отсутствие трека не блокирует документ; антифрод-сигналы «нет данных GPS» |
| NERU_CAMERAS | поток распознанных госномеров → сверка с активными ПЛ (антифрод) | внешняя система → Платформа | Kafka / HTTP push, JSON | поток событий | best effort | буферизация потока; пропуски не влияют на ядро |
| TAX_COMMITTEE | проверка РМА, статуса ЮЛ/ИП, кадровой принадлежности водителя | Платформа | REST (или через шину госвзаимодействия) / JSON | онлайн, кэш | 99,5%, p95 ≤ 2 с | кэш ≤ 72 ч; ручной режим с пометкой «непроверено» и обязательной досверкой; отрицательная досверка → автоблокировка документа |
| MVD_GAI | валидация ТС (учёт, арест, розыск) и ВУ (действительность, категории, лишение) | Платформа | REST / JSON | онлайн, кэш | 99,5%, p95 ≤ 2 с | как TAX_COMMITTEE |
| PAYMENT_GATEWAY | оплата тарифов («Корти милли», банки, кошельки) через биллинг E-PERMIT | двусторонний | REST + колбэки / JSON | онлайн | 99,7% | очередь платёжных колбэков; абонементы обслуживаются локально; ручное подтверждение бухгалтером |
| NOTIFICATIONS | SMS/Email/Push участникам | Платформа | SMPP/HTTP к операторам РТ; SMTP; FCM/APNs | асинхронно | 99% | очередь с повторами; резервный SMS-шлюз второго оператора |
| DIGITAL_SIGNATURE | КЭП титулов (УЦ РТ, Закон № 1965), метки времени | Платформа | PKI: CAdES/XAdES/JWS, OCSP/CRL, TSA | онлайн | 99,9% | кэш CRL/OCSP для проверки; недоступность TSA — очередь меток; недоступность облачной подписи — подписание невозможно (документ ждёт в текущем статусе), уведомление |
| QR_VERIFY | публичная верификация QR (онлайн + офлайн) | внешние потребители → Платформа | REST + JWKS / JWS(COSE) | онлайн + офлайн | 99,95% | офлайн-проверка подписи нагрузки по ISO 18013-5 работает без сети по дистрибутированным ключам JWKS |
| MED_REGISTRY | аккредитация медработников/медпунктов, поверка приборов (Минздрав) | Платформа | REST / JSON | онлайн + батч | 99% | кэш реестра; аккредитация проверяется по последней копии |
| STATISTICS | госстатотчётность (замена бумажной Замимаи 7) | Платформа → Агентство | REST/SFTP батч / XML, XLSX | батч (месяц/квартал) | по регламенту | повтор выгрузки; данные формируются из витрин |
| CUSTOMS | данные международных рейсов на пункты пропуска | двусторонний | REST/Kafka / JSON (связка eTIR/E-PERMIT) | события | 99% | очередь повторов |
| AGGREGATORS | API агрегаторов (ЧУРА, НЕРУ) | внешние системы → Платформа | REST / JSON | онлайн | 99,7% | см. 12.3 |

### 12.4.2. Единая платформа Минтранса — двусторонний контракт мастер-данных

- ИН-12.4.2: **REST-справочники**: Платформа читает реестры единой платформы (`companies`, `drivers`, `vehicles`, `employees`, лицензии, сертификаты, контрольные карточки, международные разрешения) постранично с параметром `updated_after` (инкрементально; паттерн legacy-выгрузок сохраняется). Полные снимки — регламентно (еженедельно) для контроля дрейфа.
- ИН-12.4.3: **Kafka-события изменений**: единая платформа публикует события `up.company.changed`, `up.driver.changed`, `up.vehicle.changed`, `up.employee.changed`, `up.license.changed` и др.; Платформа применяет их как SCD-2-версии локальной копии (МД-11.6.3). Гарантия — at-least-once, идемпотентность по ключу события.
- ИН-12.4.4: **Обратный поток**: Платформа публикует события выдачи/закрытия/аннулирования перевозочных документов и агрегаты истории перевозок для единой платформы (принцип однократности: данные документа хранятся у источника — Платформы, единая платформа получает ссылки и статусы).
- ИН-12.4.5: **Снимки при выдаче**: в момент подписания Т1 значения мастер-данных фиксируются в документе (МД-11.1.1); онлайн-проверка против единой платформы выполняется в составе блокирующих проверок; при недоступности — деградация по матрице 12.4.1.

### 12.4.3. E-PERMIT

ИН-12.4.6: перед выдачей международного ПЛ (WB_TRUCK_INTL, WB_PAX_INTL) Платформа валидирует дозвол: `GET permit/{number}` (страна, маршрут, срок, тип, остаток поездок); снимок ответа сохраняется в `type_data.epermit_snapshot`. Биллинг: счета Платформы создаются в централизованной биллинговой платформе E-PERMIT; колбэки оплаты идемпотентны; сверка реестров платежей — ежесуточно.

### 12.4.4. ЭЦП / Удостоверяющий центр

ИН-12.4.7: подписание титулов Т1–Т6 — квалифицированной ЭП по Закону РТ № 1965 (облачная подпись или токены), формат CAdES-T/XAdES-T либо JWS с меткой времени TSA; проверка сертификатов OCSP/CRL с кэшированием; подтверждение водителя (Face ID/PIN) — простая ЭП, титулом не является (roles-matrix.yaml).

### 12.4.5. eCMR / eTIR

ИН-12.4.8: обмен международного контура — AS4/eDelivery; полезная нагрузка — XML-профиль UN/CEFACT MMT-RDM (маппинг — таблица 11.1.1). Международный ПЛ хранит ссылки `ecmr_id`/`etir_ref`; события выдачи/закрытия транслируются в соответствующие системы асинхронно и не блокируют внутренний документооборот.

### 12.4.6. ГАИ / Налоговый комитет

ИН-12.4.9: онлайн-проверки перед выдачей (checks.yaml №№ 1–8, 14–16): РМА и кадровая принадлежность — Налоговый комитет; учёт/розыск ТС, действительность и категории ВУ, лишение — ГАИ. Результат проверки с меткой времени и источником входит в снимок документа. Деградация — по матрице (кэш ≤ 72 ч → ручной режим с пометкой и досверкой; отрицательная досверка → BLOCKED + уведомление).

### 12.4.7. Платёжный шлюз и SMS-шлюзы

ИН-12.4.10: оплата — через биллинговый контур E-PERMIT («Корти милли», банковские карты, мобильные кошельки); прямые интеграции с банками — резервный вариант. ИН-12.4.11: SMS — прямые подключения к операторам РТ (Tcell, МегаФон Таджикистан, Babilon-M, ZET-Mobile) по SMPP/HTTP; ключевой сценарий — **SMS-резерв**: отправка номера и срока ПЛ водителю при отсутствии интернета; очередь с повторами и переключением оператора.

### 12.4.8. Камеры NERU

ИН-12.4.12: Платформа принимает поток распознанных госномеров с дорожных камер (Kafka-топик или HTTP-push пакетами): `{plate, camera_id, geo, timestamp}`. Обработчик сверяет номер с наличием **активного ПЛ** (модель RFID/FASTag, Индия): попадание без активного ПЛ или с просроченным документом формирует антифрод-сигнал в контур аналитики Минтранса (без автоматических санкций на этапе 1). Поток не влияет на доступность ядра; допускается буферизация и потеря отдельных событий.

## 12.5. Массовая загрузка (bulk)

| № | Требование |
|---|---|
| ИН-12.5.1 | Крупным перевозчикам предоставляется массовый импорт CSV/XLSX: водители, ТС, сотрудники, заявки на путевые листы. Шаблоны файлов (с тадж./рус. заголовками) публикуются на портале; кодировка UTF-8. |
| ИН-12.5.2 | Импорт асинхронный: `POST /api/v1/bulk/imports` (file_id + тип импорта) → `job_id`; `GET /api/v1/bulk/imports/{job_id}` — статус (QUEUED/PROCESSING/DONE/FAILED), счётчики (всего/успешно/ошибки). |
| ИН-12.5.3 | Отчёт об ошибках — построчный: номер строки, поле, код и текст ошибки (модель ИН-12.1.7); выдаётся файлом (CSV) и в JSON. Частичный успех допустим: валидные строки применяются, ошибочные — в отчёт (режим «всё или ничего» — опцией `atomic=true`). |
| ИН-12.5.4 | Семантика строк — upsert по бизнес-ключам (РМА, госномер); лимит — 10 000 строк на файл (конфигурируемо); квоты — по уровню аккредитации/тарифу. |
| ИН-12.5.5 | Массовые выгрузки (замена ночного окна legacy): `POST /api/v1/exports` (сущность, фильтры, формат CSV/XLSX/JSON) → асинхронное задание → ссылка на файл в S3 с ограниченным сроком действия. |

## 12.6. Аккредитация интеграторов

| № | Требование |
|---|---|
| ИН-12.6.1 | **Процедура**: заявка на портале разработчика → проверка заявителя (ЮЛ, РМА, вид деятельности) → договор с оператором Платформы (ГУП ЦЦТО) → доступ в sandbox → сертификационные испытания → приказ об аккредитации → выдача продуктивных ключей. Реестр аккредитованных интеграторов публичен. |
| ИН-12.6.2 | **Тестовый контур (sandbox)**: полнофункциональная среда с тестовыми данными и эмуляторами внешних систем (единая платформа, E-PERMIT, УЦ, платёжный шлюз); отдельный Keycloak-realm; тестовые РМА/госномера; данные периодически очищаются. Sandbox доступен до и после аккредитации без ограничений по функциональности. |
| ИН-12.6.3 | **Сертификационные испытания**: обязательный чек-лист сценариев (создание заявки, обработка 409 до Т2/Т3, получение подтверждённого ПЛ, правило 7 дней, идемпотентность, обработка ошибок RFC 7807, приём webhooks с проверкой подписи, rate limiting). Протокол испытаний прилагается к договору. |
| ИН-12.6.4 | **Договор и лимиты**: договор фиксирует уровень аккредитации и квоты (rps, суточные объёмы, число организаций-клиентов), SLA сторон, требования ИБ (хранение токенов, инциденты), ответственность за достоверность данных. Уровни (базовый/расширенный) различаются лимитами и доступом к v2-возможностям. |
| ИН-12.6.5 | **Мониторинг**: по каждому интегратору — метрики (объёмы, error rate, латентность, доля 4xx/5xx, подозрительные паттерны: массовые аннулирования, фиктивные рейсы); личный кабинет интегратора с дашбордом и журналом вызовов; алерты оператору Платформы. |
| ИН-12.6.6 | **Приостановка и отзыв**: автоматическая приостановка при инциденте ИБ или систематическом превышении квот; отзыв аккредитации — решением оператора по договору (нарушение условий, недостоверные данные, неустранённые замечания) с уведомлением ≥ 30 дней (кроме инцидентов ИБ — немедленно); отзыв не затрагивает ранее выданные документы; организации-клиенты уведомляются и переводятся на другого интегратора или прямой доступ. |
| ИН-12.6.7 | Все действия по аккредитации (выдача/ротация ключей, изменение квот, приостановки) фиксируются в журнале аудита Платформы. |
