# 05. Соответствие Платформы каталогу стандартов АГВ

Источник: `docs/Стандарты АГВ (1) .xlsx` — каталог международных стандартов (в основном серия ISO/IEC), применимых к государственным ИТ-системам РТ. Два листа: «Лист1» (40 позиций, обзорный) и «По секторам» (тот же каталог, детализированный по частям серий — 121 строка, сгруппированная по доменам: СМИБ, сетевая безопасность, реагирование на инциденты, криминалистика, управление ключами, крипто-сертификация, приватность, критическая инфраструктура, облако, риск-менеджмент, аудит, DevSecOps, ISO 20022, PAdES, ITSM, ITAM, хранение данных, Common Criteria, OT-безопасность, цифровая подпись).

Это не набор функциональных требований к путевому листу, а институциональный чек-лист: часть стандартов ложится на код и архитектуру Платформы напрямую, часть — на процессы эксплуатации будущего оператора (ГУП ЦЦТО/Минтранс/АГВ), часть в принципе не применима к домену (нет SCADA/АСУ ТП, нет прямого банковского SWIFT-обмена).

Раздел 13 ТЗ (`spec/ru/13-безопасность.md`) уже спроектирован так, что покрывает содержательно почти все технически релевантные стандарты каталога (см. таблицу ниже). Вопрос не «что доработать в ТЗ», а **что из уже описанного в разделе 13 реально реализовано в текущей сборке, а что — только текст ТЗ**. Ниже — сведение по факту кода (аудит проведён 2026-09-03: полный обход `apps/backend/*`, `infra/`, `apps/web`, `scripts/`, `.github/workflows`).

### Организационное — не код, ответственность заказчика/будущего оператора платформы
- Формальная политика ИБ / документ СМИБ (27001), реестр процессов обработки ПДн, план реагирования на инциденты, регламенты ITSM/ITAM эксплуатации, программа обучения персонала, внешний пентест перед вводом в пром. эксплуатацию (по плану — и так не должен запускаться раньше готовности). Это зона ответственности АГВ/Минтранса/оператора, не то, что можно «доделать в коде».

### Не применимо к платформе
- OT/АСУ ТП (62443, 27019) — нет промышленных систем.
- Облачные стандарты (27017/27018/19086/19944) — хостинг не публичное облако; MinIO в compose не используется ни одним сервисом (мёртвая инфраструктура — можно убрать или начать реально использовать для вложений).
- ISO 20022, PCI DSS — платформа не является прямым участником банковского обмена и не принимает карты напрямую; ответственность лежит на биллинговом шлюзе E-PERMIT.
- Common Criteria (15408) — продуктовая сертификация крипто-модулей нацУЦ, не зона ответственности разработки прикладной платформы.

## 5.4. Почему TLS сознательно не включён на этом стенде (2026-09-03)

Разобрано с заказчиком: полное включение TLS на текущем локальном Windows-стенде означало бы —
- self-signed сертификат → браузер ругается на каждой странице, пока сертификат не установлен вручную;
- перевод Keycloak из dev-режима (`start-dev`, встроенное хранилище) в прод-режим (`start`) требует отдельной Postgres-БД для самого Keycloak и единого внешнего hostname — нетривиальная миграция с реальным риском сломать вход целиком;
- переезд ~20 QA-скриптов и всех закладок/адресов, которыми пользуется заказчик прямо сейчас, с `http://localhost:*` на `https://...`.

На реальном сетевом окружении (за пределами localhost/loopback) риск отсутствия TLS реален и описан выше (п.1) — но здесь, на изолированном локальном стенде, где к сервисам обращается только сама машина, риск утечки трафика по сети отсутствует по построению (нечего перехватывать за пределами loopback-интерфейса). Решено не жертвовать стабильностью работающего, полностью протестированного демо-стенда ради TLS, который на этом конкретном контуре не даёт реального выигрыша в защите — и задокументировать это здесь как оргзадачу для реального развёртывания.

**Когда переносить на реальный контур (госЦОД/выделенный сервер с доменом):** план уже зафиксирован комментарием `TODO(prod)` в `infra/docker-compose.prod.yml` у сервиса `keycloak` — (1) reverse-proxy (nginx/Traefik) с сертификатом от реального УЦ (не self-signed), (2) `KC_DB=postgres` + отдельная БД `keycloak` в общем Postgres по аналогии с `masterdata`/`waybill`, (3) `KC_PROXY_HEADERS=xforwarded` + `KC_HTTP_ENABLED=true` (Keycloak слушает HTTP только за прокси) + единый `KC_HOSTNAME`, (4) обновить все базовые URL в скриптах/фронтенде на `https://`.
